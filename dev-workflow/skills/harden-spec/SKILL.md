# harden-spec

**Announce:** "harden-spec으로 spec을 적대적으로 압박해 굳힙니다."

## 핵심 원칙

brainstorming이 만든 **spec 초안을, plan/구현으로 넘어가기 전에 적대적으로 압박**해서, 늦게 발각되면 기능을 재설계·재구현하게 만드는 갭을 **지금** 메운다. 대상은 *작성된 spec 파일*이고, 결과물은 **더 단단해진 그 파일 자체**다(별도 문서 아님).

프리모템 태도로 본다: **"이 기능을 다 만들었는데 결국 재설계하게 됐다 — 무엇을 놓쳤었나?"**

갭의 처리는 셋뿐이다:

1. **사실** — 코드·문서 직접 조회로 해소(근거 명시). 사용자에게 묻지 않는다.
2. **판단** — 조회로 답이 유일하게 결정되지 않는 것(요구·정책·트레이드오프·기본값). **전부 사용자에게 질문해 해소한다.**
3. **유예(DEFERRED)** — 판단 갭 중 **사용자가 질문에 "나중에"라고 답한 것만.**

**질문 없이 닫히는 판단 갭은 없다.** "자명한 기본값"의 판정자도 사용자다 — 자명하면 질문이 싸다(추천답 수락 한 번). 분류가 애매하면 판단이다.

## 모델 고정 (fable)

이 스킬은 frontmatter로 `model: fable` + `effort: max`를 고정한다 — 놓친 갭 하나가 재설계를 부르는 단계라 세션 모델과 무관하게 최고 성능으로 압박한다. 단, 이 오버라이드는 **스킬이 invoke된 턴에만** 유효하고 사용자의 다음 프롬프트에서 세션 모델로 복원된다. 따라서:

- 질문·diff 승인을 전부 **AskUserQuestion 도구로** 진행해 압박 전체를 한 턴 안에서 끝낸다(도구 응답은 턴을 끊지 않는다).
- 사용자의 자유 입력으로 턴이 끊긴 뒤 재개하는 시점에 현재 모델이 fable이 아니면, **`/model fable` 전환을 1회 권고**하고 사용자 선택 후 재개한다(전환 거절 시 그대로 진행).

## 언제 / 언제 아님

- **쓴다:** brainstorming으로 spec 초안이 있고 review-loop/plan 전에 굳히고 싶을 때. **또는 아직 파일은 없어도 이미 손에 쥔 계획·아이디어를 압박해 굳히고 싶을 때**(§입력 — 느슨한 계획 모드).
- **안 쓴다:**
  - 압박할 설계 자체가 백지다(계획조차 없다) → 먼저 `superpowers:brainstorming`.
  - 코드/구현의 결함을 찾는다 → `dev-workflow:review-loop`(codex).
  - 우호적 협업 설계를 하고 싶다 → `superpowers:brainstorming`.

**파이프라인 내 자리 (상보 관계):**

```
brainstorming → spec 초안 → [harden-spec] → review-loop(spec) → plan → 구현
  (협업·우호)              (적대·사람)        (codex·산출물)
```

harden-spec은 codex가 못 보는 것 — *사람만 아는 누락된 요구·숨은 가정·제품 지식* — 을 먼저 메워, 뒤따르는 review-loop가 진짜 결함에 집중하게 한다.

## 입력

- 대상 spec을 인자로 받는다(경로 또는 feature 슬러그).
- 생략 시 `docs/specs/`의 최신 파일 또는 현재 브랜치에 대응하는 spec을 찾아 **"이 spec을 압박합니다: `<path>` — 맞나요?"로 확인한 뒤** 시작한다.
- `docs/specs/`가 없으면 대상 문서를 사용자에게 묻는다.
- **느슨한 계획 모드 (파일 없는 입력):** 대상이 파일이 아니라 대화 중 제시된 계획·아이디어·초안이어도 된다. 이 경우:
  - 그 서술을 §절차 1의 "spec 주장"으로 삼고, repo 컨텍스트(CLAUDE.md·ADR·기존 spec)로 불변식·기결정만 보강한다 — 대상 파일이 없을 뿐 project-aware·프리모템은 동일.
  - 하드닝(§절차 4)은 반영할 파일이 없으므로, 종료 시 **"확정된 결정을 `docs/specs/`에 spec 초안으로 남길까요?"**를 제안한다 — 승인 시 초안 생성, 거절 시 결정·잔여 리스크 요약으로 종료.
  - 압박할 *계획 자체가 없는 백지*면 harden-spec이 아니라 `superpowers:brainstorming`이다.

## 절차 (5단계)

### 1. 로드 (context 우선)
대상 spec 본문 + 실행 repo의 `CLAUDE.md`·`AGENTS.md`·`docs/adr/`·`docs/specs/`를 읽어 세 바구니로 분류한다:
- **불변식/함정** — 이 repo가 반복적으로 밟는 규칙(CLAUDE.md에서 추출).
- **기결정** — ADR·spec `D<n>`·명시 규칙·이미 내려진 사용자 결정. **압박 대상에서 제외**(§기결정 가드).
- **spec의 주장** — 이 spec이 무엇을 하겠다는가(범위·정책·데이터·상태전이·AC).

repo에 위 문서가 없으면 범용 세트로 폴백하되, **일반 질문만 하지 말고** 최소한 spec 본문의 내부 정합성부터 판다.

### 2. 갭 스윕 → 갭 대장(ledger)
§커버리지 축을 훑어 spec이 **침묵·모호·모순·미검증**인 지점을 모아 **갭 대장**을 만든다:

| # | 갭 | 축 | 위험 | 분류(사실/판단) | 처리 |

- **rework 위험순 정렬**: 비가역(마이그레이션·데이터) → 교차모듈 파급 → 불변식 접촉 → 그 외.
- **사실**은 코드·문서를 직접 조회해 근거와 함께 `해소(조회)`로 기록한다 — 사용자에게 묻지 않는다. 사실은 **조회로 답이 유일하게 결정될 때만**이다 — spec·AC 문구가 *함의*하는 수준(명시 아님)이면 판단이다(묶음 질문 한 칸이면 닫힌다).
- **판단**은 전부 질문 대상이다. 대장에서 질문 없이 지워지는 판단 갭은 없다.
- **검증 필요(실측)** — 조회 불가(repo에 해당 코드·문서 없음)이고 **사용자가 결정할 수도 없는** 외부 사실(인프라 특성·데이터 실측치 등)만, 질문 대신 근거와 함께 `잔여 리스크`에 "구현/전환 단계 실측 항목"으로 남긴다. 사용자가 결정할 수 있는 것은 여기 못 들어간다 — 그건 판단이다.
- 대장은 압박 내내 갱신하고 §종료 산출에서 전체를 보고한다 — 갭이 조용히 사라질 곳이 없다.

### 3. 압박 (하이브리드 질문, 전부 AskUserQuestion)

질문은 예산이 아니라 **커버리지다**: 갭 대장의 판단 갭이 **소진될 때까지** 묻는다. 사용자가 바쁘다고 하면 **질문 수를 줄이는 게 아니라 묶음 비중을 높여 라운드 수를 줄인다** — 커버리지는 불변.

모든 질문은 **AskUserQuestion 도구**로 던진다: 추천답을 첫 선택지로 놓고 "(추천)"을 붙이며, 근거는 선택지 description에 적는다. 자유 서술 답은 사용자가 Other로 쓴다.

- **고위험 갭** — 비가역·마이그레이션, 교차모듈 파급, 불변식 접촉, **AC·목표 자체를 바꾸는 결정**: **한 번에 1문**, 답을 받고 필요한 꼬리 질문까지 파고든 뒤 다음 갭으로.
- **그 외 판단 갭**: **최대 4문 묶음 라운드**를 반복해 소진한다.
- **결정 하나 = 질문 하나.** 여러 결정을 한 질문으로 병합해 개수를 줄이지 않는다 — 나란히 묶음 라운드에 넣는 것이 올바른 병합이다.
- 기결정은 건너뛴다(가드). 신규 갭이 기결정과 충돌하면 재론이 아니라 "이 기결정이 이 spec과 양립하는가"만 확인한다.

### 4. 하드닝 (제안 후 적용)
갭이 해소될 때마다 **spec에 넣을 구체 문구(diff)를 제안**하고, 승인되면 **파일에 반영**한다. 승인도 AskUserQuestion으로 받는다(반영/수정/보류 — 턴 유지). 변경 단위를 작게 유지해 되돌리기 쉽게 한다. 결정·엣지케이스·실패 모드·범위 경계를 spec의 해당 섹션(결정사항·AC·비목표 등)에 실제로 기록한다.

**diff 승인은 문구 검토지 결정이 아니다** — 결정 자체는 반드시 §절차 3의 질문으로 받은 뒤 diff에 담는다. 묻지 않은 결정을 diff에 심지 않는다.

### 5. 종료
§종료 산출 참조.

## 커버리지 축 (project-aware)

목록을 실행 repo의 CLAUDE.md에서 실제로 추출하고, 없거나 얕으면 이 범용 세트로 폴백한다.

| 축 | 묻는 것 |
|---|---|
| 완결성 | 명시 안 된 요구·엣지케이스·빈 상태·에러/실패 모드 |
| 불변식 준수 | repo 규칙 위반 소지(예: 권한 fail-closed, 트랜잭션·CAS·낙관락, 시각/타임존, enum 동기화) |
| 교차 영향 | 다른 모듈·기존 데이터·권한·마이그레이션에 미치는 파급 |
| 동시성·상태전이 | 트랜잭션 경계, 상태 전이표의 누락 전이, 경쟁 조건 |
| 비가역·롤백 | 마이그레이션 가역성, cutover, 롤백 계획 |
| 검증가능성 | 이 spec이 맞는지 어떻게 테스트/관측하나(AC가 검증 가능한가) |
| 범위 경계 | 무엇을 **안 하는지**가 명시됐나(scope creep 방지) |
| 숨은 가정 | 명시 안 된 가정이 뒤집히면 설계가 무너지나 |
| 제품 정책·수신자 경험 | 사용자 설정(opt-out 등)·기본값·노출 방식 — 코드로 답이 결정되지 않는 제품 결정 |
| 시간 경과·데이터 변화 | 생성 시점과 처리 시점 사이에 대상이 삭제·변경·권한 회수되면 어떻게 되나 |

## 기결정 가드 (review-loop 연동)

ADR·spec `D<n>`·명시 규칙·이미 내려진 사용자 결정은 **재론하지 않는다.** harden-spec은 기결정을 *전제로* 그 위의 갭만 판다.

| 합리화 | 실제 |
|---|---|
| "이 기결정이 틀린 것 같은데 다시 따져보자" | 기결정 번복은 harden-spec의 일이 아니다. 정말 위험하면 갭이 아니라 **DEFERRED로 남겨 사용자가 별도로 재론**하게 한다. 압박 흐름에서 재론하지 않는다. |
| "ADR을 못 봤으니 그냥 물어보자" | 먼저 `docs/adr`·spec `D<n>`을 **읽는다**. 거기 있으면 기결정이다. |
| "확실히 하려고 한 번 더 확인" | 기결정 재확인에 질문을 쓰지 않는다. 질문은 열린 갭을 소진하는 데 쓴다. |

종료 시 확정된 결정·재론 금지 항목을 spec 안에 **`## 재논의 금지(기결정)` 블록**으로 남긴다. 이는 review-loop가 쓰는 규약(가드는 *리뷰 대상 문서 안*에 있어야 codex가 본다)과 같아, review-loop의 재지목을 선제적으로 줄인다.

## 질문 회피 합리화 (전부 무효)

| 합리화 | 실제 |
|---|---|
| "자명한 기본값이라 질문 없이 diff로 제안하면 된다" | 자명 여부의 판정자는 사용자다. 자명하면 추천답 수락 한 번 — 질문이 더 싸다. |
| "diff 승인 때 사용자가 어차피 본다" | 승인은 문구 검토다. 묻지 않은 결정을 diff에 심는 것은 결정을 대신 내리는 것이다. |
| "사용자가 바쁘다니 질문을 줄이자" | 줄이는 것은 라운드 수(묶음 확대)지 커버리지가 아니다. 안 물은 갭은 그대로 rework 위험이다. |
| "AC·불변식이 이미 방향을 정했다" | 방향이 정해져도 남는 트레이드오프는 판단이다. 특히 **AC를 조정하는 추천은 반드시 단독 질문**이다. |
| "기존에도 있던 이슈라 이 spec 고유의 갭이 아니다" | 이 spec이 접촉하는 순간 이 spec의 갭이다. 질문하거나, 사용자가 미루면 DEFERRED다. |
| "질문이 벌써 N개라 너무 많다" | 질문 수 상한은 없다. 소진 기준은 갭 대장이지 개수 감각이 아니다. |

## 종료 산출

세션 종료 시 대상 spec 파일에 다음이 있어야 한다:
1. 압박으로 확정된 결정·엣지케이스·실패 모드가 반영된 **실제 diff**.
2. **`## 재논의 금지(기결정)`** 블록(기결정 + 이번에 확정한 결정).
3. **`## 잔여 리스크 (DEFERRED)`** — 사용자가 유예한 갭을 명시(은폐·무시 금지). **질문을 거치지 않은 DEFERRED는 존재할 수 없다.**

그리고 종료 보고에 **갭 대장 최종 상태 전체**를 표로 출력한다 — 모든 갭이 `해소(조회)` / `해소(질문·결정)` / `DEFERRED(사용자 유예)` / `검증 필요(실측)` 중 하나여야 하며, 그 외 상태로 남은 갭이 있으면 아직 끝난 게 아니다.

그다음:
- **커밋**: spec 파일만 **명시적으로 stage 후 커밋**한다.
  - `.git/index.lock`이 있으면 다른 세션이 git 사용 중 — 지우지 말고 기다린다.
  - `git add -A` 금지(무관한 untracked·다른 세션 작업 혼입 — 이 세션이 수정한 파일만 명시 stage).
  - 커밋 메시지에 AI 서명/도구 흔적 금지(글로벌 규칙).
- **정지**: 다음 단계(review-loop → plan)는 **자동 전환하지 않고** 권고만 한다. 단계 경계는 *새 세션 + `/clear`* 규약(핸드오프 후 사람이 시작). 단, **spec이 새 화면을 만들거나 기존 화면 구성을 바꾸면 review-loop 전에 `dev-workflow:ui-mockup`(3.5)을 먼저 권고한다** — 화면 결정이 spec에 들어간 뒤 적대검증을 받아야 목업발 변경도 검증망 안에 있다.

## 하지 말 것 (red flags — 멈추고 자기점검)

- 판단 갭을 **질문 없이** diff 제안·DEFERRED·"자명한 기본값"으로 닫는다 → 처리는 셋뿐: 조회(사실)·질문(판단)·사용자 유예(DEFERRED).
- 고위험 갭을 묶음에 섞거나, **여러 결정을 한 질문으로 병합**한다 → 고위험은 단독 1문, 결정 하나당 질문 하나.
- 질문을 채팅 텍스트로 던진다 → **AskUserQuestion 도구**로(모델 고정 유지 + 추천답 구조화).
- **기결정(ADR·`D<n>`·사용자 결정)을 재론**한다 → 전제로 두고 갭만 판다.
- spec·CLAUDE.md를 **안 읽고 일반 질문**을 한다 → 먼저 로드해서 그 repo의 불변식으로 압박한다.
- 코드에서 확인 가능한 **사실을 사용자에게 묻는다** → 직접 조회한다.
- 압박이 끝나자 **다음 단계로 자동 전환**한다 → 정지하고 새 세션을 권고한다.
- 못 닫은 갭을 **조용히 넘긴다** → 질문 후 사용자가 미룬 것만 DEFERRED로 명시한다.
- `git add -A`로 커밋하거나 **AI 서명**을 넣는다 → 명시 stage + no-AI-trace.

## 인자

- (선택) 대상 spec 경로/슬러그. 생략 시 자동 탐색 + 확인.
- 그 외 인자는 두지 않는다(파일 하나를 읽으므로 git 기준 등 불필요).
