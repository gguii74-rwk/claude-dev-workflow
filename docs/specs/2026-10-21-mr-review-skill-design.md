# mr-review 스킬 설계 — 남의 MR을 두 모델이 독립 검토해 팀 정책 형식의 판정 초안을 만든다

> 상태: 설계(브레인스토밍·빌더 검토 완료, 사용자 승인 대기) · 작성 2026-10-21
> 관련: `review-loop`(자기 작업의 적대검증 루프 — 이 스킬과 다르다, §1.3), 프로젝트별 어댑터 문서(프로젝트의 공통 문서 저장소에 둔다, §4)

## 1. 의도

### 1.1 왜

팀에 MR 작성 규칙(변경 사유, 기준선 링크, 배포본 첨부)과 리뷰 판정 규칙이 있어도, 리뷰어가 매번 손으로 대조하지 않으면 지켜지지 않는다. 실제로 한 프로젝트의 최근 5주 머지 MR을 다시 세어 보니 기준선 칸이 비었다고 집계된 MR의 절반은 문서가 있는데 칸에 위치를 안 적은 경우였고, 리뷰어는 그 차이를 알 수 없었다. 코드 결함보다 더 자주 빠지는 것은 **판단**이다 — 왜 고치는지, 어떤 방법을 왜 골랐는지, 다른 곳에 번지지 않는지, 필요 이상으로 고치지 않았는지.

이 스킬은 리뷰어가 MR 번호 하나를 주면 (1) 작성 규칙 준수를 기계적으로 검사하고, (2) 서로 다른 두 모델이 서로의 결과를 보지 않고 위 판단을 검토한 뒤, (3) 팀 리뷰 정책이 정한 출력 형식으로 **판정 초안** 하나를 만든다. 게시와 승인은 사람이 한다.

### 1.2 누가, 언제

지정된 사람 리뷰어가, MR이 열린 뒤, 자기 PC의 Claude Code 세션에서 수동으로 돌린다. 첫 사용자는 PM 겸 리뷰어 1명이고, 결과가 좋으면 다른 리뷰어에게 공유한다. 공유를 전제로 경계 세 가지를 처음부터 지킨다(§5.4).

### 1.3 review-loop와 무엇이 다른가

| | review-loop | mr-review |
|---|---|---|
| 대상 | 내가 만든 spec·plan·구현 | 남이 올린 MR |
| 목적 | 결함을 찾아 고친다(적대) | 판단·규칙 준수를 검토해 판정 초안을 만든다 |
| 쓰기 | 코드 수정·커밋·ledger | **읽기 전용** — 저장소도 GitLab도 안 바꾼다 |
| 판정 어휘 | FIXED/ACCEPTED/… (플러그인 고유) | **팀 정책 어휘만**(APPROVE/HOLD_EVIDENCE/CHANGES_REQUESTED/RETURN_TO_DESIGN) |
| 모델 | Codex 리뷰, Claude 수정 | Claude·Codex 독립 병렬 → Claude 통합 |
| 반복 | 미판정 0까지 루프 | 1회. 새 커밋이 오면 다시 돌린다 |

## 2. 목표 · 비목표 · 실패 조건

**목표**

- G1. 작성 규칙 검사(Review Contract 10줄, 기준선 위치, 변경 사유 3줄, 배포본 첨부, 리베이스 필요)를 모델 없이 결정적으로 수행하고 결과를 표로 보여 준다.
- G2. 어댑터가 정한 렌즈(§4.3)로 두 모델이 독립 검토한다. 어느 모델이 무엇을 잡았는지 항상 구분한다.
- G3. 출력은 팀 정책의 실행 블록 형식 그대로다. 리뷰어가 복사해 게시할 수 있다.
- G4. 프로젝트 공통 문서와 팀 위키를 근거로 읽고, 어느 문서를 근거로 썼는지 리포트에 남긴다.
- G5. Codex가 없는 환경에서도 Claude 한 모델로 돌아가되, 결과에 「교차 검토 없음」을 표시한다.

**비목표**

- GitLab에 댓글·승인·라벨·이슈를 쓰는 것. 폴링·웹훅·CI 연동.
- 테스트·빌드 실행. 검증 상태는 전부 `[판독]`이다(사용자 결정 2026-10-21). 단 배포본 zip과 head의 **파일 대조**(§5.2b)는 실행이 아니라 비교라 범위 안이다(사용자 결정 2026-10-21).
- 적대적 결함 사냥. 정책이 「변경 범위 밖 재감사는 임무가 아니다」라고 정했다.
- 판정 규칙을 새로 만드는 것. 정책은 「스킬은 어댑터일 뿐 별도 판정 규칙을 만들 수 없다」고 못 박았다.
- 고도화팀 포크 내부 MR 지원(어댑터 2차 범위, 어댑터 문서 §7).

**실패 조건**(기술적으로 돌아가도 실패)

- F1. GitLab에 무엇이든 썼다.
- F2. 한 모델만 돌았는데 두 모델이 합의한 것처럼 읽힌다.
- F3. 조건부 승인(「승인 가능하지만 테스트 남음」)을 출력했다.
- F4. 어댑터가 외부 전송을 금지한 자료(개인 위키 등)가 Codex 프롬프트에 들어갔다.
- F5. 토큰·비밀값이 리포트·로그·프롬프트 파일에 남았다. 어댑터가 정한 개인정보 패턴이 가려지지 않은 채 Codex 프롬프트에 들어갔다.
- F6. 리뷰한 head SHA와 리포트의 SHA가 다르다.
- F7. 임시 워크트리나 내려받은 배포본 zip이 남았다.
- F8. 리뷰어가 동의한 적 없는 기준선 위에서 `APPROVE` 초안이 나왔는데 리포트가 그 사실을 표시하지 않았다.

## 3. 제약

- 팀 리뷰 정책(어댑터가 경로·버전을 지정)이 SSOT다. 출력 첫 줄·절 순서·판정 4종·발견 유형 4종·조건부 승인 금지·길이 40줄을 그대로 따른다.
- **정책 버전 전환기**: 정책 최신판과 MR 템플릿에 박힌 계약 버전이 다를 수 있다(어댑터 §2가 현재 상태를 적는다). 판정 초안 첫 줄의 정책 ID는 **MR 계약에 적힌 버전**을 쓰고(다른 도구가 그 ID로 판정 댓글을 인식한다), 판정 기준·실행 블록 본문은 **어댑터가 지정한 최신판**을 쓴다. 리포트 헤더에 두 버전을 병기한다. 이전 판정 댓글 파싱은 두 ID를 모두 받는다(이 설계의 결정 — 정책의 전환 기간 조항을 따른 것).
- Codex는 codex 플러그인 companion(≥1.0.6)의 `task --prompt-file`로 호출한다. 샌드박스는 read-only, cwd 밖은 못 읽으므로 근거 문서는 **프롬프트 파일 본문에 발췌로** 넣는다. 동시 1작업. 실행·회수 절차는 review-loop §2b(파일로 띄우고 파일로 받기, `COMPANION_EXIT` 마커, 실행 로그 ≥1 확인)를 그대로 쓴다.
- 이 플러그인 저장소는 공개다. 프로젝트 이름·내부 주소·사람 이름·문서 경로는 플러그인에 넣지 않고 어댑터에 둔다.
- 외부 모델 전송 범위는 어댑터의 허용 목록을 넘지 않는다. 범위를 넓히려면 사용자 결정이 필요하다.
- GitLab 읽기는 `glab api`로 한다(이미 쓰는 도구, 토큰 관리 안 함). `glab mr` 하위 명령은 호스트 불일치로 실패하는 환경이 있어 쓰지 않는다.

## 4. 어댑터 계약 — 스킬이 프로젝트에서 받는 것

스킬은 `--adapter <경로>` 인자 또는 환경변수 `MR_REVIEW_ADAPTER`로 어댑터 문서 하나를 받는다. 없으면 멈추고 안내한다. 어댑터는 마크다운 한 파일이며 다음 절을 가진다(절 제목 고정, 내용은 프로젝트가 정한다).

| 절 | 내용 |
|---|---|
| 4.1 저장소 | GitLab 호스트, 프로젝트 이름 ↔ 프로젝트 ID ↔ 로컬 체크아웃 경로(워크스페이스 루트 기준) |
| 4.2 정책 | 리뷰 정책 문서 경로·정책 ID, 표준 절차 문서 경로, 추가로 항상 읽을 절 |
| 4.3 렌즈 | 검토 질문 목록. 각 렌즈 = 질문 · 근거 문서 · 발견 시 매핑되는 발견 유형(DEFECT/MISSING_EVIDENCE/DESIGN_DRIFT/FOLLOW_UP) · 차단 승격 조건 |
| 4.4 문서 지도 | 변경 파일 경로 패턴 → 읽을 공통 문서. 항상 읽을 문서와 영역별 문서를 나눈다. **기준선 후보 경로 패턴**(diff 안의 어떤 문서를 기준선 후보로 볼지) |
| 4.5 위키 | 위키 루트(여러 개 가능, 각각 `외부 모델 전송: 허용/금지`), 용어집 파일, 검색 규칙, 발췌 상한 |
| 4.6 외부 전송 허용 | Codex 프롬프트에 넣어도 되는 자료 목록(화이트리스트)과 전송 전 가릴 개인정보 패턴. 목록에 없는 것은 넣지 않는다 |
| 4.9 댓글 형식 | 이전 판정 댓글 첫 줄 패턴(정책 ID 버전별), 기준선 확인 댓글 패턴, 작성자 응답 토큰, **신뢰 리뷰어 목록**(Human reviewer 외에 판정 댓글을 인정할 GitLab 계정) |
| 4.7 운영 배포 대상 | 배포본 첨부가 필수인 변경 파일 경로 규칙 |
| 4.8 리포트 | 리포트 저장 디렉터리(git 밖), 파일명 규칙 |

## 5. 동작

### 5.0 전제 확인

`glab` 인증, 어댑터 파일, 로컬 체크아웃, codex companion 경로·버전(review-loop §2b ①과 같은 해소 절차). companion이 없거나 낡았으면 **단일 모델 모드**로 계속하되 시작 시 한 줄로 알린다. 어댑터·glab이 없으면 멈춘다.

### 5.1 MR 수집

1. `glab api`로 MR 메타(제목·본문·source/target·head SHA·`need_rebase`·reviewer·approvals), 변경 파일 목록, 댓글(시스템 이벤트 제외)을 읽는다.
2. **스냅샷 고정.** 로컬 체크아웃에서 `git fetch origin <target>`과 `git fetch origin refs/merge-requests/<iid>/head`를 한 뒤, **fetch한 head SHA가 1에서 읽은 API head SHA와 같은지 확인한다 — 다르면(수집 사이에 push가 있었음) 1부터 다시 한다.** target도 fetch 직후의 SHA로 고정하고 base = `merge-base <target SHA> <head SHA>`. 이후 diff·변경 파일 목록·배포본 대조·리포트는 전부 이 세 SHA(target·base·head)에 귀속한다. 세션 scratchpad에 임시 워크트리를 만든다(같은 이름 잔존물은 먼저 제거). 이후 모든 단계는 이 워크트리의 파일을 읽는다.
3. 로컬 체크아웃이 없으면 API 변경분으로 diff-only 모드. 잘림(`overflow`·`too_large`)이 있으면 API diff 버전의 base·head SHA를 고정하고, 그 파일을 **base와 head 양쪽에서** raw 파일 API로 받아 로컬에서 diff를 다시 만든다(이름 변경은 diff 메타의 old_path·new_path로, 삭제는 head 쪽 없음으로 처리). head 파일 하나만 받는 것은 복원이 아니다 — 삭제된 코드가 보이지 않는다. **양쪽 blob으로 diff를 재구성하지 못한 변경 파일이 하나라도 있으면 그 파일들을 `MISSING_EVIDENCE`로 「차단 발견」에 적고 판정은 `APPROVE`가 될 수 없다**(파일 수 비율로 판단하지 않는다 — 작은 파일 하나가 인증 코드일 수 있다). 리포트 맨 위에 「불완전 diff-only 리뷰」 경고와 그 목록을 적고 로컬 clone을 권한다.
4. 댓글에서 **이전 판정 댓글**(첫 줄이 정책의 판정 형식)과 **작성자 응답 토큰**(`FIXED <sha>`·`EVIDENCE`·`BASELINE_UPDATED`·`REFUTED`·`FOLLOW_UP_REQUESTED`)을 뽑는다. **형식만으로 믿지 않는다** — 이전 판정 댓글은 GitLab 댓글 작성자(API의 author id)가 **GitLab MR의 reviewers 필드에 실제로 지정된 계정**이거나 어댑터 4.9의 신뢰 리뷰어 목록에 있을 때만 인정한다. MR 본문의 `Human reviewer` 줄은 작성자가 쓰는 값이라 신뢰 기준으로 쓰지 않는다(reviewers 필드와 다르면 §5.2 검사표에 「reviewer 불일치」로 적는다). **MR 작성자 계정은 어느 목록에 있어도 판정 댓글 작성자로 인정하지 않는다.** 작성자 응답 토큰은 댓글 작성자가 MR 작성자일 때만 인정한다. 조건에 안 맞는 댓글은 「무시한 댓글」로 부록에 적는다. 신뢰할 이전 판정이 없으면 재리뷰 모드로 가지 않고 전체 리뷰를 한다. 인정된 이전 판정의 head가 현재 head와 다르면 **재리뷰 모드**(§5.6).

### 5.2 작성 규칙 검사 — 모델 없이

결정적 검사. 결과는 표 한 장이며 리포트 부록 A가 된다.

| 검사 | 판정값 |
|---|---|
| Review Contract 10줄 | 각 줄 `채움 / 자리표시자 / 없음`. `Policy` 줄이 최신판과 다르면 `채움(구버전)` — 미완이 아니다(§3 전환기) |
| 기준선 확인 댓글 | 경량 트랙이면 GitLab reviewers 필드의 리뷰어가 쓴 「기준선 확인」 댓글(어댑터가 형식을 정한다)이 있는가 → `있음 / 없음 / 낡음 / 해당 없음(정식·핫픽스)`. **「낡음」** = 확인 댓글보다 뒤에 MR 본문이 바뀜(GitLab 시스템 노트 「changed the description」의 시각 또는 MR `updated_at`이 댓글 시각보다 뒤) — 리뷰어가 동의한 기준선이 지금 본문과 같다고 볼 수 없으므로 「없음」과 같이 처리하고 F8 표시·재확인 문안을 낸다. head가 그대로여도 본문만 바뀌면 낡음이다 |
| `Baseline` 유형 | `문서 링크 / MR 본문 배경 / 이슈 / 서술만 / 빈칸·자리표시자 / 칸 없음` |
| 변경 사유 ①② | 「배경」 또는 링크된 이슈에 ①왜 ②무엇을이 있는가(양식 문구 그대로면 없음) |
| 변경 파일 속 문서 | 어댑터 4.4가 정한 **기준선 후보 경로 패턴**(설계·spec·변경 기록 문서)에 맞는 파일이 diff에 있는가. 있으면 기준선 **후보**일 뿐이다 — 그 문서가 이번 변경(제목·변경 파일·②의 적용 범위)을 다루는지 모델 검토자(§5.4)가 확인해 맞을 때만 **「위치 미기재」**(근거 없음과 구분), 아니면(오탈자 수정 등 무관 문서) 기준선 없음 그대로 |
| 첨부 | 본문·댓글의 업로드 링크 분류: 배포본 zip / 문서 / 로그 / 없음. 본문이 「첨부했다」고 쓰는데 링크가 없으면 **「첨부 누락」** |
| 배포본 | 어댑터 4.7 규칙으로 운영 배포 대상이면 zip 첨부 필수 여부. 첨부가 있으면 §5.2b 대조 결과 |
| 리베이스 | `need_rebase` |

**기준선 미확인 처리(사용자 결정 2026-10-21):** 경량 MR에 기준선 확인 댓글이 없어도 리뷰는 끝까지 진행하고 판정 초안을 낸다. 대신 리포트에 「리뷰어가 먼저 게시할 기준선 확인 문안」 절을 넣고 헤더에 「기준선 미확인 — 확인 문안을 먼저 게시한 뒤 판정을 게시」를 표시한다(F8). 확인 댓글을 검출하는 패턴은 어댑터가 정한다.

**조기 종료:** 계약이 미완이거나 기준선이 없으면(빈칸·자리표시자·칸 없음이고 diff에 기준선 후보 문서도 없음) 정책대로 리뷰를 시작하지 않는다. 리포트는 판정 초안(기준선 없음 → `RETURN_TO_DESIGN`, 증거 부족 → `HOLD_EVIDENCE`)과 **작성자에게 보낼 보완 요청 문안**만 담고 끝난다. 기준선 후보 문서가 있으면 §5.3 이후를 진행하되, §5.4의 검토자가 후보 문서가 이번 변경과 무관하다고 판정하면 그 시점에 기준선 없음으로 되돌려 `RETURN_TO_DESIGN` 초안으로 끝난다. 「첨부 누락」은 보완 요청 문안을 만들고 계속 진행한다. 사용자가 `--full`을 주면 조기 종료 없이 끝까지 간다(판정은 그대로 계산한다).

### 5.2b 배포본 zip 대조 — 모델 없이(사용자 결정 2026-10-21)

운영 배포 대상이면 먼저 **기대 목록**을 계산한다: base..head를 `--no-renames`로 본 추가·수정 파일과 삭제 파일을 각각 어댑터 4.7의 대상·제외 규칙으로 걸러 두 목록(배포 목록·삭제 목록)을 만든다. 정책 §6.1이 zip을 만드는 기준과 같은 규칙이어야 한다 — 전체 diff와 비교하면 spec을 함께 고친 정상 MR이 불일치로 떨어진다. 그 다음 **zip 유무와 관계없이** 대조한다. ① zip 안의 커밋 SHA 주석 = 리뷰 head, ② zip 파일 목록 = 배포 목록, ③ 각 파일 바이트 = 워크트리 `git show <head>:<경로>`, ④ MR 본문의 삭제 목록 = 삭제 목록(삭제 목록이 비어 있지 않은데 본문에 목록이 없거나 다르면 불일치 — 「배포본: 삭제만」 표기만으로 통과시키지 않는다). 배포 목록이 비어 있고 삭제 목록만 있으면 zip 없이 ④만 본다. 결과는 `일치 / 불일치(항목·파일 목록) / 대조 불가(다운로드 실패·zip 손상)`. 불일치·대조 불가·zip 누락은 `MISSING_EVIDENCE`로 「검증 상태」에 적고 보완 요청 문안을 만든다(fail-closed). 내려받은 zip은 scratchpad에만 두고 끝나면 지운다(F7). 업로드 파일 다운로드가 API로 안 되는 환경이면 「대조 불가」로 처리하고 멈추지 않는다.

### 5.3 컨텍스트 팩

1. 어댑터 4.4로 변경 파일 → 읽을 공통 문서 목록. 4.2의 항상 읽을 절 포함.
2. 어댑터 4.5로 위키 검색: 용어집에서 변경 영역의 용어 → 슬러그 → 페이지; 변경 파일명·기능명·테이블명으로 본문 grep. 페이지 전체가 아니라 관련 절만 발췌(결정의 「이유」, 「이후 변경」, 함정·교훈 절 우선). 발췌 상한은 어댑터가 정한다.
3. **팩 A**(Claude용) = 전부. **팩 B**(Codex용) = 팩 A에서 어댑터 4.6 허용 목록에 없는 출처를 뺀 것. 뺀 출처는 리포트에 「Codex 미제공」으로 적는다.
4. 팩 B와 MR 본문·댓글에 어댑터 4.6이 정한 **개인정보 패턴 마스킹**(전화번호·주민번호 등)을 적용한다. 가려야 할 패턴이 남아 있다고 판단되거나 마스킹이 실패하면 Codex를 건너뛰고 **단일 모델 모드**로 간다(이 설계의 결정 — 외부 전송 범위를 넓히는 쪽으로 실패하지 않는다). **Codex 입력의 전체 범위**는 ① 이 프롬프트 파일(마스킹된 팩 B·MR 본문·댓글·렌즈) ② Codex가 cwd에서 직접 읽는 대상 저장소 워크트리(D4 — 마스킹하지 않는다, 저장소 밖은 못 읽는다)다. 워크트리는 대상 저장소의 체크아웃이어야 하며 위키·메모리·다른 저장소를 그 안에 두지 않는다.
5. 팩에 들어간 출처(경로@커밋 또는 위키 페이지명)를 리포트 부록 B에 기록한다.

### 5.4 독립 병렬 검토

두 검토자는 서로의 존재와 결과를 모른다(오류 비상관화). 입력은 같은 구조다: Review Contract · base..head diff · 변경 파일 전문(워크트리) · MR 본문·댓글 · 팩 · 렌즈 질문 · 출력 스키마.

- **Claude 검토자**: Agent 도구로 새 컨텍스트의 서브에이전트. 팩 A. 워크트리를 직접 읽는다.
- **Codex 검토자**: companion `task --prompt-file`, cwd = 워크트리, read-only. 팩 B는 프롬프트 파일 본문에 넣는다. 실행·회수는 review-loop §2b 절차. 실행 실패·스키마 불일치면 자동 재실행하지 않고 단일 모델 모드로 떨어지며 원문을 보고한다.

출력 스키마(둘 다 같다): 발견마다 `렌즈 ID · 발견 유형(정책 4종) · 파일:줄 · 근거 문서(팩 출처 또는 코드 경로) · 실패 시나리오(DEFECT·DESIGN_DRIFT면 필수) · 확신(high/medium/low) · 권고 · 현 설계 안에서 수정 가능한가(yes/no + no면 어떤 전제가 깨졌는지)`. 마지막 항목이 `no`인 차단 발견은 §5.5-4에서 `RETURN_TO_DESIGN` 판정의 입력이 된다. 그리고 의도 대조표 입력: MR 검증 표의 행마다 `PASS/FAIL/UNKNOWN` + 코드 위치 + 「작성자 주장」인지 「코드로 확인」인지.

단일 모델 모드면 Claude만 돈다. Codex가 있는데 Claude 서브에이전트가 실패하면 그 반대 — 어느 쪽이든 결과 헤더에 「교차 검토 없음(돈 모델: X)」.

### 5.5 통합과 판정

메인 세션이 한다. 두 검토자의 결과를 보고 코드를 다시 읽을 수 있다.

1. 지문(파일 + 정규화 제목)으로 같은 발견을 합친다. 출처를 `양쪽 / Claude만 / Codex만`으로 표시한다.
2. **상충**(한쪽은 차단 발견, 다른 쪽은 같은 자리를 무해로 봄)과 **한쪽만 잡은 낮은 확신의 차단 후보**는 메인이 코드로 확인해 판정한다. 확인이 안 되면 리포트 「리뷰어 확인 필요」 절에 두 주장을 나란히 두되, **판정 입력에서 빼지 않는다** — 미해결 차단 후보가 하나라도 있으면 4의 계산에서 `APPROVE`가 나올 수 없다. 정책 판정은 4종뿐이므로(D9) 다섯 번째 값을 만들지 않는다: 이 상태에서는 **게시용 판정 블록(§5.7-2)을 생성하지 않고**, 헤더에 `판정 미확정 — 리뷰어 확인 필요 n건`을 적고 「리뷰어 확인 필요」 절에 각 후보를 확인했을 때·기각했을 때 각각 어느 판정이 되는지 두 갈래로 적는다. 리뷰어가 후보를 확인·기각한 결과를 `--resolve <후보 ID>=<confirmed|dismissed> …`로 주면 그때 판정을 계산해 블록을 만든다(기각 근거는 리포트에 남긴다).
3. 발견 유형 매핑은 어댑터 4.3을 따른다. 특히 **최소 범위 렌즈**는 기본 `FOLLOW_UP`이고, 어댑터가 정한 접촉 표면(공유 DB·인증·외부 연동 등)을 추가로 건드릴 때만 `DESIGN_DRIFT`다 — 정책에 「과잉 구현」 발견 유형이 없어서 둔 규칙이다(이 설계의 결정).
4. 판정은 정책 순서로 계산한다: 기준선 없음 **또는 차단 발견 중 「현 설계 안에서 안전하게 수정 불가」(보안 경계 훼손·데이터 손상 가능·승인 전제 붕괴 — 정책 §5.2·§5.3)로 표시된 것이 있음** → `RETURN_TO_DESIGN` / 그 밖의 차단 발견 → `CHANGES_REQUESTED` / 필수 증거 부족(복원 못 한 diff·배포본 불일치 포함) → `HOLD_EVIDENCE` / 그 외 → `APPROVE`(추천 초안). 여러 문제가 겹치면 가장 앞 단계. 미해결 차단 후보가 있으면 계산 자체를 미루고 판정 미확정으로 둔다(2).
5. 검증 상태는 전부 `[판독]`. 작성자가 적은 실행 결과는 「다른 주체가 제공한 증거」로 표시한다. 배포본 대조(§5.2b)만 스킬이 직접 수행한 결과로 적는다.

### 5.6 재리뷰

이전 판정 댓글의 head ≠ 현재 head면: delta(이전 head..현재 head)를 먼저 보고, 이전 차단 발견마다 작성자 토큰과 대조해 `해소 / 미해소 / 재발` 표를 만든다. 그 다음 영향받은 기준·경로를 현재 전체 head에서 다시 보고, 판정은 현재 head에 귀속한다. target이 바뀌었거나 충돌 해결 커밋이 있으면 범위를 넓힌다. 이전 리포트 파일이 있으면 함께 읽는다.

### 5.7 출력

리포트 파일 하나(어댑터 4.8 경로, `<프로젝트>-<iid>-<head 7자>.md`) + 터미널 요약 10줄 이내.

리포트 구성(순서 고정):

1. 헤더: 리뷰 모드(전체/diff-only/재리뷰), 돈 모델, 교차 검토 여부, 리뷰한 head·base SHA, 어댑터 버전, 정책 버전(MR 계약 버전 / 판정 기준 버전), 기준선 미확인 표시(있을 때), 판정 미확정 표시(§5.5-2 — 있을 때).
2. **판정 초안 — 정책 실행 블록 그대로**(복사해 게시 가능). 첫 줄 형식·5개 절·40줄 규칙 준수. 판정 미확정 상태에서는 이 절을 비우고 「리뷰어 확인 후 `--resolve`로 생성」 한 줄만 둔다.
3. 리뷰어가 먼저 게시할 기준선 확인 문안(경량 MR에 확인 댓글이 없을 때).
4. 작성자 보완 요청 문안(있을 때).
5. 리뷰어 확인 필요(상충·낮은 확신).
6. 부록 A 작성 규칙 검사표·배포본 대조 결과 · 부록 B 근거 출처(Codex 미제공 표시 포함) · 부록 C 모델별 원본 발견(합치기 전).

**산출물 전체의 비밀값 제거(F5):** 리포트 본문·부록 C(모델별 원본 발견)·보완 요청 문안은 쓰기 전에 어댑터 4.6의 비밀값·개인정보 패턴으로 가린다(검토자가 L5에서 인용한 하드코딩 비밀값은 `[masked:secret] <파일:줄>`로만 남긴다). Codex 실행의 원시 로그(review-loop §2b 방식의 `.out` 파일)와 프롬프트 파일은 결과를 추출한 뒤 **지운다** — 보존하지 않는다. 실행 실패로 원문 보고가 필요할 때도 가린 뒤 보고한다. 이 규칙은 정상·실패 경로 모두에 적용된다.

마지막에 워크트리와 내려받은 zip, 원시 로그·프롬프트 파일을 지운다(성공·실패 무관). GitLab에는 아무것도 쓰지 않는다.
