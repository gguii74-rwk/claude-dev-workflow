## 3. 항목별 명세

### 3.ⓑ cleanup 결과의 워크트리 표기

**현상**: `cleanup` 첫 줄 `CLEANED worktree=<true|false> zip=… raw=… masked=… extra=…`. `false` 는 세 경우에 똑같이 나온다 — diff-only(워크트리가 원래 없음) · 사용자가 미리 지움 · 같은 `W` 에 cleanup 재실행. 읽는 쪽(메인 세션·사람)은 「지우기 실패」와 구분하지 못한다.

**원인**(조회 사실 `report.mjs:628-635`·`:808`): `worktree` 는 호출 시점에 워크트리 디렉터리가 **있어서 지웠으면** `true`, 없었으면 `false` 인 불리언이고 그대로 출력된다. 삭제가 실패하면 예외로 끝나므로(`fs.rmSync` 가 던진다) `false` 가 「실패」인 경우는 없다 — 표기가 그 사실을 말해 주지 않을 뿐이다.

**수정**
1. 값을 두 낱말로 바꾼다: **`worktree=removed`**(이 호출이 워크트리 디렉터리를 지웠다) · **`worktree=absent`**(지울 워크트리 디렉터리가 없었다 — diff-only · 이미 지워짐 · 재실행). 세 번째 낱말은 두지 않는다(D155 — diff-only 도 `absent`).
2. **지우는 경로 = 항상 `<W>/worktree`**(D152). 현행은 `snapshot.json` 의 `worktree` 값을 그대로 믿고 그 경로를 지운다(조회 사실 `report.mjs:629` — `snapshot.worktree || path.join(work, 'worktree')`). 수집은 항상 `<W>/worktree` 에만 워크트리를 만들므로(조회 사실 `collect.mjs:96`) 정상 동작은 같고, 기록 파일의 값이 다른 곳을 가리킬 때(예: `W` 를 같은 머신의 다른 위치로 복사한 사본에서 cleanup — 사본의 `snapshot.json` 은 원본 경로를 가리킨다) 작업 디렉터리 밖을 지우지 않게 된다. `snapshot.worktree` 값은 지우기에 쓰지 않는다 — 달라도 오류로 알리지 않고 무시한다. `removed|absent` 판정도 `<W>/worktree` 의 존재 여부로 한다(판정 방식은 현행 `fs.existsSync` 그대로).
   - **경로는 호출 시점에 절대 경로로 한 번 계산해(`path.resolve(work, 'worktree')`) 존재 확인·`git worktree remove` 인자·`fs.rmSync` 세 곳에 같은 값을 쓴다**(review-loop(spec) R1-1). CLI 는 `--work` 를 절대화하지 않으므로(조회 사실 `mr-review.mjs:44`) `path.join` 을 그대로 쓰면 상대 `--work`(예: `--work .`)에서 git 에 `worktree` 같은 상대 인자가 가는데, `git worktree remove` 는 인자를 등록 워크트리 경로의 **끝부분 일치**로도 찾는다 — 사본 `W` 에서 정리하면 원본만 등록돼 있을 때 원본 워크트리를 커밋 안 한 파일째 지운다(현행은 `snapshot.worktree` 의 절대 경로를 써서 이 길이 없다 — D152 가 새로 여는 회귀를 막는다).
3. 그 밖의 동작은 불변: 워크트리 등록 해제(`git -C <snapshot.checkout> worktree remove --force <W>/worktree`)와 `prune` 은 지금처럼 디렉터리가 **있어서 지울 때만** 돈다 — `absent` 일 때 `prune` 을 새로 돌리지 않는다(D154: 사람이 디렉터리만 지우면 체크아웃에 등록이 남지만 해가 없고 다음 `collect` 가 치운다 — 조회 사실 `collect.mjs:101`). 워크트리 삭제가 실패하면 지금처럼 그 자리에서 예외(`ERR`)로 끝난다(D156 — §6 수용된 한계).
4. `cleanup()` 반환 객체의 `worktree` 칸도 같은 문자열(`'removed'|'absent'`)로 바꾼다(조회 사실: 호출자 = `cmdCleanup` 과 테스트뿐 — `report.mjs:806` · `tests/mr-review/report.test.mjs`).
5. 첫 줄의 나머지 칸(`zip=`·`raw=`·`masked=`·`extra=`)·둘째 줄(`extra: …`)·`ERR` 경로 — 불변.
6. SKILL.md §8 의 `CLEANED worktree=<b> …` 문구를 `worktree=<removed|absent>` 로 바꾸고 한 구절을 붙인다: 「`absent` = 지울 워크트리가 없었다(diff-only · 이미 지워짐) — 실패가 아니다」.

### 3.ⓔ `merge` 패스 3 — 넓은 발견이 다른 사안을 삼킴

**현상**: 두 검토자의 발견이 「같은 `file` + `intentRows` 가 **하나라도** 겹침」이면 패스 3 이 합친다. 검증 표 행을 여러 개 건 넓은 발견은 같은 파일의 거의 모든 발견과 겹친다 → 서로 다른 사안이 한 발견(`source: both` · `joinedBy: intentRows`)이 되고, 단독 출처였다면 받았을 `needsMain`(「단독 출처 낮은 확신 차단」·「단독 출처 설계 내 수정 가능 판단」)이 생기지 않는다. 잘못 합친 것은 첫 줄 수치(`joined=`)에만 묻어 있어 메인이 놓치기 쉽다. 반대로 합치지 **않은** 같은 파일 쌍은 `candidates`(D138)로 보인다 — 덜 합치는 쪽은 눈에 보이고 잘못 합치는 쪽은 보이지 않는다.

**원인**(조회 사실 `merge.mjs:74-86`): 패스 3 조건 = `inter(c.rws, x.rws).length > 0 && c.f.file != null && c.f.file === x.f.file`. 교집합 크기만 보고 두 묶음이 얼마나 다른지는 보지 않는다. 패스 안은 claude 배열 순 → 아직 짝 없는 codex 첫 것(greedy)이라, 넓은 발견이 앞에 있으면 먼저 가져간다.

**수정**(D150 — **D137 의 패스 3 조건 변경** · D157 후보 표시)
1. 패스 3 조건 = 두 발견의 `intentRows` 묶음이 **비어 있지 않고 서로 같다**(원소 집합 동치 — 순서·중복 무관) **그리고** `file` 이 같다(둘 다 `null` 아님). 비교하는 묶음은 현행과 같은 값이다 — `--rows n` 이 있으면 1~n 밖 번호를 걸러 내고 중복을 없앤 뒤(`rws`). `--rows` 가 없으면 걸러 내지 않은 값 그대로(현행).
2. 그 밖은 전부 불변: 패스 순서(0 `--same` → 1 지문 → 2 `decisionIds` → 3) · 패스 안 순서(claude 배열 순 → 짝 없는 codex 첫 것) · 1:1(D136) · 한 번 짝 지은 발견은 다음 패스에서 다시 쓰지 않음 · `joinedBy` 의 값 이름 `intentRows`(값 집합 불변 — SC-5 스키마·`validateFindings`·부록 D 불변).

**수용된 한계**

- 행 묶음이 같고 파일도 같은 **다른 사안**은 여전히 패스 3 이 합친다(D150·D138 수준 — 검증 표 행 하나에 여러 발견이 걸릴 수 있다).
- 잘못 합쳐진 짝을 **푸는** 수단은 없다(D158) — `--same` 으로 다른 짝에 다시 배정할 수 있을 뿐이고, 양쪽 다 맞는 짝이 없으면 합쳐진 채 남는다(패스 2 `decisionIds` 로 합쳐진 「같은 결정 · 다른 위치」 발견이 그 예). 실제로 막힌 사례는 0 — 사례가 나오면 다음 트랙에서 다룬다.
