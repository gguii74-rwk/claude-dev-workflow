## 3. 설계 (D1~D21 확정 — harden-spec 2026-08-09 · **D22~D25** = spec 루프 사용자 판정 2026-08-09)

### C-9. doctor 신설

**성질** — 진단 전용. **사용자 작업물·설정을 쓰지 않는다**(D9). 이름은 codex CLI의 `codex doctor`와 같은 어휘를 쓴다(사용자가 뜻을 추측할 필요가 없다).

> **D9 — "읽기 전용"의 정확한 범위.** 점검 2의 `git fetch`는 엄밀히 `.git` 객체를 갱신하므로 "파일을 쓰지 않는다"는 초안 문면과 어긋났다. 실제 경계는 **사용자 작업물·설정(repo 파일·CLAUDE.md·settings.json·설치본)을 쓰지 않는다**이며, 마켓플레이스 clone의 `fetch`는 **진단에 필수인 조회 행위로 예외 명시**한다. `fetch`는 상위 clone의 작업 트리를 바꾸지 않고 원격 추적 단서만 갱신하므로 실질 위험이 없다. fetch 없이 현 clone 상태로 판정하면 상시 "판정 불가"가 나온다 — 실측에서 로컬 clone HEAD(`a117486`)가 origin/main(`3267b82`)보다 뒤처져 있었다.

`SKILL.md` frontmatter에 **`model`·`effort` 오버라이드를 두지 않는다**(D21) — 명시된 프로브를 돌려 표로 정리하는 낮은 난이도 작업이라 harden-spec 같은 모델 고정의 근거(놓친 갭 하나가 재설계를 부름)가 없고, 고정하면 가벼운 진단에 비싼 모델을 강제하게 된다.

**설정 루트는 한 번 결정해 전 프로브가 공유한다.** 모든 조회(`installed_plugins.json` · 마켓플레이스 clone · plugin cache · 글로벌 `settings.json`)의 기준은 **`${CLAUDE_CONFIG_DIR:-$HOME/.claude}`**다. setup이 이미 글로벌 settings 위치로 이 변수를 인정하고 있고(`setup/SKILL.md:32`), 값을 바꾸면 레지스트리 자체가 다른 프로필로 전환된다. `~/.claude`를 하드코딩하면 **활성 프로필이 아닌 다른 프로필을 진단해 "최신"·"미등록"을 틀리게 보고**한다 — 스코프 하드코딩과 같은 계열의 조용한 오진이다.

**판정 규칙 5건**

- **(a) 버전 뒤처짐은 `dev-workflow/` 경로 한정으로 판정한다**(D5). 설치 sha와 `origin/main`의 **`dev-workflow/` 내용이 같은지**만 본다.
  - **판정은 커밋 이력이 아니라 트리로 한다.** 1차 판정 = 양쪽 sha의 `dev-workflow/` **subtree object id 비교**(`git rev-parse <sha>:dev-workflow`). 같으면 내용이 동일하므로 **뒤처짐 없음/드리프트 없음**이다. 다를 때만 `git log … -- dev-workflow/`를 **무엇이 달라졌는지 보여주는 보조 근거**로 붙인다. object·경로 조회가 실패하면 (b)에 따라 **"판정 불가"**다.
  - **왜 로그로는 안 되나.** `git log A..B -- <path>`는 *그 경로를 건드린 커밋을 세는 것*이지 최종 트리를 비교하지 않는다. 변경 후 되돌린 이력이 있거나 서로 다른 커밋이 같은 내용을 만들면 **트리는 같은데 로그는 남아** 거짓 뒤처짐·거짓 드리프트가 된다 — (a)가 없애려던 늑대소년을 한 겹 아래에서 재생산하는 것이다.
  - **근거(실측 2026-08-09).** user-scope 설치본 `a117486` vs `origin/main` `3267b82` 사이에 `dev-workflow/` 변경이 **0건**이다 — sha는 다른데 플러그인 내용은 동일하다. 이 repo는 docs/specs 커밋이 압도적이라 **단순 sha 비교는 커밋할 때마다 거짓 경보**한다. 늑대소년이 되면 진짜 뒤처짐도 무시된다 — doctor가 없애려던 실패 양상을 반대 방향으로 재생산하는 것이다.
  - 이 방식은 §1이 지적한 **"버전 문자열은 같은데 내용은 낡음"**(범프 없는 스킬 문면 변경)도 그대로 잡는다. version 문자열은 표시용이지 판정 근거가 아니다.
  - 현 상태 판정: user-scope = **최신**(sha 상이하나 경로 변경 0건), project-scope `d57bfe9`(0.11.0) = **뒤처짐 3건**.
  - **스코프 간 드리프트도 같은 방식으로 판정한다.** 설치 sha들을 raw로 비교하지 않고 **각 sha의 `dev-workflow/` subtree object id가 모두 같은지**만 본다. 이 규칙이 없으면 (a)가 origin 비교에서 막은 오탐이 **스코프 상호 비교로 그대로 새어 들어온다** — 이 repo는 docs/specs 커밋이 압도적이라 두 스코프가 같은 내용으로 갱신돼도 raw sha 비교는 영구히 드리프트를 보고한다(반례: `d23f2bb`·`a117486`·`3267b82`는 sha가 다르지만 `dev-workflow/` 트리가 같다). 어느 한쪽 sha가 결측이거나 조회가 실패하면 (b)에 따라 **"판정 불가"**다.
  - **스코프 목록을 하드코딩하지 않는다.** 설치 스코프는 `user`·`project`·`local` 3종이고(`claude plugin install -s <scope>`), `installed_plugins.json`의 엔트리는 `scope`와 (project·local이면) `projectPath`를 가진 **배열**이다. 두 종만 열거하면 **stale한 local 설치가 활성인 repo에서 doctor가 그 설치를 보지 못한 채 "최신"이라 보고한다** — 조용히 틀리는 바로 그 실패다. 그래서 배열 전체를 열거하고 스코프 이름은 **출력에 그대로 옮긴다**(새 스코프가 생겨도 자동으로 덮인다).
- **(b) 근거가 없으면 "판정 불가"로 표시하고 절대 "최신"이라 말하지 않는다.** 네트워크 실패뿐 아니라 **`gitCommitSha`·`version` 필드 결측**에도 같은 규칙을 적용한다(**D11** — D6의 확장).
  - **근거(실측).** `installed_plugins.json`에 `gitCommitSha`가 아예 없는 엔트리가 **5건**(claude-md-management · security-guidance · ralph-loop · kotlin-lsp · swift-lsp), `version: "unknown"`이 **3건** 있다. dev-workflow 자신은 현재 둘 다 있지만 구조적으로 보장되지 않는다. version 문자열로 폴백하면 (a)가 막은 "버전 같은데 내용 다름"이 다시 새어 들어온다.
- **(c) 마켓플레이스 clone 부재는 "미등록"으로 별도 표시한다**(D19). 네트워크 실패와 **원인도 조치도 다르다** — 전자는 기다림, 후자는 `/plugin marketplace add gguii74-rwk/claude-dev-workflow` → `/plugin install`이다(setup 마커 블록의 기존 문구 재사용). 브리프 `:149`의 "그램 최초 install 백로그 잔존"이 정확히 이 케이스다.
- **(d) `CLAUDE_CTX_LIMIT`은 실제 환경변수 값을 먼저 본다**(D10). 훅이 실제로 읽는 것은 `env.CLAUDE_CTX_LIMIT` — **프로세스 환경변수**다(`context-threshold-hook.mjs:45`). 셸 프로필 등 다른 경로로 주입되면 settings.json grep만으로는 "미설정" 오탐이 난다. settings.json 3곳은 **"어디서 왔는가 / 어디에 넣으면 되는가"**를 밝혀 조치 안내를 붙이는 용도로 병행 조회한다.
- **(e) 모델 대조는 doctor만 할 수 있고, 불일치는 양방향으로 판정한다.** 훅은 런타임에 윈도를 모르지만 **스킬은 Claude 자신이 자기 모델을 안다.** 훅이 구조적으로 못 하는 검사를 메우는 것이며, setup과 중복이 아니다 — setup은 값을 **묻고 쓰는** 쪽, doctor는 **현재 모델과 맞는지 판정하는** 쪽이다.
  - **양방향인 이유(실측).** 훅은 설정된 양수 값을 **검증 없이 그대로** 쓴다(`context-threshold-hook.mjs:52` — `Number.isFinite(envLimit) && envLimit > 0 ? envLimit : DEFAULT_LIMIT`). 그래서 **1M 모델에 200k가 설정된 역방향**도 실패한다: 실제 8% 사용 시점을 40%로 계산해 멀쩡한 작업에 조기 넛지가 뜬다. 훅 자신이 그 방향을 *"과대평가가 더 해롭다 — 1M 세션에 200k를 가정하면 실제 8% 사용 시점에 40% 임계로 오판해 멀쩡한 작업을 조기 종료시킨다"*(`:50~51`)고 적어 뒀다. 한 방향만 규정한 진단은 **훅이 스스로 더 해롭다고 적은 쪽을 못 잡는다.**

**버전 대조 범위 = dev-workflow 하나뿐이다**(D12). codex는 점검 3의 **존재·인증만** 보고 플러그인 버전은 대조하지 않는다 — 비목표 "다른 머신 진단 안 함"과 같은 결의 범위 제한이며, 상류 마켓플레이스(`openai/codex-plugin-cc`) fetch를 추가하지 않아 산출물을 `SKILL.md` 1개로 유지한다.

**출력** — **정상이든 아니든 4항목 표를 항상 출력**하고(D16), 조치 안내만 이상 항목에 붙인다. 증상 트리거로 뜬 경우 사용자는 이미 문제를 의심하는 중이라 "이상 없음" 한 줄로는 납득되지 않고, 무엇을 봤는지 안 보이면 결국 수동 대조로 되돌아간다 — 그것이 doctor가 없애려던 바로 그 행동이다. 표 4줄은 짧다.

**부분 실패에도 중단하지 않는다.** 한 프로브가 실패해도(fetch 실패 · 객체 조회 실패 · 파일·clone 부재 · codex 명령 실패) **나머지 프로브를 계속 수행하고 표 4행을 반드시 출력**한다. 실패한 항목만 정의된 상태("판정 불가" · "미등록" · "미설치")로 표기하고 그 항목에 조치 안내를 붙인다. 중단하면 D16이 무의미해진다 — **환경이 가장 망가진 순간에 사용자가 아무 정보도 못 얻는 것**이 doctor의 존재 이유와 정면으로 어긋난다.

**오발동 경계 4종** (문면에 명시)

| 잠식 위험 | 경계 |
|---|---|
| review-loop | **루프 실행 중의 codex 실패는 review-loop 소관.** doctor가 끼면 루프가 끊긴다. doctor는 **루프 밖**의 증상 문장에만 |

**D14 — 증상 어휘의 경계선** (**D22로 정정 — 2026-08-09 사용자 결정**). description에는 **dev-workflow 파이프라인 환경 요소(넛지 · codex 연동 · 플러그인 버전)를 가리키는 증상 문장만** 올린다 — "넛지가 안 떠" · "codex가 안 돌아" · "플러그인 최신인가" · "버전 맞나". **문면에 명시적으로 제외**를 적을 대상은 둘이다: ① 도구 이름·현상에 묶이지 않은 일반 실패 문장("왜 안 돼", "에러 났어", "환경이 꾸직해") ② **다른 제품·도구를 주어로 한 같은 어휘**("playwright 플러그인 최신인가", "node 버전 맞나", "codex로 딴 작업 돌리는데 안 돌아").

> **왜 규칙 문면을 넓혔나(D22).** 초안 문면은 *"주어가 dev-workflow 고유 명사인 문장만"*이었는데 예시 4종 중 3종에는 제품 귀속이 없다 — 규칙과 예시가 어긋난 채로는 구현자가 어느 쪽을 따를지 갈린다. 예시를 규칙에 맞춰 좁히는 길(모두 "dev-workflow …"로 시작)은 **사용자가 실제로 그렇게 말하지 않아** 증상 트리거의 값어치를 없애고 D1의 2경로를 명시 호출 하나로 수렴시킨다. 그래서 **규칙을 실제 의도(파이프라인 환경 요소)에 맞춰 정정하고, 넓어진 만큼 잠식은 제외 ②와 음성 arm 실측으로 받는다.** 경계를 문면에 두는 이유는 측정 때문이다 — §5의 오발동 음성 arm이 측정할 대상이 문면에 없으면 측정 자체가 성립하지 않는다. 넓히면 발견성은 오르지만 상위 스킬·일반 디버깅과 겹쳐 잠식이 커지고, 이는 spec이 "오발동은 이 스킬의 주된 위험"으로 본 판단과 정면으로 어긋난다.

**dev-cycle 본문에는 doctor 상호참조를 넣지 않는다**(D20). 발동 경로를 **명시 호출 + 증상 트리거** 둘로 한정한 것이 기결정(D1)이며, dev-cycle 경유는 제3 경로 신설이라 기결정 확장이다. 세 스킬 경계표(파이프라인 vs 환경)의 선명함도 유지되고, §5 fp-I3 회귀 arm이 같은 파일을 측정 중이라 arm 정의가 흐려지지 않는다. 상호참조는 AC 5의 README 트러블슈팅으로 충족한다.

### C-6 D11. setup 마커 문구

현재 템플릿은 *"새 기능·**큰 변경**을 시작하면"* 이라 경량 트랙을 배제하는 것처럼 읽힌다. dev-cycle description은 이미 "작은 단일 단계 변경도 경로 판정이 필요하면"을 담고 있어 **둘이 어긋나 있다.** 마커 문구를 dev-cycle 트리거에 맞춰 정합시킨다.

**파생 문제 — 기존 삽입분 드리프트 (D13으로 해소).** 마커는 이미 여러 repo의 CLAUDE.md에 삽입돼 있고, setup은 멱등 교체라 **다시 돌려야** 갱신된다.

**D13 — 9단계 종료 보고에 안내 한 줄로 닫는다.** 릴리스 안내에 *"마커가 삽입된 repo는 `/dev-workflow:setup` 재실행으로 문구를 갱신한다"*를 넣는다. 기계 장치를 만들지 않으므로 G1·G2(과설계 금지)와 정합하고, 마커는 dev-cycle로 가는 **포인터**라 문구가 낡아도 기능 자체는 깨지지 않는다 — 드리프트의 실제 손해가 "경량 트랙 배제처럼 읽힘"에 국한되므로 안내로 충분하다. doctor의 5번째 점검 항목으로 넣는 안은 기각했다: 환경 진단이 아니라 repo 콘텐츠 검사라 doctor의 성질과 결이 다르다.

### fp-I3. dev-cycle description — 조건부 결정

`(design → spec → harden → review → plan → review → implement → review → integrate)` 괄호가 G-c(description은 트리거만)를 위반할 소지다. 다만 C-6 ledger가 *"W1이 5/5 선택으로 발견성 목적은 이미 달성"* 이라 기록해 뒀다 — **제거하면 발견성이 떨어질 수 있고 그게 유일한 쟁점**이다.

**결정: 제거를 시도하고 발견성 TDD로 판단한다.** 5/5가 유지되면 제거 확정, 떨어지면 **유지하고 D번호로 예외를 기록**한다. 실측에 달린 항목을 미리 못 박지 않는다.

> **D26 — 제거 확정 (2026-08-10 TDD 결과).** `new` 5/5 유지로 D8 조건을 충족했다(`cur` 5/5 · `none` 5/5 — **세 arm이 전부 같다**). 근거 인용은 15런 전부 트리거 예 *"작은 변경인데 어떤 절차로 가야 해"*였고 **괄호 요약을 근거로 든 rep은 0건**이다. 정직하게 적으면 요약의 행동 기여도 0, 제거의 행동 기여도 0이다 — 제거를 확정하는 근거는 **G-c(description은 트리거만)** 규약이지 행동 변화가 아니며, TDD가 말해 준 것은 *"제거해도 발견성이 안 떨어진다"* 하나다. 전문은 `.remember/tdd-7b-doctor.md`.

- **진단 정확도 = 대조표 전항 일치**(D18). 아래 참조.

**D18 — 진단 정확도 실측을 GREEN 조건에 넣는다.** TDD 4계열은 전부 *"doctor가 뜨는가"*만 측정하고 **프로브가 내린 판정이 맞는지는 아무도 보지 않는다.** 초안 그대로면 틀린 판정을 내는 doctor도 GREEN으로 릴리스된다 — 실제로 D5가 고친 sha 오탐이 초안·brainstorming을 통과해 harden-spec까지 살아온 것이 반례다. 그래서 구현 후 **doctor를 이 머신에서 실제로 돌려** 아래 대조표가 전부 일치하는지 확인하고 결과를 impl ledger에 적는다. D18이 더하는 것은 **수동 실측 2회**(200k 모델 세션 1회 + 1M 모델 세션에서 `CLAUDE_CTX_LIMIT` 주입 1회)뿐이다 — TDD 런 수(D23 기준 90)와는 별개이고, 기계 장치를 만들지 않으므로 경량 경로·G1·G2에 저촉하지 않는다.

| 대조 항목 | 기대 판정 |
|---|---|
| user-scope (`a117486`) | **최신** — sha가 origin/main과 달라도 `dev-workflow/` 변경 0건 |
| project-scope (`d57bfe9`, 0.11.0) | **뒤처짐** — 경로 변경 3건 |
| **스코프 간 드리프트** | 실제 스코프 sha 쌍에 대해 **doctor와 다른 명령**(`git diff --quiet <shaA> <shaB> -- dev-workflow/`의 종료코드)으로 낸 정답과 doctor 판정이 **일치**. doctor가 쓰는 `rev-parse … :dev-workflow`를 oracle로 재사용하지 않는다 |
| `CLAUDE_CTX_LIMIT` 과소평가 방향 — **200k 모델 세션** | **이상** — 미설정이라 기본 1M으로 계산돼 넛지 미발화 |

| codex | **정상** — `Logged in using ChatGPT`(exit 0), companion 존재 |

**오탐 케이스는 자연 발생 여부를 확인한 뒤 기록한다.** 구현이 갈리는 지점은 둘이다 — ① raw sha 비교와 트리 비교가 갈리는 **"sha는 다른데 `dev-workflow/` 트리는 같은 쌍"**, ② 로그 기반과 트리 기반이 갈리는 **"경로를 건드린 커밋은 있는데 최종 트리는 같은 쌍"**(변경 후 되돌린 이력). ①은 V-7b-1 갱신 직후에 성립할 수 있으나 그 시점 origin/main 위치에 달려 있고, ②는 이 repo 이력에 그런 쌍이 있어야 한다. **성립하는 것만 실측하고, 성립하지 않으면 그 사실을 impl ledger에 적고 규칙 문면 확인으로 갈음한다.** 설치본을 조작하거나 픽스처용 커밋을 만들지는 않는다(D9·G1·G2).

**degraded 분기도 정확도 게이트에 넣는다 — 재현 가능한 것만 실측하고 나머지는 갈음한다.** 위 6항은 전부 *정상 상태*라, 이대로면 **fetch가 실패했을 때 진단을 중단해 표를 안 내는 구현도 GREEN**이 된다. doctor가 가장 필요한 순간이 degraded 상태이므로 아래 분기를 게이트에 포함한다.

| degraded 분기 | 정의된 기대 출력 |
|---|---|
| 마켓플레이스 clone 부재 | **"미등록"** + `marketplace add` 안내 (D19) — 일반 "판정 불가"가 아니다 |
| fetch·subtree object 조회 실패 | **"판정 불가"** — "최신"이라 말하지 않는다 (D6·D11) |
| `gitCommitSha`·`version` 필드 결측 | **"판정 불가"** (D11) |
| dev-workflow 미설치(해당 스코프) | **"미설치"** |
| codex CLI 부재 · 미로그인 · companion 부재 | 각각 그 상태로 표기 + 조치 안내 (D15) |

- **조작 없이 재현 가능한 분기만 실측**한다. 나머지는 **문면 확인으로 갈음**하고, **분기별로 어느 쪽으로 처리했는지 impl ledger에 적는다**(fp-S6·fp-S7에서 쓴 것과 같은 갈음 규칙 — 설치본을 망가뜨리거나 픽스처용 커밋을 만들지 않는다: D9·G1·G2).
- 어느 분기든 **부분 실패에도 표 4행이 나오는지**를 함께 확인한다. 이것이 이 분기 검증의 핵심이다.

**local 스코프는 이 머신에 설치본이 없다.** 열거 방식으로 고쳤으므로 코드 경로는 스코프 종류에 의존하지 않지만, local 설치의 실측은 이 머신에서 불가능하다 — **자연 픽스처 부재를 impl ledger에 명시**하고, 열거가 배열 전체를 도는지(스코프 이름 하드코딩이 없는지)를 문면·구현 확인으로 갈음한다.

**CTX_LIMIT 두 방향은 한 세션에서 동시에 성립하지 않는다.** 미설정을 "과소평가 이상"으로 판정하려면 현재 모델이 **200k**여야 하는데, 같은 200k 세션에 `CLAUDE_CTX_LIMIT=200000`을 주입하면 그건 **정상**이다. 반대로 1M 세션에서는 미설정이 정상이고 주입만 이상이다. 그래서 두 행은 **서로 다른 모델 세션**에서 재고(`/model` 전환), **각 실행의 모델을 impl ledger에 함께 적는다.** 한 세션에 몰면 AC 8은 *충족 불가능한 게이트*이거나 *틀린 doctor도 통과시키는 게이트*가 된다. 환경변수는 실행 1회에 앞에 붙이는 것으로 충분해 파일을 쓰지 않으므로 D9 범위를 유지한다. 판정 규칙 (e)를 양방향으로 고쳤으니 검증도 양방향이어야 한다 — 새 규칙에 D18의 취지(*"프로브가 내린 판정이 맞는지 아무도 보지 않는다"*)가 미치지 않으면 고친 의미가 없다.

**픽스처** — 발견성·오발동 계열은 사용자 발화만 주면 되므로 환경을 망가뜨릴 필요가 없다(7a보다 부담이 작다). 진단 정확도(D18) 쪽은 이 머신이 **이상 상태 2종을 자연 픽스처로 갖고 있다** — ops-hub project-scope 0.11.0 고정 · `CLAUDE_CTX_LIMIT` 미설정(**200k 모델 세션에서 이상이 된다** — 1M 세션에서는 기본값과 일치해 정상이다). 설치본을 조작하지 않고 실측되며, 남는 것은 모델 세션 전환과 환경변수 1회 주입뿐이다.

**예외 — C-6 D11(마커) 계열은 픽스처가 필요하다.** "작은 변경 문장에서 마커를 읽고 dev-cycle로 가는가"를 측정하려면 **개정된 마커 블록이 삽입된 CLAUDE.md**가 arm별로 있어야 한다(`new`=개정 문구, `cur`=현행 "새 기능·큰 변경" 문구). 발화만으로는 측정되지 않으므로 이 15런은 CLAUDE.md 픽스처를 준비한다.

**7a 교훈 승계** — 픽스처는 호출부 연결로 끝내지 말고 **게이트와 base diff까지 실측 통과**시킨다. 같은 계열 결함이 C-5·C-6·7a로 4회 반복됐다.

**프로브 사전 실증(2026-08-09)** — 4종 전부 한두 줄로 동작함을 확인했다: 설치본 스코프별 조회 · 마켓플레이스 fetch + `origin/main:plugin.json` · `codex login status`(→ `Logged in using ChatGPT`, exit 0) · settings.json 3곳 grep.

**8단계 게이트** — 비-npm repo이므로 **writing-skills TDD GREEN 기록으로 갈음**한다(C-6 D7).
