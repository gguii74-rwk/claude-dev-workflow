## 3. 설계 (초안 — D번호 확정은 harden-spec)

### C-9. doctor 신설

**성질** — 읽기 전용, 진단 전용, 파일을 쓰지 않는다. 이름은 codex CLI의 `codex doctor`와 같은 어휘를 쓴다(사용자가 뜻을 추측할 필요가 없다).

**세 스킬의 경계**

| 스킬 | 성질 | 발동 |
|---|---|---|
| `dev-cycle` | 읽기 전용 — **파이프라인** 지도 | 새 기능·다음 단계 질문 |
| **`doctor`** | 읽기 전용 — **환경** 진단 | 명시 호출 + 증상 문장 |
| `setup` | **쓰기** — repo 채택 | 명시 요청 전용 |

**점검 4항목** (프로브는 SKILL.md에 그대로 명시한다 — 매 실행 재조합 금지)

| # | 항목 | 프로브 | 이상 판정 |
|---|---|---|---|
| 1 | 설치본 버전 | `installed_plugins.json`의 **전 스코프**(user + project) | 마켓플레이스보다 뒤처짐 · 미설치 · **스코프 간 드리프트** |
| 2 | 마켓플레이스 최신 | 마켓플레이스 clone `fetch` → `origin/main`의 `plugin.json` | fetch 실패 = **"판정 불가"** |
| 3 | codex | `codex login status` + companion 스크립트 존재 | 미로그인 · CLI 없음 · companion 없음 → 깊은 문제는 `codex doctor`로 위임 |
| 4 | `CLAUDE_CTX_LIMIT` | settings.json 3곳(글로벌·프로젝트·로컬) + **현재 모델 대조** | 200k 모델인데 미설정 또는 1M 설정 = 넛지 미발화 |

**판정 규칙 3건**

- **(a) 버전은 version + sha 둘 다 본다.** 문자열만 보면 "최신인데 낡음"을 놓친다(§1 실측).
- **(b) 네트워크 실패는 "판정 불가"로 표시하고 절대 "최신"이라 말하지 않는다.** 오프라인에서 조용히 통과시키면 doctor가 실패 양상을 재생산한다.
- **(c) 모델 대조는 doctor만 할 수 있다.** 훅은 런타임에 윈도를 모르지만 **스킬은 Claude 자신이 자기 모델을 안다.** 훅이 구조적으로 못 하는 검사를 메우는 것이며, setup과 중복이 아니다 — setup은 값을 **묻고 쓰는** 쪽, doctor는 **현재 모델과 맞는지 판정하는** 쪽이다.

**출력** — 표 1개 + **이상 항목에만** 조치 안내. 전부 정상이면 한 줄로 끝낸다.

**오발동 경계 4종** (문면에 명시)

| 잠식 위험 | 경계 |
|---|---|
| review-loop | **루프 실행 중의 codex 실패는 review-loop 소관.** doctor가 끼면 루프가 끊긴다. doctor는 **루프 밖**의 증상 문장에만 |
| setup | "이 repo에 세팅해줘"는 setup. 쓰기가 필요하면 setup으로 보낸다 |
| dev-cycle | "다음 단계 뭐야"는 dev-cycle. doctor는 환경만 |
| 막연한 실패 문장 | "왜 안 돼?"에 뜨면 안 된다. 증상 어휘를 **dev-workflow 도구 이름·현상에 묶어** 일반 오류와 구분한다 |

### C-6 D11. setup 마커 문구

현재 템플릿은 *"새 기능·**큰 변경**을 시작하면"* 이라 경량 트랙을 배제하는 것처럼 읽힌다. dev-cycle description은 이미 "작은 단일 단계 변경도 경로 판정이 필요하면"을 담고 있어 **둘이 어긋나 있다.** 마커 문구를 dev-cycle 트리거에 맞춰 정합시킨다.

**파생 문제(미해결 Q1)** — 마커는 이미 여러 repo의 CLAUDE.md에 삽입돼 있다. 문구를 바꾸면 기존 삽입분과 드리프트가 생기고, setup은 멱등 교체라 **다시 돌려야** 갱신된다.

### fp-I3. dev-cycle description — 조건부 결정

`(design → spec → harden → review → plan → review → implement → review → integrate)` 괄호가 G-c(description은 트리거만)를 위반할 소지다. 다만 C-6 ledger가 *"W1이 5/5 선택으로 발견성 목적은 이미 달성"* 이라 기록해 뒀다 — **제거하면 발견성이 떨어질 수 있고 그게 유일한 쟁점**이다.

**결정: 제거를 시도하고 발견성 TDD로 판단한다.** 5/5가 유지되면 제거 확정, 떨어지면 **유지하고 D번호로 예외를 기록**한다. 실측에 달린 항목을 미리 못 박지 않는다.

## 5. 검증 계획

**writing-skills TDD** — arm 3종 `new`(개정) / `cur`(현행) / `none`(무지침 대조군). 무지침 대조군은 7a에서 **규정 왜곡 1건**을 실제로 잡아냈으므로 유지한다.

| 계열 | 프롬프트 | arm | 런 |
|---|---|---|---|
| 발견성(양성) | 증상 문장 3종 — "넛지가 안 떠" · "codex가 안 돌아" · "플러그인 최신인가" | new·cur + 2종만 none | 40 |

| fp-I3 회귀 | C-6의 W1 프롬프트 재사용 — 요약 제거 후 5/5 유지되는가 | new·cur | 10 |
| D11 | 작은 변경 문장에서 마커를 읽고 dev-cycle로 가는가 | new·cur | 10 |

**총 80런** — 7a(68런)와 같은 구간이며 C-6이 경고한 243런 구간에 들어가지 않는다. 음성 계열을 `new`만 도는 이유는 **cur에는 doctor가 없어 잠식 자체가 불가능**하기 때문이다.

**판정 기준(잠정 — harden-spec에서 확정)**

- **양성 = 분리 입증.** `new`가 5/5로 doctor를 부르고, `cur`이 그보다 유의하게 낮을 것. 7a의 실측 형식(`cur 0/3 · none 1/2 → new 5/5`)을 따른다. **`cur`도 높게 나오면 개정의 행동 기여가 0**이라는 뜻이며, 그때는 7a의 C-3처럼 "미검출"로 정직하게 기록한다.
- **음성 = 잠식 0.** `new`에서 setup·dev-cycle·review-loop가 떠야 할 문장에 doctor가 뜬 횟수 0/5. **1건이라도 뜨면 GREEN이 아니다** — 오발동은 이 스킬의 주된 위험이라 양성보다 엄격하게 본다.
- **fp-I3 회귀 = 5/5 유지.** 미달이면 제거를 철회하고 유지로 판정한다(§3 조건부 결정).

**픽스처** — 발견성은 사용자 발화만 주면 되므로 환경을 망가뜨릴 필요가 없다(7a보다 부담이 작다). 진단 정확도 쪽은 이 머신이 **이상 상태 2종을 자연 픽스처로 갖고 있다** — ops-hub project-scope 0.11.0 고정 · `CLAUDE_CTX_LIMIT` 미설정. 조작 없이 실측된다.

**7a 교훈 승계** — 픽스처는 호출부 연결로 끝내지 말고 **게이트와 base diff까지 실측 통과**시킨다. 같은 계열 결함이 C-5·C-6·7a로 4회 반복됐다.

**프로브 사전 실증(2026-08-09)** — 4종 전부 한두 줄로 동작함을 확인했다: 설치본 스코프별 조회 · 마켓플레이스 fetch + `origin/main:plugin.json` · `codex login status`(→ `Logged in using ChatGPT`, exit 0) · settings.json 3곳 grep.

**8단계 게이트** — 비-npm repo이므로 **writing-skills TDD GREEN 기록으로 갈음**한다(C-6 D7).

- **Q7.** 정상 케이스의 출력이 **한 줄로 충분한가** — 증상 트리거로 뜬 경우 사용자는 "무엇을 봤는지"를 알고 싶을 수 있다.
