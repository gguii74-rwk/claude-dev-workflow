## 1. 문제 (실측 · 공식 근거)

사용자 판정(2026-11-15)의 방향은 「진행 상황은 바로바로 파일에 기록 · 단계와 단계 사이는 새 세션 · 한 단계 안은 자동 압축으로 관리」다. 단계 안을 자동 압축(대화가 길어지면 Claude Code가 앞부분을 요약으로 바꾸는 동작)에 맡기려면 **압축을 넘겨도 진행 상태와 절차가 남아야** 하는데, 지금은 두 군데가 비어 있다.

1. **review-loop의 진행 상태가 대화 안에만 있다.** 적대/확인 소진 카운터 · 현재 모드 · 복귀 사용 여부 · 실행 예산은 §2i 일시중단(넛지 · 사용자 중단 · 폴백②) 때만 루프 파일(`.remember/loop-<ledger basename>-<phase>.md`)에 적힌다. 라운드 도중 압축되면 이 값들은 요약문에만 의존한다(finding·판정·미확인 FIXED 큐·batch 적재는 ledger 문서에 이미 있다 — 빈 곳은 카운터·모드·진행 위치다).
2. **압축 뒤 스킬 본문이 잘린다.** 공식 문서: 호출했던 스킬 본문은 압축 뒤 「스킬당 5,000토큰 · 합계 25,000토큰」까지만, **파일 앞부분부터** 다시 붙는다(§6a F5). review-loop SKILL.md는 83,005바이트(45,047자 — 문자 수 기반 추정 18,000~26,000토큰)라 5,000토큰은 대략 100~120행까지다. **§절차(240행 이하 — §0 재개 · §2 라운드 · §2i 일시중단 · §2j 카운터 · §4 종결) 전부가 잘린다.** 같은 추정으로 mr-review(14,000~19,000) · doctor(8,600~11,800)도 잘리고, orchestrate · harden-spec · dev-cycle · ui-mockup은 3,300~6,000으로 경계에 걸친다.
3. **압축은 넛지와 무관하게 지금도 일어난다.** 실례 1건(2026-11-12 — 55분 쉰 뒤 325K → 18K). 공식 문서의 유휴 압축(약 200K 넘는 대화가 쉬면 압축 — §6a F6)과 일치한다. 넛지(기본 40% = 400K)는 이 경로를 막지 못한다.

**실측에 없는 것(L5 — 그대로 적는다)**: 압축 때문에 review-loop가 실제로 잘못 이어진 사례는 관측되지 않았다(맥북 이 저장소 5턴 이상 48세션 중 넛지 6건 · 자동 압축 실례 1건 — 그 세션의 뒤 동작은 조사하지 않았다). 이 트랙의 근거는 실패 사례가 아니라 **문서로 확정된 플랫폼 동작(본문 절단 · 유휴 압축)과, 사용자가 정한 다음 단계(넛지만 끄고 실제 트랙 시험)의 전제 조건**이다 — 보완 없이 넛지를 끄면 시험이 「압축을 견디는가」가 아니라 「상태를 잃는가」를 재게 된다. review-loop의 「신규 규칙 입증 책임」(실패 실제 사례 인용) 원칙과의 관계는 D13이다 — 사례가 없음을 그대로 적고, 근거를 밝혀 넣고, AC13에서 통하지 않으면 고치거나 뺀다.

## 3. 설계

### 3a. 훅 — 압축 직후 재읽기 안내 (D3 · D4 · D5 · D14~D18)

**등록** — `hooks.json`의 `hooks` 아래에 추가한다(`Stop` 항목은 불변):

```json
"SessionStart": [
  { "matcher": "compact",
    "hooks": [ { "type": "command",
                 "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/scripts/compact-reread-hook.mjs\"" } ] }
]
```

**스크립트 계약** (`compact-reread-hook.mjs`)

- 입력: stdin JSON. **읽는 값은 `source` 하나뿐**이다. `source`가 문자열이고 `compact`가 아니면 아무것도 출력하지 않고 exit 0(D15 — 등록의 matcher가 유일한 문지기가 되지 않게 한다: matcher가 빠지면 모든 세션 시작에 틀린 안내가 붙는다). stdin이 없거나 · 비었거나 · 깨졌거나 · `source`가 없으면 안내를 낸다(matcher를 통과해 온 호출이다 — 안내를 잃지 않는다).
- 출력: stdout에 JSON 1개 — `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"<안내문>"}}`, exit 0(D14 — 평문도 공식 계약상 주입되지만 안내문이 `[`로 시작해 JSON으로 오인될 여지를 없앤다. 공식 마켓의 다른 플러그인도 이 형식을 쓰고, 격리 실험에서 이 형식의 주입을 확인했다 — §6b H1·H4).
- **채우는 값은 스킬 폴더 절대 경로 하나**다 — 스크립트 자신의 위치(`import.meta.url`)에서 `../../skills`를 해소한다. 파일 시스템 조회(`readdir`·`existsSync` — 경로 존재 확인 포함) · 세션 기록(`transcript_path`) 읽기 · 환경 변수 분기는 없다(끄는 스위치도 없다 — D18). 실패할 지점이 stdin 읽기 하나뿐이고(잡아서 안내를 낸다), 다른 세션의 파일을 짚을 일이 없다.
- 길이: 안내문 2,000자 이하(공식 한도 10,000자 — 넘으면 파일 경로 + 앞 2,000자 미리보기로 바뀐다, F2).
- SessionStart 훅은 세션을 막지 못하는 계약이다(F3 · H3) — node가 없거나 스크립트가 죽어도 훅 오류 알림만 뜨고 세션은 진행한다(넛지 훅과 같은 의존).

**안내문 정본** (문구 승인 2026-11-15 — 구현은 글자 그대로 쓴다. `<SKILLS>` = 해소한 스킬 폴더 절대 경로 · `<스킬 이름>`·`<ledger 문서 이름>`·`<phase>`는 글자 그대로 · 줄바꿈 = 아래 7줄):

```
[dev-workflow] 이 대화는 방금 압축(요약)됐다. 압축 뒤에는 호출했던 스킬 본문이 앞부분만 남고(스킬당 약 5,000토큰), 진행 상태는 요약문에만 남는다.
dev-workflow 스킬(review-loop · harden-spec · orchestrate · mr-review 등)을 실행하던 중이 아니면 이 안내를 무시한다. 실행하던 중이면 다음 행동 전에:
1. 그 스킬의 SKILL.md 전문을 Read로 다시 읽는다(길면 나눠서 끝까지) — <SKILLS>/<스킬 이름>/SKILL.md. 스킬을 다시 호출하지 않는다 — 처음부터 다시 시작하는 것이 아니라 하던 곳에서 이어 간다.
2. 진행 상태를 파일에서 다시 읽는다 — review-loop: 그 루프의 .remember/loop-<ledger 문서 이름>-<phase>.md 를 읽고 SKILL.md의 「압축 뒤 이어가기」를 따른다. 그 외: 작업 중이던 산출물 파일(spec·plan 등)과 핸드오프 파일(기본 .remember/remember.md)의 이 세션 몫.
3. 트랙 프롬프트 파일(.remember/track-*.prompt 등)로 시작한 세션이면 그 파일을 다시 읽는다 — 역할·진행 범위·정지 조건·종료 표지 규약은 압축 뒤에도 그대로 유효하다.
4. 대화에만 있던 작업 목록(예: harden-spec의 갭 대장 · 아직 묻지 않은 질문)은 요약문에 기대지 말고 산출물 파일과 대조해 다시 만든다.
5. 요약문과 파일·git이 다르면 파일·git을 믿는다.
```

- 조건문인 이유(D4): 훅은 그 세션이 어떤 스킬을 돌리던 중인지 알 수 없고, 플러그인을 설치한 **모든 세션 · 모든 저장소**의 압축에서 돈다. dev-workflow와 무관한 세션에는 「무시한다」 한 문장이 전부다(압축 1회당 약 400토큰).
- 1번 줄의 「다시 호출하지 않는다」(D17): Skill 도구로 다시 부르면 스킬이 처음(재개 점검 · 사전 게이트)부터 다시 시작하려 한다. 다만 **다른 플러그인이 압축 직후에 「관련 스킬은 반드시 호출하라」를 다시 넣을 수 있다**(H4) — 그래서 review-loop는 다시 호출돼 들어와도 같은 곳으로 가게 문서 맨 앞에서 받는다(§3c).
- 3번 줄(D16): 트랙의 정지 조건(push 금지 · 다음 단계 시작 금지)과 종료 표지 규약은 트랙 프롬프트 파일에 있고 압축 뒤에는 요약문에만 남는다 — 표지가 빠지면 메인 세션의 감시가 완료를 잡지 못한다. 훅은 그 파일을 찾지 않는다(조건문만).
- 4번 줄(D10): harden-spec의 「아직 묻지 않은 갭」은 종료 보고 전까지 대화에만 있다. 스킬 문서는 고치지 않고 이 한 줄로만 받는다.
- 이 안내는 다음 압축 때 요약에 흡수되어 사라진다(F5) — 그래서 일회성 안내가 아니라 **압축마다 다시 도는 훅**이어야 한다.

|---|---|
| 1 | `$L.pid`가 살아 있으면 띄우지 않고 ③으로(현행) — 아래 2~3을 하지 않는다. 그 라운드의 기록은 이미 있다 |
| 2 | **그 라운드 이름의 옛 `$L.out`·`$L.pid`를 지운다**(D19) — 같은 문서를 예전에 검증한 루프가 같은 이름의 출력을 남겼을 수 있다. 두 파일은 기동 때 어차피 새로 쓰는 파일이라 잃는 것이 없고, 「출력 파일이 없으면 아직 안 띄운 것」이라는 판정(§3c)이 항상 맞게 된다 |
| 3 | **루프 파일을 통째로 다시 쓴다**(라운드 기록 — 파일명 규격 §0 그대로) |
| 4 | 래퍼 기동(현행) |

- **이 시점인 이유**: §2a가 방금 커밋해 작업 트리가 clean이고 HEAD가 확정돼 있다 — §2i의 「순서 1(커밋)이 2(파일)보다 앞서야 한다」를 그대로 만족한다. 라운드가 도는 동안은 추적 파일 편집이 금지라(§2b ③) 기록이 응답 수신 때까지 유효하다. 카운터는 직전 라운드의 §2j를 지난 값이다. clean을 따로 다시 검사하지 않는다 — 수신 측(§0 · §0b)의 대조가 맡는다.
- **형식 = 4섹션 골격 그대로, 내용은 가볍게**:
  - `## 현재` — §0 복원 필드 전체(현행 목록 그대로). HEAD 칸(「중단 시 HEAD SHA」 — 칸 이름은 바꾸지 않는다) = 이 시점 HEAD.
  - `## task 진행` — 현행대로(해당 없음 또는 1줄).
  - `## 미해결 ledger` — ledger 위치 참조 + 건수 1줄(루프 직접 판정 · batch 적재 · 미판정 blocking — 내용은 ledger 표가 원본) + **미확인 FIXED 큐는 항목당 1줄** `fingerprint · 수정 커밋 · 원문 위치(라운드 출력 파일 경로 + finding 제목)`. 확인 대기 대장의 번복에서 승계한 항목(현행 §1 — 라운드 출력이 없다)은 원문 위치 = **대장 문서 경로 + 대장 행 번호**(원 지적 = 그 행의 질문 요지 + 처리 커밋 diff — 현행 규정 그대로). **원 지적 원문과 diff 요약을 베껴 쓰지 않는다** — 원문은 `.remember/`의 라운드 출력 파일(또는 대장 행)에, diff는 수정 커밋에, 판정 주체는 ledger 행의 출처 표기에 이미 있다.
  - `## 다음 액션` — `라운드 기록 — <R|C><N> 기동 직전 · 종류(일반 | 예약분: 복귀 적대 · 재진입 확인 · 폴백②) · 판정 정책(자동 | 정밀)` + 「압축 뒤 같은 세션 = §0b · 새 세션 = `/review-loop --resume`(이 라운드는 응답 미수신 — 재실행)」.
- **새 복원 필드는 없다.** 「라운드 기록」 표지와 기동 라운드는 `## 다음 액션`에 적는다(그 절은 이미 진행 중 라운드의 번호·종류·판정 정책을 담는다 — §2i).
- **일시중단 기록에서 재개한 세션**(§0 복원 통과 뒤 · 응답 처리 전)은 루프 파일 `## 다음 액션` 맨 앞에 1줄 `재개 처리 중 — <수신 라운드 또는 다음 단계>`를 더해 다시 쓴다(나머지는 전체 형식 그대로 — 이 세션이 죽으면 새 세션은 §0으로 그대로 복원한다). 다음 라운드 기동 때 라운드 기록이 덮어쓴다. 일시중단 기록을 **쓰던** 세션과 그 기록을 **이어받아 처리하던** 세션이 압축 뒤 같은 파일을 보고 갈리게 하는 표지다(§3c 표).
- **§2i 일시중단은 현행 그대로**다 — 순서 0~4를 따라 **전체 형식**(큐의 원 지적 원문을 코드펜스로)으로 같은 파일을 덮어쓴다. 라운드 기록은 일시중단 기록을 대신하지 않는다.
- **종결하면 §4가 이 파일을 제거한다 — 빠른 종료(§2e)도 같다.** 지금까지는 일시중단한 루프에만 파일이 있었지만 이제 모든 루프에 있다.
- **전제 문구(D8)**: §0 「루프 상태 파일 — §2i가 쓴다」 → 「§2b 라운드 기록 · §2i · §0 재개 표지가 쓴다」 · §0 「남아 있는 `loop-*.md`는 항상 재개 대기 중인 루프의 것이다」 → 「**끝나지 않은 루프**의 것이다(이 세션이 돌리는 중이거나 재개 대기)」. 제거는 여전히 §4 하나뿐이라 0개/1개/2개 이상 판별은 그대로 결정적이다. **장치는 더하지 않는다** — 돌고 있는 루프의 파일을 다른 세션이 발견해 이어받는 경우(같은 루프의 동시 실행)는 08-10 D9가 이미 규약 위반으로 두고 잠금 없이 가기로 한 영역이다. 단일 작성자 · `remember.md` 무접촉 · `.remember/` 비커밋 · clean 판정 제외는 불변.
- **새 세션이 라운드 기록에서 재개하면**(세션이 죽은 경우 — §0 자동 감지·`--resume`): §0 스냅샷 대조는 그대로다(HEAD·clean이 맞을 때만 복원 — 응답을 처리하기 전에 죽은 경우만 통과한다). 통과하면 기동 라운드는 **재실행**한다(§2i의 기존 규칙 「완료된 고아 라운드는 재실행 — 응답 미수신 = 예산 미소모」). 큐 원문은 기록의 위치 참조로 읽고, 참조한 원문 위치(라운드 출력 파일 · 대장 행)가 없으면 복원하지 않고 사용자 확인(fail-closed — 원문 없이는 확인 프롬프트 첨부물 계약을 채울 수 없다. §0 통합 규칙과 같은 처리).
- **근거 구절(D13)**: 규정 끝에 1구절 — 「근거: 압축 뒤 이 본문은 앞 5,000토큰만 남고 카운터·모드는 대화에만 있다 — 실패 사례가 아니라 플랫폼 동작 대비」.
- **비용(추정 — 미실측)**: `## 현재` 250~350토큰 + 큐 항목당 약 40토큰 + 나머지 100토큰 ≈ **라운드당 400~700토큰**(수정 5건 기준 약 600). 전체 형식을 매 라운드 쓰면 1,500~3,000토큰이다. 실측치는 AC13 ⑥에서 적는다.

### 3c. review-loop — 압축 뒤 이어가기 (§0b 신설 · D7 · D9 · D17 · D20 · D28)

**SKILL.md 맨 앞(Announce 줄 바로 뒤 — 압축 뒤에도 남는 앞부분)**에 1문단: 「이 루프를 돌리던 중 대화가 압축(요약)됐다면 이 본문은 앞부분만 남아 있다 — 이 SKILL.md 전문을 Read로 다시 읽고 §0b를 따른다. 스킬을 다시 불러 들어왔더라도 §0·§1이 아니라 §0b다.」 훅이 돌지 않는 경우(유휴 압축에서의 발화는 미확정 — M1 · 훅 비활성)에도 통하는 경로이고, 다른 플러그인의 안내에 끌려 스킬을 다시 호출한 경우(H4)도 같은 곳으로 모은다.

**§0b 「압축 뒤 이어가기 (같은 세션)」** — §0 바로 뒤.

1. **적용 조건**: 이 세션이 루프를 돌리던 중 대화가 압축된 경우(압축 뒤 안내를 받았거나, 대화 앞부분이 요약으로 바뀐 것을 스스로 알아챈 경우). `/clear` 뒤나 새 세션은 §0이다.
2. **다시 읽는다**: SKILL.md 전문 → 이 루프의 루프 파일(`.remember/loop-*.md`가 1개면 그것 · 여러 개면 ledger 문서·phase로 특정 — 특정하지 못하면 7) → ledger 문서의 `## 적대검증 ledger (<phase>)`(작업 트리 사본) → `git status --short` · `git log --oneline <루프 파일의 HEAD>..HEAD` → 기동 라운드의 `$L.out`(마커)과 `$L.pid`.
3. **항상 보는 것**: 브랜치와 base SHA가 루프 파일과 같아야 한다(이 세션이 바꿀 일이 없는 값이다). 다르면 7.
4. **위치 판정** — 루프 파일 `## 다음 액션`의 기동 라운드 기준. 「스냅샷 대조」 = §0과 같은 검사(HEAD == 루프 파일의 HEAD · tracked 변경 없음 — `.remember/` 제외)이고, 「적용」 행에서 어긋나면 7이다(D9 — 응답을 처리하기 전에는 이 세션이 추적 파일을 바꾸거나 커밋할 일이 없다. 어긋났다면 남이 바꾼 것이다). 루프 파일이 있으면 **「기록 누락 · 모순」 행을 먼저 검사**하고, 해당하지 않을 때 나머지 행을 본다(같은 라운드의 정상 갱신과 뒤 라운드의 기록 누락이 섞이지 않게).

   | 루프 파일 · 관측 | 위치 | 스냅샷 대조 | 이어갈 곳 |
   |---|---|---|---|
   | `## 다음 액션`이 일시중단 기록(§2i) · 「재개 처리 중」 줄 없음 | 일시중단 절차 중 | — | §2i의 남은 순서 |
   | `## 다음 액션`이 일시중단 기록 · 맨 앞에 「재개 처리 중」 줄(§3b) | 재개 뒤 처리 중 | 수신 라운드의 판정 행이 **루프 파일 HEAD 뒤에** ledger에 더해졌으면(재개 뒤 판정을 시작했다) **면제** · 아니면 적용 — §2i 순서 0이 일시중단 때 적어 둔 수신 기록은 처리 증거가 아니다(D9 그대로) | 일시중단 기록의 `## 다음 액션`(수신 라운드 · 판정 정책 · 미처리 단계)부터 — 수신 라운드가 있으면 그 finding이 전부 ledger에 있는지 대조한 뒤 남은 단계. 카운터는 이미 반영돼 있다(6) |
   | 라운드 기록 · `$L.out` 없음 | 기동 전 | 적용 | §2b ①부터 기동 |
   | `$L.out` 있음 · 마커 없음 · pid 생존 | 응답 대기 | 적용 | §2b ③ 대기 |

5. **한 줄 보고(D20)**: 위치를 판정하면 이어 가기 전에 화면에 1줄 — 「압축 뒤 이어가기 — `<R|C><N>` `<위치>`부터 · 적대 소진 n · 확인 소진 n」. 훅 안내문은 화면에 보이지 않는다(F4) — 이 줄이 사람과 메인 세션이 보는 유일한 흔적이다.
6. **카운터는 더하지 않고 다시 계산한다.** 그 라운드의 §2j에서 `소진 = 루프 파일의 값 + (기동 라운드가 일반 예산 라운드이고 유효 응답 — 확인은 완전 응답 — 이면 1, 아니면 0)`을 **대입**한다. 압축 전에 이미 올렸는지를 기억에 묻지 않는다 — 몇 번을 다시 계산해도 같은 값이다. 예약분 라운드는 두 카운터 불변. 「재개 처리 중」 행에서는 수신 라운드가 §2i 순서 0에서 이미 반영됐으므로 루프 파일의 값을 그대로 쓴다(+0). 판정 정책은 루프 파일에 적힌 **수신 시점 모드**(§2i 재개 계약과 같다). 결과에 따라 갈리는 전이(score · 전환 신호 · batch flush · 복귀 · 확인 결과 처리)는 ledger 기록에서 다시 판정한다. 답을 받지 못한 질문(batch 제시 · 즉시 ESCALATE)은 ledger의 미판정·batch 적재를 근거로 다시 묻는다 — 위임 모드에서 이미 ledger·대장에 적힌 자동 채택은 다시 채택하지 않는다.
7. **되찾을 수 없으면 추측으로 이어 가지 않는다** — 루프 파일·ledger를 바꾸지 않고 멈춰서 어긋난 내용을 알린다. 수동 모드 = 사용자 확인(§사람에게 묻는 형식) · 위임 모드 = 보고하고 멈춤(§위임 모드 표의 fail-closed 행 — 자리 1곳 추가).
8. **근거 구절(D13)**: 절 첫머리에 1구절 — §3b와 같은 근거(본문 절단 · 플랫폼 동작 대비).

### 3d. 넛지와의 공존

- 넛지 훅(`Stop`)은 무변경이다. 넛지가 오면 현행 §2i 경로 ①대로 전체 형식 루프 파일 → 인계. 라운드 기록이 이미 있어도 §2i가 덮어쓴다.
- 압축 뒤 사용량이 크게 떨어지면 넛지 훅은 스스로 새 주기로 되돌린다(현행 — 구간 2단 이상 하락 시 재초기화). 새 훅은 넛지의 상태 파일을 읽지도 쓰지도 않는다.
- 넛지를 받은 뒤(핸드오프 작성 중) 압축이 겹치면: 사용량이 떨어져 넛지의 사유(대화가 너무 크다)가 사라진 상태다 — 인계를 마치든 이어 가든 해가 없다. 새 훅의 2번 줄과 §2i는 같은 파일을 가리킨다.
- 넛지 훅과 바이트 동일해야 하는 review-loop 문장 2개(§2b 진행 중 금지 (1)의 인용문 · §2i의 작업 단위 정의 — 넛지 훅 주석이 정본을 review-loop로 지정)는 **이번에 건드리지 않는다**(AC9).

### 3e. 발효 · 버전 호환

- **구버전 세션의 라운드 기록 재개**(D26) — 보장하지 않는다.
- **라운드 기록 누락**(D28) — 모델이 기록을 빠뜨리면 압축 뒤 멈추고 보고한다. 빈도는 AC13과 시험에서 드러난다.
