## 2. 목표 / 비목표

**목표:** 위 네 지점에서 **규정과 실무의 어긋남을 닫는다.** 새 기계 장치를 만들지 않고, 이미 실무가 수렴한 형태를 문면으로 승격하는 것이 이 트랙의 성격이다.

- **C-3** — `review-loop` §finding ledger의 ledger 위치를 phase별로 명시하고 planless 예외(D17)를 흡수한다.
- **C-4** — `review-loop` §2i의 핸드오프를 **4섹션 골격**으로 표준화하고, 공유 파일 덮어쓰기 전 보존 확인을 넣는다.
- **C-7** — `ui-mockup`의 목업 생략 기록을 **D번호+근거**로 승격하고(=D16 재검토 결론), 슬러그 기본값에서 `-design` 접미를 제거한다.
- **C-8** — Stop 훅의 1회 넛지를 **구간 기반 재넛지**로 바꾼다.

**비목표 (YAGNI / 범위 보호):**

## 3. 설계안 (harden-spec에서 D번호로 확정)

### C-3. impl ledger 위치 — phase별 명시

`review-loop/SKILL.md` §finding ledger `:83`의 "해당 phase 산출물 문서 말미"를 phase별 표로 바꾼다.

| phase | ledger 위치 |
|---|---|
| spec | spec 문서 말미 |
| plan | **plan 엔트리포인트 말미** (task 파일이 아니다) |
| impl | **plan 엔트리포인트 말미** (plan ledger와 같은 문서, 섹션만 다름) — **plan을 생략한 트랙은 spec 문서 말미** |

- impl에 자체 산출물 문서가 없다는 것이 모호함의 원인이므로, "impl의 phase 산출물 문서 = plan 엔트리포인트"를 명시한다.
- planless 예외는 D17의 흡수다. 단일 원본·복제 금지 규정은 현행 그대로 유지한다.

### C-4. 핸드오프 4섹션 골격 + 보존 확인

`review-loop/SKILL.md` §2i를 개정한다. **4섹션을 핸드오프 문서의 고정 골격으로 승격**하고, 현행 필드 목록을 그 안에 배치한다.

| 섹션 | 내용 |
|---|---|
| ① **현재** | 현행 복원 필드 전부 — phase / 적대·확인 소진 카운트 / 현재 모드 / 복귀 사용 여부 / base(해소된 ref + SHA) / branch / 중단 시 HEAD SHA / score 이력 / 보안 크리티컬 판정 |
| ② **task 진행** | plan/impl phase의 task 상태 |
| ③ **미해결 ledger** | 미확인 FIXED 큐(fingerprint별 원 지적 원문·수정 커밋 SHA·diff 요약·판정 주체 — 현행 규정 유지) + 미판정 blocking |
| ④ **다음 액션** | 재개 명령 + 다음 단계·트랙 지목 |

- §0 복원 필드와 §2i 핸드오프 필드가 **동일 목록**이라는 현행 계약은 유지한다 — 바뀌는 것은 배치이지 목록이 아니다.
- **덮어쓰기 전 보존 확인 1줄**: `.remember/remember.md`는 공유 파일이다. 쓰기 전에 기존 내용을 읽고, **이 루프와 무관한 기록(다른 트랙·운영 후속)이 있으면 보존 방법을 먼저 확인**한다. `ui-mockup:56`의 미커밋 보존 확인과 같은 메커니즘이다.
- `--resume`은 **안전판**이며 실질 재개 수단은 이 핸드오프임을 명시한다.

### C-7. ui-mockup 2건

① **생략 기록 승격** (`ui-mockup/SKILL.md:38` §입력 진입 확인)
현행 "「UI 목업 생략(사용자 결정)」 한 줄만 기록·커밋하고 종료"를 **`D<n>. UI 목업 생략(사용자 결정) — <근거>`** 로 바꾼다. 근거는 진입 확인에서 사용자가 밝힌 사유이며, **근거 없이는 닫지 못한다.**

이것이 **D16 재검토의 결론**이다 — 사용자 명시 생략 경로는 유지하되(판정자는 사용자라는 §핵심 원칙 1과 정합), 한 줄 도장으로 닫는 경로만 차단한다. 경량 판정에 의한 **자동** 생략 금지는 D16 원안 그대로다.

② **슬러그 기본값** (`:36` §입력)
"spec 파일명에서 날짜 접두를 제거한 값"을 **"날짜 접두와 `-design` 접미를 함께 제거한 값"** 으로 바꾸고 예시를 갱신한다(`2026-07-25-foo-design.md` → **`foo`**).
- 기본 **제안값**만 바뀐다. 사용자가 다른 슬러그를 지정하는 경로, `^[a-z0-9-]+$` 단일 세그먼트 검증은 불변.
- 소유자 판정은 spec의 `## UI 설계` 참조 기반이라 기존 디렉터리 탐색에 영향이 없다.

### C-8. 훅 재넛지 — 구간 기반

`hooks/scripts/context-threshold-hook.mjs`의 `decideNudge`를 1회 플래그에서 **구간 인덱스**로 바꾼다.

- 넛지 지점 = `threshold + k × 0.15` (k = 0, 1, 2, …) — 기본 임계 40%에서 **40 → 55 → 70 → 85%**.
- 현재 구간 `k_cur = floor((ratio − threshold) / 0.15)`. **`lastNudgeStep`이 `null`(아직 넛지 없음)이면 `k_cur ≥ 0`에서 넛지**하고, 값이 있으면 **`k_cur > lastNudgeStep`일 때만** 넛지한다.
- 플래그 파일에 마지막 넛지 구간 `k`를 저장한다 — 형식은 `step=<k>`(현행은 `"1"` 고정). 인터페이스는 `alreadyNudged: boolean` → **`lastNudgeStep: number | null`**.
- 재넛지(k ≥ 1) 문구는 **강화형** — 이전에 안내했고 지금 몇 %인지, 핸드오프를 아직 쓰지 않았다면 지금 쓰라는 취지를 담는다. 첫 넛지 문구는 현행 유지.
- 구버전 플래그 파일(`"1"`)은 `step=` 형식이 아니라 파싱에 실패하므로 **`lastNudgeStep = 0`으로 간주**한다 — 첫 넛지는 이미 한 것으로 보고 다음 구간부터 재넛지한다.
- `computeContextUsage`·임계 해석(`CLAUDE_CTX_THRESHOLD`)·`stop_hook_active` 처리는 불변. 간격 0.15는 상수.

브리프 §0-2 규약: 스킬 문면 변경은 writing-skills TDD 필수 — **베이스라인(현행 스킬로 실패 재현) → 개정 → 마이크로테스트(5+ reps, 무지침 대조군 포함)**. C-6의 dcx 하네스(픽스처 28종·`ARM=new|cur|none` 규약)를 재사용한다.

| arm | 대상 | 픽스처 | 판정 기준 |
|---|---|---|---|
| **L-1** | C-3 — plan 보유 트랙의 impl ledger 위치 | plan 엔트리포인트 + task 파일 존재, impl 루프 진입 | ledger를 **plan 엔트리포인트 말미**에 두는가(task 파일·spec에 두지 않는가) |
| **L-2** | C-3 — planless 예외 | plan 없음(경량 트랙), spec에 D블록 존재 | **spec 문서 말미**에 두는가 |
| **H-1** | C-4 — 4섹션 골격 | 컨텍스트 임계 넛지 수신 상태의 impl 루프 | 핸드오프를 **4섹션**으로 쓰고 복원 필드가 ①에 들어가는가 |
| **H-2** | C-4 — 공유 파일 보존 | `.remember/remember.md`에 **다른 트랙 기록**이 이미 있음 | 덮어쓰기 전 **보존 확인**을 하는가(무단 덮어쓰기 0건) |
| **U-1** | C-7① — 생략 기록 | 화면 구성 변경 spec + 사용자가 3.5 생략 선택 | **D번호+근거**로 기록하는가(한 줄 도장 0건) |
| **U-2** | C-7② — 슬러그 기본값 | `YYYY-MM-DD-foo-design.md` spec으로 ui-mockup 진입 | 기본 제안이 **`foo`** 인가(`foo-design` 0건) |
| **none** | 무지침 대조군 | 위 축 중 3~5개 × 2~3 reps | 개정본 고유 기여의 분리 측정(C-6 전례 — 무지침도 같은 결론이면 고유 기여로 주장하지 않는다) |

- **C-8은 TDD 대상이 아니다** — `decideNudge`는 순수 함수라 node로 직접 케이스를 돌린다(모델 예산 0). 케이스: 임계 미만(39%) / 첫 넛지(40%) / 구간 내 재호출(54%) / 다음 구간(55%·70%·85%) / 커스텀 `CLAUDE_CTX_THRESHOLD` / 구버전 플래그 파일 / `stop_hook_active`. 실행 경로(`main`)의 플래그 읽기·쓰기도 임시 디렉터리에서 확인한다.
- **하네스 관례 보강(C-6 핸드오프 미이행 항목)**: "구현 완료 픽스처는 **호출부까지 연결**한다" — 빈 스텁 픽스처 결함이 C-5·C-6에서 3회 반복됐다. 이번 배치 전에 반영한다.
- **8단계 게이트**: 이 repo는 npm 프로젝트가 아니므로 비-npm 갈음(dev-cycle 8단계 주석) — **writing-skills TDD GREEN 기록 + C-8 스크립트 케이스 전건 통과**로 impl 게이트를 대신한다.

## 7. 미해결 질문 (harden-spec 입력)

1. **4섹션의 빈 섹션 처리** — "② task 진행"이 spec phase·planless 트랙에서는 빈다. "해당 없음" 명기인가, 섹션 생략 허용인가?
