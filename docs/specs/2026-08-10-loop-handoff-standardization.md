## 5. 결정사항

### 경로·절차

**D1. 경로 = 정식.** 접촉 표면이 **데이터 손상/유실**에 닿는다 — 원 사고 F3이 인계 내용 유실이고, 이월 blocking ①·③도 상태 유실 축이다. dev-cycle 규약상 이 축은 규모·요청과 무관하게 정식이다. 3.5(ui-mockup)는 화면이 없어 **비대상**.

**D2. plan(5·6) 생략.** 브리프 §0-1 규약(spec → harden → review-loop(spec) → writing-skills TDD 직접 구현 → review-loop(impl))을 승계한다. 근거 ① 7a·7b가 같은 구성으로 종결했다 ② 대상이 SKILL.md 단일 문서라 plan 분할의 가치(다파일 전체 정합성)가 나오지 않는다. **6은 5 생략에 따라 자동으로 해당 없음**(dev-cycle 규약).

### 파일 체계

**D3. 두 파일로 가른다 — 역할 경계.**

| 파일 | 소유 | 내용 | 수명 |
|---|---|---|---|
| `.remember/loop-<ledger basename>.md` | **그 루프를 도는 세션(단일 작성자)** | 4섹션: ① 현재 / ② task 진행 / ③ 미해결 ledger / ④ 다음 액션 | 루프 **성공 종료 시 제거** |
| `.remember/remember.md` | 공유 | 트랙 인계·승계 관례·백로그·하네스 등 | 영속 (트랙 종결 시 `archive-<날짜>-<slug>.md` 이관 — 현 관례 유지) |

**D4. `<ledger basename>` = canonical ledger 문서의 파일명 그대로(날짜 접두 포함).** 예: `docs/specs/2026-08-09-ledger-handoff-mockup-nudge.md` → `.remember/loop-2026-08-09-ledger-handoff-mockup-nudge.md`. 고유성을 `docs/specs/` 파일명에서 **상속**하므로 충돌 감지 장치를 두지 않는다(브리프 G1·G2 과설계 금지와 정합). 기존 `archive-<날짜>-<slug>.md` 관례와 동형이다.

- **phase마다 ledger 위치가 다를 수 있다**(C-6 D17: plan 있는 트랙의 impl ledger = plan 엔트리포인트 말미 / planless 트랙 = spec 문서 말미). `<ledger basename>`은 **그 루프의 phase ledger가 놓이는 문서**의 파일명이다 — 트랙 이름이 아니다.
- 따라서 한 트랙이라도 phase에 따라 루프 파일명이 달라질 수 있다. D5(성공 종료 시 제거)가 이를 흡수한다 — 직전 phase 루프가 정상 종결했다면 파일은 0개이므로 D7이 결정적이다. **2개 이상이 보이면 앞 phase 루프가 미완이라는 뜻이고, fail-closed가 올바른 동작이다.**

**D5. 성공 종료 시 루프 파일을 제거한다**(§3 종료 전 커밋 시점). 남아 있는 `loop-*.md`는 **항상 미완 루프**의 것이다 — 이 불변식이 D7의 판별을 결정적으로 만든다.

**D6. 루프가 `remember.md`를 건드리는 시점은 정확히 하나다.**

- **진행 중**(§2i 컨텍스트 핸드오프): `loop-*.md`만 쓴다. `remember.md` **무접촉** → F3의 사고 경로가 구조적으로 사라진다.
- **종결 시**(§4 단계 경계): 다음 단계·트랙 인계를 `remember.md`에 쓴다. **이 한 시점에만** 덮어쓰기 전 **기존 내용 보존 확인**을 건다(C-4 원안의 "보존 확인 1줄" 부활).
- 7a **D9 개정을 정밀화한다** — "보존 확인 불필요"는 *진행 중*에만 참이었다. 종결 쓰기가 남아 있는 한 F3 경로는 완전히 닫히지 않으므로, 접촉면을 1시점으로 줄인 뒤 그 지점에 보존 확인을 남긴다.

### 복원

**D7. `--resume` 대상 선택 = `.remember/loop-*.md` 조회.**

| 발견 수 | 동작 |
|---|---|
| 0개 | 새 루프(적대 소진 0 · 확인 소진 0 · 빈 ledger · 적대 모드) |
| 1개 | 그 파일에서 복원 |
| 2개 이상 | **fail-closed 사용자 확인** (파일명이 트랙을 보여주므로 선택이 결정적이다) |

`§0` 스냅샷 대조(branch·HEAD SHA·base SHA·clean tree)는 **현행 그대로** 유지한다. 텍스트 경계 파싱도, 저장값을 기대값으로 되쓰는 자기참조 대조도 없다.

**D8. 비소급 — 0.14.0 이전 형식(`remember.md` 안의 루프 상태)은 복원하지 않는다.** 전환기 1회성 문제를 영구 조항으로 만들면 시간이 지나 죽은 규칙이 된다(C-6 D8 비소급 전례). 대신 **릴리스 종료 보고에 1회 안내**한다 — 미완 루프가 있으면 사용자가 직접 `loop-*.md`로 옮긴다.

### 소유권·직렬화

**D9. 루프 파일은 그 루프를 도는 세션만 쓴다**(§2i에 1줄). 재읽기·비교·락 같은 기계장치는 두지 않는다. 근거 ① 같은 트랙 루프의 동시 실행은 이미 review-loop 규약 위반이고, 그 상황에선 핸드오프보다 **같은 브랜치의 상호 커밋·ledger 분기**가 먼저 터진다 ② 수신 측 방어가 이미 있다 — `§0` 스냅샷 대조가 branch·HEAD·base·clean tree 불일치를 fail-closed로 잡으므로 stale 상태로 **재개하는** 경로는 막혀 있다 ③ 실측 0건 ④ 매 쓰기마다 절차를 붙이면 G1·G2에 저촉된다.

**D10. 미해결 ledger 섹션의 원 지적 원문은 코드펜스 안에 넣는다**(§2i에 1줄). 원문에 줄머리 `##`가 있어도 섹션 경계로 오인되지 않는다. 이 이상의 escaping 규약은 두지 않는다 — 복원 주체가 파서가 아니라 **LLM**이고, 이 repo가 이미 문면화한 원칙(`SKILL.md:277` "문서의 문자적 논리 갭은 실행 영향으로 severity 재평가 — 문자적 갭 ≠ 즉시 high")이 정확히 이 경우다. 실측 충돌 사례 0건이며, 그 조항의 단서("닫는 수정이 저비용이면 반영한다")에 따라 **1줄만** 반영한다.

### 파급·적용

**D11. 훅 넛지 문구에 단서 1줄을 붙인다** — `context-threshold-hook.mjs:85~86`은 **모든 세션**에 `.remember/remember.md`를 지시하므로, 루프 세션이 그대로 따르면 D6의 무접촉 규칙과 충돌하고 F3 경로가 훅을 통해 되살아난다. 비-루프 세션의 안내는 그대로 두고 "review-loop 실행 중이면 그 스킬의 핸드오프 규정을 따른다"만 덧붙인다.

**D12. 적용 시점 — 이 트랙 자신의 review-loop는 개정 전 규격(0.13.0)으로 돈다.** 개정은 **0.14.0 설치 이후 시작하는 루프**부터 발효한다. C-4는 자기참조 트랙이라(고치는 규격을 자기 루프가 사용한다) 못박지 않으면 4·8단계 루프가 개정 중인 문면을 따라가 상태가 섞인다.

- 물리적으로는 이미 분리돼 있다 — 실행되는 스킬은 **설치본**(`~/.claude/plugins/cache/claude-dev-workflow/dev-workflow/0.13.0/skills/`)에서 로드되고, 이 트랙이 고치는 것은 **작업 트리**의 원본이다. D12는 그 분리를 문면으로 확정해, 루프 중 "새 규격대로 하자"는 판단이 끼어들지 않게 한다.

### 승계 (7a 확정분 — 재논의 대상 아님)

**D13.** 4섹션 명칭은 ops-hub 런북 원문을 그대로 쓴다(7a D12 승계).
**D14.** ③ 미해결 ledger는 **ledger 전체**(단일 원본 위치 참조 + 루프 직접 판정 표시) + 미확인 FIXED 큐 + 미판정 blocking을 담는다. ③을 "큐 + 미판정"으로 좁히면 §0 복원 필드와 §2i 핸드오프 필드가 **동일 목록**이라는 계약이 문면에서 깨지고, FIXED 큐가 비었는데 루프 직접 판정만 있는 상태에서 재개 세션이 감사 없이 빠른 종료한다(7a D22 승계).
**D15.** 빈 섹션은 생략하지 않고 "해당 없음"을 적는다 — ②는 spec phase·planless 트랙에서 빈다(7a D11 승계).
**D16.** ledger 본문의 단일 원본은 phase 산출물 문서 말미이고, ③은 그 **위치와 루프 직접 판정 목록**을 담는다(복제 금지와 무충돌).

### 범위 방어

**D17. 다중 머신 git 동기 환경을 전제한 방어는 넣지 않는다.** 이 repo의 `.remember/`는 심링크로 `claude-memories` git repo를 가리키고 3머신이 병렬 push하지만, 그것은 **작성자 개인 인프라**이지 이 플러그인 사용자 일반의 조건이 아니다. 그 전제로 blocking ①을 설계하면 범용 규약에 개인 환경 종속이 들어간다. 확인 근거: `dev-workflow/` 전체에 `ops-hub` 문자열 **0건**(산출물 무종속). 실측 표본이 ops-hub 한 곳이라는 사실은 **근거의 한계**로만 기록한다.

## 8. 미해결 질문 (harden-spec 입력)

1. **4섹션 ④의 명칭 통일** — 실측상 `## 다음 액션` 3건 / `## 다음 단계 — …` 변형 다수다. D13(런북 원문 그대로)을 적용하면 변형은 비준수가 되는데, 기존 파일을 소급 개명하지 않는다면 문면에 그 비소급을 적을지.
2. **종결 시 "보존 확인"의 구체 형태**(D6) — 읽고 판단하라는 지시 1줄인지, "기존 섹션 목록을 열거한 뒤 유지/교체를 밝힌다" 수준까지 규정할지. 과설계 경계선이다.
3. **TDD arm 예산** — arm 3종 + 대조군의 실제 런 수. 7b는 90런, C-6은 243런이었다. 배치 직전 모델 주간 잔여를 확인하고 부족하면 **L-1 우선**(핵심 축)으로 나눠 실행한다.
4. **`loop-*.md`의 `.gitignore` 취급** — dev-workflow repo에서는 `.remember` 전체가 ignore 대상이라 무관하나, 이 규약을 채택하는 다른 repo에서 루프 파일이 커밋될 수 있다. 규약이 관여할 문제인지(비목표 후보).
5. **`--resume` 2개 이상 fail-closed의 실제 발생 조건** — 두 트랙(또는 같은 트랙의 두 phase)이 동시에 미완인 경우다. `setup` 안내나 종료 보고에서 "미완 루프 잔존"을 드러낼지.
6. **루프 파일 제거(§3)와 인계 쓰기(§4)의 순서** — D5는 제거를 §3 종료 전 커밋 시점에, D6은 인계 쓰기를 §4에 둔다. 제거가 먼저이므로 §4는 세션 컨텍스트만으로 인계를 써야 한다. 순서를 뒤집을지, 아니면 "§4를 마친 뒤 제거"로 옮길지. `.remember/`가 이 repo에서 ignore 대상이라 "커밋 시점"이라는 표현 자체가 이 repo에선 비어 있다는 점도 함께 본다.
