- **`ui-mockup`의 유사 조항과의 공통 규약 승격.** 지키는 대상이 달라 승격하지 않는다(7a D15 승계).
- **`.remember/`의 추적 정책(`.gitignore`).** 각 repo 소관이며 이 규약은 관여하지 않는다. 이 repo는 `.remember` 전체가 ignore 대상이다. 추적하는 repo에서 동작이 갈리지 않게 하는 것은 `§0`만이 아니라 **D29**다 — `§0:210`의 제외는 복원 게이트 하나뿐이라, §3·D26의 clean 확인까지 같은 제외를 걸어야 추적/비추적이 같아진다(추적 정책 자체는 여전히 비관여).
- **ops-hub 측 후속.** 이 repo 범위 밖(브리프 §트랙 C 말미).

## 5. 결정사항

### 경로·절차

**D1. 경로 = 정식.** 접촉 표면이 **데이터 손상/유실**에 닿는다 — 원 사고 F3이 인계 내용 유실이고, 이월 blocking ①·③도 상태 유실 축이다. dev-cycle 규약상 이 축은 규모·요청과 무관하게 정식이다. 3.5(ui-mockup)는 화면이 없어 **비대상**.

**D2. plan(5·6) 생략.** 브리프 §0-1 규약(spec → harden → review-loop(spec) → writing-skills TDD 직접 구현 → review-loop(impl))을 승계한다. 근거 ① 7a·7b가 같은 구성으로 종결했다 ② 대상이 SKILL.md 단일 문서라 plan 분할의 가치(다파일 전체 정합성)가 나오지 않는다. **6은 5 생략에 따라 자동으로 해당 없음**(dev-cycle 규약).

### 파일 체계

**D3. 두 파일로 가른다 — 역할 경계.**

| 파일 | 소유 | 내용 | 수명 |
|---|---|---|---|
| `.remember/loop-<ledger basename>-<phase>.md` | **그 루프를 도는 세션(단일 작성자)** | 4섹션: ① 현재 / ② task 진행 / ③ 미해결 ledger / ④ 다음 액션 | **재개하지 않는 종료 경로에서 제거**(D5·D18) |
| `.remember/remember.md` | 공유 | 트랙 인계·승계 관례·백로그·하네스 등 | 영속 (트랙 종결 시 `archive-<날짜>-<slug>.md` 이관 — 현 관례 유지) |

**D4. 루프 파일명 = `loop-<ledger basename>-<phase>.md`** — `<ledger basename>`은 canonical ledger 문서의 파일명에서 확장자만 뗀 값(날짜 접두 포함), `<phase>`는 `spec`·`plan`·`impl`. 예: `docs/specs/2026-08-09-ledger-handoff-mockup-nudge.md`의 spec 루프 → `.remember/loop-2026-08-09-ledger-handoff-mockup-nudge-spec.md`. 고유성을 `docs/specs/` 파일명에서 **상속**하므로 충돌 감지 장치를 두지 않는다(브리프 G1·G2 과설계 금지와 정합). 기존 `archive-<날짜>-<slug>.md` 관례와 동형이다.

- **phase 접미는 조건 없이 항상 붙인다.** 근거는 실측 — **planless 트랙은 spec ledger와 impl ledger가 같은 문서 말미에 있어** basename만으로는 phase가 구분되지 않는다: 7a(`2026-08-09-ledger-handoff-mockup-nudge.md:307`/`:415`) · 7b(`2026-08-09-doctor-marker-description.md:307`/`:393`) · C-6(`2026-08-08-dev-cycle-extension.md:258`/`:316`) **3건 전부 해당**. 접미가 없으면 두 phase 루프가 같은 파일을 공유해, D7의 "1개 → 그 파일에서 복원"이 앞 phase 상태를 다음 phase 루프에 실어 나른다(§0 스냅샷 대조가 fail-closed로 막더라도 "선택이 결정적"이라는 D7의 근거 자체가 거짓이 된다).
- **phase마다 ledger 위치가 다를 수 있다**(C-6 D17: plan 있는 트랙의 impl ledger = plan 엔트리포인트 말미 / planless 트랙 = spec 문서 말미). `<ledger basename>`은 **그 루프의 phase ledger가 놓이는 문서**의 파일명이다 — 트랙 이름이 아니다. plan 있는 트랙은 basename이 이미 갈리지만, 판별 규칙을 조건 분기 없이 한 줄로 유지하려고 접미는 그 경우에도 붙인다.
- 따라서 한 트랙에서도 phase마다 루프 파일이 다르다. D5와 합쳐 **2개 이상이 보이면 재개 대기 중인 루프가 둘이라는 뜻이고, fail-closed가 올바른 동작이다.**

**D5. 루프 파일의 수명 기준 = "이 루프를 다시 재개하는가".**

| 종료 경로 | 처리 |
|---|---|
| 성공 종료(빠른 종료 · 확인 경유) | **제거** |
| 폴백 ①(다음 phase 리뷰의 필수 확인 항목으로 이월) · 폴백 ③(배포 검증으로 대체) | **제거** — 루프는 끝났고 부채는 다른 장치가 받는다 |
| 컨텍스트 ≥40% 핸드오프 | **유지** |
| ESCALATE에서 사용자가 중단 선택 | **유지** |
| 폴백 ②(새 세션에서 확인 라운드 1회) | **유지** |

- 남아 있는 `loop-*.md`는 **항상 재개 대기 중인 루프**의 것이다 — 이 불변식이 D7의 판별을 결정적으로 만든다.
- "성공 종료 시 제거"만 규정하면 폴백 ①·③으로 **종결된** 루프가 파일을 남겨 재개 대기와 구분되지 않는다. 가정이 아니다 — 7a spec 루프가 실제로 폴백 ①로 종료했다(`2026-08-09-ledger-handoff-mockup-nudge.md` C3 이후 처리).

**D25. 생성 트리거 = "유지" 3경로 전부.** 위 표에서 유지인 세 경로(컨텍스트 ≥40% · ESCALATE 중단 · 폴백②)는 **종료 전에 루프 파일을 생성하거나 갱신한다.** "유지"는 *이미 있는 파일을 지우지 않는다*가 아니라 *재개 상태가 그 파일에 남아 있어야 한다*는 뜻이다.

- 컨텍스트 임계는 셋 중 하나일 뿐이다. §2i만 생성 지점으로 두면 **40%를 넘기지 않은 채 ESCALATE 중단·폴백②로 끝난 루프는 남길 파일이 없어** 재개 상태가 사라지고, 그 자리에서 옛 문면대로 `remember.md`에 쓰면 D6의 진행 중 무접촉까지 깨진다. 두 경로 모두 컨텍스트 임계와 무관하게 발생한다 — `SKILL.md:287`(ESCALATE 중단: "핸드오프(ledger 포함)를 쓰고 종료")·`:182`(폴백② 정의).
- 따라서 §2 범위에 `SKILL.md:182`·`:287`을 포함한다. 세 경로가 쓰는 내용은 동일하다 — §2i의 핸드오프 필드 전체(= §0 복원 필드, D14·AC5의 동일 목록 계약).
- **매 라운드 갱신(항상 파일이 존재하게 하는 안)은 채택하지 않는다.** 종료 3경로에서만 써도 재개 가능성이 확보되고, 라운드마다 쓰기를 더하는 것은 G1·G2 과설계 금지에 저촉된다.

**D26. 유지 3경로의 종료 순서 = 커밋 → 루프 파일 → 안내 → §4 건너뛰고 종료.**

| 순서 | 동작 |
|---|---|
| 0 | **§2j의 카운터·모드 전이를 먼저 확정한다** — 완전한 응답을 받은 라운드는 소진에 반영하고 현재 모드를 갱신한 뒤 ledger에 기록 |
| 1 | 마지막 ledger 갱신을 **커밋하고 clean tree 확인**(§2a·§3과 같은 규칙 — 명시적 stage, `git add -A` 금지) |
| 2 | **커밋 후 HEAD**로 루프 파일을 생성·갱신(§0 복원 필드 전체) |
| 3 | 재개 안내(`/clear` 후 `--resume`) |
| 4 | **§4의 `remember.md` 인계와 루프 파일 제거를 건너뛰고 종료** — 이 경로는 종결이 아니라 일시중단이다 |

- **순서 0이 없으면 이미 쓴 라운드가 소진에 안 잡힌 채 snapshot이 기록된다.** 현행 문면상 §2i는 **§2j보다 앞**에 있고 ESCALATE 중단은 §2d에서 바로 종료하므로, 완료된 응답 직후 중단하면 카운터가 한 단계 뒤처진다 — 재개 세션이 그 라운드를 **다시 쓰고**, `auto-rounds` 경계의 batch flush와 확인 예산 판정도 한 단계 밀린다. §2j 자신이 "적대 응답을 받았으면 예외 없이 소진을 올린다 — 그 라운드를 실제로 썼기 때문이다"라고 못박고 있으므로, D26은 그 원칙이 **중단 경로에서도 성립하도록 순서를 고정할 뿐**이다.

- **순서 2가 1보다 앞서면 루프 파일에 커밋 전 HEAD가 박히고 §3 커밋이 그것을 무효화해, 다음 재개가 `§0` 스냅샷 대조에서 항상 중단된다.** 현행 문면이 실제로 그 순서다 — `SKILL.md:287`은 "핸드오프(ledger 포함)를 쓰고 종료"인데 §3은 "4번으로 가기 전에 마지막 ledger를 커밋"이라, 쓰기가 커밋보다 앞선다. §2i는 이미 "핸드오프 전 커밋으로 clean tree를 만든다"로 올바른 순서를 갖고 있으므로, D26은 **그 규칙을 나머지 두 유지 경로(`:182`·`:287`)로 일반화**한 것이다.
- 순서 4는 D6·D5에서 나온다 — `remember.md` 쓰기는 **종결 시 1회**(D6)인데 유지 경로는 종결이 아니고, 루프 파일을 지우면 D5의 유지가 깨진다. **D18(제거 = §4 인계 뒤)은 제거 경로에만 적용된다.**

**D27. 복원 필드에 실행 예산 3종을 넣는다.** `--max` · `--confirm-rounds` · `--auto-rounds`의 **해소된 값**을 §0 복원 필드·§2i 핸드오프 필드에 추가하고, 재개 시 저장값을 복원한다.

- 현행 복원 필드에는 이 셋이 없고(`SKILL.md:208` 이하 목록) 재개 안내도 인수 없는 `--resume`이라, **비기본값으로 시작한 루프가 재개되면 기본값(5·2·3)으로 되돌아간다.** 실제 영향: §인자가 보안 크리티컬 작업에 권고하는 `--auto-rounds 1`로 시작한 루프가 재개 후 3이 되어 **자동 수정과 batch 적재가 다시 켜지고**, `--max 2`는 5로 늘어 사용자가 지정한 상한을 넘긴다.
- **재개 시 인자를 다시 명시했는데 저장값과 다르면 fail-closed 사용자 확인.** 이 설계의 다른 불일치 처리(`§0` 스냅샷 대조 · D7 3분기)와 같은 규율이고, 예산을 의도적으로 바꾸는 경우에도 확인 1회로 끝난다.
- D14(③이 ledger 전체를 담는다)와 **같은 필드 영역이지만 축이 다르다** — 저건 ledger 내용, 이건 호출 설정이다. AC5의 "§0 ↔ §2i 동일 목록" 계약은 양쪽에 같이 추가하므로 유지된다.

**D28. 폴백②는 확인 예산 밖 예약분으로 추적한다.** 복원 필드에 **`폴백② 허용/소비 여부`**를 추가하고, 그 값이 *허용·미소비*면 재개 세션의 **확인 예산 잔여 0 가드를 정확히 한 번 우회**한다. 소비하면 다시 잠긴다.

- **D5(폴백② = 유지 경로)와 D27(예산·소진 카운터 복원)의 결합이 교착을 만든다.** 폴백②는 애초에 *확인 예산이 소진된 뒤* 고르는 "예산 밖 확인 1회"인데, 재개 세션이 소진 2/2와 `--confirm-rounds` 값을 그대로 복원하면 `§0`·§2h ②의 **"확인 필수 조건 성립 + 잔여 0 → ESCALATE, `task`를 실행하지 않는다"** 에 그대로 걸린다. 사용자가 폴백②를 고른 순간 그 라운드를 승인한 것인데, 재개가 같은 ESCALATE로 되돌아가면 약속한 확인 1회를 영원히 못 돈다.
- **이미 있는 패턴을 그대로 쓴다** — §2h는 복귀 재진입 확인을 "상한 밖 예약분이라 잔여 0에서도 실행하고, **예약분 소비 여부는 예산 잔여와 별도 상태**(복귀 사용 여부)로 추적한다"고 규정한다. 폴백②도 같은 성격의 예약분이므로 필드 하나를 같은 방식으로 추가한다. 새 개념이 아니라 기존 규율의 적용 확대다.
- **폴백②를 별도의 새 확인 흐름으로 정의하는 안은 채택하지 않는다** — 실행 내용이 기존 확인 라운드와 같아 흐름을 복제할 이유가 없고 G1·G2에 저촉된다.

**D28 세부 계약 — 예약분의 소비·카운터·재승인·총 유계.** 필드만 추가하면 기존 예산 상태 머신과 어긋나므로 네 지점을 함께 못박는다.

| 지점 | 규정 | 현행과의 차이 |
|---|---|---|
| **소비 시점** | **완전한 응답에서만** 소비 표시로 바꾼다. 실패·타임아웃·부분 응답이면 미소비 유지 | §확인 모드 응답 완전성 계약("확인 예산을 소모하지 않는다")과 동형 |
| **카운터** | 폴백② 라운드는 **`확인 소진`을 올리지 않는다**(예약분이므로) | `SKILL.md:328` §2j 표가 "완전한 확인 응답 → `확인 소진++`"이라, 그대로면 2/2에서 **3/2**가 된다. 복귀 재진입 확인이 이미 받는 예외와 같은 취급 |
| **재승인** | 소비 후에는 **폴백②를 다시 제시하지 않는다** — 남은 선택지는 폴백①·③ | 미규정이면 같은 라운드를 무한 재승인할 수 있다 |

- "복귀가 폴백보다 우선한다"(§확인 모드 결과 처리)이므로 복귀 예약분과 폴백② 예약분은 **한 루프에서 둘 다 소비될 수 있다** — 그래서 유계가 9가 아니라 10이다.

**D29. 종료 경로의 clean 확인도 `.remember/`를 제외한다.**

- `§0` 스냅샷 대조는 이미 `.remember/`를 통째로 제외한다(`SKILL.md:210`). 그러나 **§3의 "커밋하고 clean을 확인한다"와 D26 순서 1의 clean 확인에는 그 제외가 없다.** `.remember/`를 추적하는 repo에서는 루프 파일의 **생성**(D25·D26 순서 2)과 **제거**(D18)가 커밋되지 않은 변경으로 남아 그 clean 확인을 깨뜨린다 — 비추적 repo에서는 애초에 보이지 않으므로 **추적/비추적 동작이 실제로 갈린다.**
- 따라서 §3·D26의 clean 확인은 `§0`과 **같은 제외 규칙**을 쓴다. 루프 파일은 리뷰 대상 산출물이 아니라 **루프 자신의 상태**이므로 어느 검사에서도 clean 판정 대상이 아니다.
- 이것은 `.gitignore` 정책(§3 비목표)을 **바꾸지 않는다** — 추적 여부는 여전히 각 repo 소관이고, 이 규칙은 루프의 clean 검사 대상만 정한다. 조건부 커밋을 넣는 안은 채택하지 않는다(추적 repo에만 도는 분기가 생겨 G1·G2에 저촉).

**D18. 제거 시점 = §4의 `remember.md` 인계·보존 확인을 마친 뒤.** §3(종료 전 커밋)에는 "이 시점에 루프 파일을 제거하지 않는다"를 명시한다. 루프 파일 ④가 §4 인계의 1차 근거이므로(D21), 먼저 지우면 마지막 세션이 루프 초반 내용을 모르는 채 세션 컨텍스트만으로 인계를 써야 한다.

**D6. 루프가 `remember.md`를 건드리는 시점은 정확히 하나다.**

- **진행 중**(§2i 컨텍스트 핸드오프): `loop-*.md`만 쓴다. `remember.md` **무접촉** → F3의 사고 경로가 구조적으로 사라진다.
- **종결 시**(§4 단계 경계): 다음 단계·트랙 인계를 `remember.md`에 쓴다. **이 한 시점에만** 덮어쓰기 전 **기존 내용 보존 확인**을 건다(C-4 원안의 "보존 확인 1줄" 부활).
- 7a **D9 개정을 정밀화한다** — "보존 확인 불필요"는 *진행 중*에만 참이었다. 종결 쓰기가 남아 있는 한 F3 경로는 완전히 닫히지 않으므로, 접촉면을 1시점으로 줄인 뒤 그 지점에 보존 확인을 남긴다.

**D19. 보존 확인의 형태 = 지시 1줄.** 문면은 "덮어쓰기 전 기존 `remember.md`를 읽고, 이번 루프가 갱신하는 부분 외의 섹션(승계 관례·백로그·하네스·다른 트랙 항목)은 그대로 보존한다" 수준으로 둔다. 기존 섹션 열거·쓰기 후 재확인 같은 출력 절차는 두지 않는다 — 판단 주체가 LLM이고 **읽기를 강제하는 것만으로 F3(전체 덮어쓰기) 경로가 닫힌다.** 실측 사고 1건 위에 기계장치를 쌓지 않는다(G1·G2).

### 복원

**D7. `--resume` 대상 선택 = `.remember/loop-*.md` 조회.**

| 발견 수 | 동작 |
|---|---|
| 0개 | **자동 감지**: 새 루프(적대 소진 0 · 확인 소진 0 · 빈 ledger · 적대 모드) · **명시적 `--resume`**: **fail-closed 사용자 확인** |
| 1개 | `--phase`가 명시됐으면 파일명의 `<phase>`와 대조 — **불일치면 fail-closed 사용자 확인**. 일치하거나 `--phase` 생략이면 복원하고, **§1 사전 게이트에서 ⓐ 확정한 phase 산출물 문서 ⓑ 변경 내용으로 독립 추론한 phase 둘 다를** 복원값·파일명과 대조해 어느 하나라도 불일치면 fail-closed |
| 2개 이상 | **fail-closed 사용자 확인** (파일명이 트랙과 phase를 함께 보여주므로 선택이 결정적이다 — D4) |

`§0` 스냅샷 대조(branch·HEAD SHA·base SHA·clean tree)는 **현행 그대로** 유지한다. 텍스트 경계 파싱도, 저장값을 기대값으로 되쓰는 자기참조 대조도 없다. 위 대조 중 **선택 단계 몫은 파일명만** 보고 하고 **ledger 몫은 §1로 미루므로**, 어느 쪽도 `§0` 대조 목록을 바꾸지 않는다.

- **1개여도 무조건 복원하지 않는다.** `§0`이 보는 값은 branch·HEAD SHA·base SHA·clean tree뿐이라(`SKILL.md:210`) **다른 트랙·다른 phase의 루프 파일이 같은 스냅샷을 그대로 통과한다.** 실제 창: 트랙 A의 spec 루프가 ESCALATE 중단으로 끝난 뒤 사용자가 커밋 없이 트랙 B의 spec 루프를 시작하면 branch·HEAD·base·clean이 전부 동일해 A의 ledger·예산 카운터가 B로 복원된다. planless 트랙에서 같은 HEAD로 `--phase impl`을 시작하는 경우도 동형이다.
- **D4의 phase 접미는 파일 *공유*를 막지 파일 *선택*을 막지 않는다.** 접미 덕에 파일명이 트랙과 phase를 정확히 보여주므로, 대조는 파일명 비교 1줄로 끝난다.
- **기대값은 두 단계로 나눠 산출한다** — 이것이 검사가 무력화되지 않게 하는 핵심이다. 파일 선택 단계에서 **독립적으로 알 수 있는 값은 호출자가 준 `--phase`뿐**이므로 그것만 대조한다(생략되면 이 단계의 대조도 생략). ledger 문서의 기대값은 **§1 사전 게이트가 이미 확정하므로**(§finding ledger 위치 규정 — spec은 spec 문서 말미, plan·impl은 plan 엔트리포인트 말미, planless는 spec 문서 말미) 복원 직후 §1에서 대조한다.
  - 이 분리가 없으면 구현자가 **발견한 파일명을 그대로 기대값으로 재사용**해(자기참조) 검사가 항상 통과한다. §1의 확정은 파일이 아니라 **작업 트리의 phase 산출물 문서**에서 나오므로 독립적이다.
  - 오복원이 §1까지 진행된 뒤 잡히지만 **리뷰를 한 번도 돌리기 전에 멈추므로 피해가 없다** — §1은 게이트다. 그 대가로 `§0`에 ledger 확정 규칙을 중복 서술하지 않는다(G1·G2).
  - **§1 대조는 ledger 문서만으로는 부족하다 — phase도 함께 본다.** `--phase`가 생략되면 선택 단계 대조가 통째로 스킵되는데, **planless 트랙은 spec·impl ledger가 같은 문서**라(D4의 실측 3건: 7a·7b·C-6) ledger 문서 대조도 함께 통과한다. 그러면 `loop-…-spec.md`가 남은 상태에서 impl을 자동 감지할 때 **앞 phase의 모드·예산·미확인 FIXED 큐가 그대로 주입된다** — D4가 phase 접미로 막으려던 바로 그 사고가 자동 감지 경로로 되살아난다. §인자가 이미 "`--phase` 생략 시 **변경 내용으로 추론**"을 규정하므로, 그 추론값은 루프 파일과 무관한 **독립 기대값**으로 쓸 수 있다.
  - 추론이 빗나가면 fail-closed가 헛발화하지만, 그 결과는 **사용자 확인 1회**라 복구 가능하다 — 조용한 오복원보다 낫다.
- **0개 분기는 호출 방식으로 갈린다.** 자동 감지에서 0개는 "미완 루프가 없다"는 정상 상태다. 그러나 사용자가 **명시적으로 `--resume`을 걸었다면 재개할 루프가 있다고 믿고 있다는 뜻**이라, 조용히 새 루프로 시작하면 예산·모드·미확인 FIXED 큐가 0인 상태로 재시작해 §2e **빠른 종료까지 갈 수 있다**(ledger 본문은 phase 산출물 문서에 남지만 루프가 그것을 모른다). 조회 실패 원인은 대개 cwd·브랜치·경로 오류라 사용자에게 물으면 즉시 드러난다. 이 분기는 **자동 감지 경로를 바꾸지 않으므로 D20과 무충돌**이다.
- 이 단서는 **D20이 배제한 "정상 감지 시의 사용자 확인"을 되살리는 것이 아니다.** D20의 근거는 "오복원은 `§0` 스냅샷 대조가 fail-closed로 막는다"인데, 그 목록이 실제로 덮지 못하는 계열이 위 창이다 — 근거가 의도한 fail-closed가 성립하도록 대조 대상을 맞추는 것이고, 일치하는 정상 경로에서는 여전히 아무것도 묻지 않는다.

**D20. 자동 감지 경로도 같은 조회를 쓴다.** `SKILL.md:208`의 "`--resume`이거나 `.remember/remember.md`에 미완 상태가 있으면 복원한다"에서 **조회 대상만** `.remember/loop-*.md`로 바꾼다(위 3분기 적용 — 0개는 **자동 감지 쪽 분기**인 새 루프, 1개는 `--phase`가 없으므로 §1 대조가 받는다). 근거 ① `--resume` 실사용 0건이라 자동 감지가 사실상 유일한 재개 경로이고, 이를 없애면 미완 루프가 있는데 조용히 새 루프로 시작하는 경로가 열린다 ② 잘못된 복원은 fail-closed로 막는다. **감지 시 별도의 사용자 확인은 두지 않는다** — 대조가 같은 일을 기계적으로 하고 있어 중복이다.

- 근거 ②는 **`§0` 스냅샷 대조 단독으로는 성립하지 않는다**(D7 단서에서 정밀화). 그 목록에 phase·ledger가 없어 같은 스냅샷의 다른 트랙·phase 파일이 통과하므로, fail-closed의 한 축을 D7의 **2단계 대조**(선택 단계의 `--phase` · 복원 직후 §1의 ledger 문서)가 맡는다. **자동 감지에는 `--phase`가 없으므로 이 경로에서는 §1 대조가 그 축을 전담한다.** D20이 배제한 것은 *정상 감지 시의 확인 절차*이고, 그 배제는 그대로다.

**D8. 비소급 — 0.14.0 이전 형식(`remember.md` 안의 루프 상태)은 복원하지 않는다.** 전환기 1회성 문제를 영구 조항으로 만들면 시간이 지나 죽은 규칙이 된다(C-6 D8 비소급 전례). 대신 **릴리스 종료 보고에 1회 안내**한다 — 미완 루프가 있으면 사용자가 직접 `loop-*.md`로 옮긴다.

### 소유권·직렬화

**D9. 루프 파일은 그 루프를 도는 세션만 쓴다**(§2i에 1줄). 재읽기·비교·락 같은 기계장치는 두지 않는다. 근거 ① 같은 트랙 루프의 동시 실행은 이미 review-loop 규약 위반이고, 그 상황에선 핸드오프보다 **같은 브랜치의 상호 커밋·ledger 분기**가 먼저 터진다 ② 수신 측 방어가 이미 있다 — `§0` 스냅샷 대조가 branch·HEAD·base·clean tree 불일치를 fail-closed로 잡으므로 stale 상태로 **재개하는** 경로는 막혀 있다 ③ 실측 0건 ④ 매 쓰기마다 절차를 붙이면 G1·G2에 저촉된다.

**D10. 미해결 ledger 섹션의 원 지적 원문은 코드펜스 안에 넣는다**(§2i에 1줄). 원문에 줄머리 `##`가 있어도 섹션 경계로 오인되지 않는다. 이 이상의 escaping 규약은 두지 않는다 — 복원 주체가 파서가 아니라 **LLM**이고, 이 repo가 이미 문면화한 원칙(`SKILL.md:277` "문서의 문자적 논리 갭은 실행 영향으로 severity 재평가 — 문자적 갭 ≠ 즉시 high")이 정확히 이 경우다. 실측 충돌 사례 0건이며, 그 조항의 단서("닫는 수정이 저비용이면 반영한다")에 따라 **1줄만** 반영한다.

### 파급·적용

**D11. 훅 넛지 문구에 단서 1줄을 붙인다** — `context-threshold-hook.mjs:85~86`은 **모든 세션**에 `.remember/remember.md`를 지시하므로, 루프 세션이 그대로 따르면 D6의 무접촉 규칙과 충돌하고 F3 경로가 훅을 통해 되살아난다. 비-루프 세션의 안내는 그대로 두고 "review-loop 실행 중이면 그 스킬의 핸드오프 규정을 따른다"만 덧붙인다.

**D12. 적용 시점 — 이 트랙 자신의 review-loop는 개정 전 규격(0.13.0)으로 돈다.** 개정은 **0.14.0 설치 이후 시작하는 루프**부터 발효한다. C-4는 자기참조 트랙이라(고치는 규격을 자기 루프가 사용한다) 못박지 않으면 4·8단계 루프가 개정 중인 문면을 따라가 상태가 섞인다.

- 물리적으로는 이미 분리돼 있다 — 실행되는 스킬은 **설치본**(`~/.claude/plugins/cache/claude-dev-workflow/dev-workflow/0.13.0/skills/`)에서 로드되고, 이 트랙이 고치는 것은 **작업 트리**의 원본이다. D12는 그 분리를 문면으로 확정해, 루프 중 "새 규격대로 하자"는 판단이 끼어들지 않게 한다.

### 승계 (7a 확정분 — 재논의 대상 아님)

**D13.** 4섹션 명칭은 ops-hub 런북 원문을 그대로 쓴다(7a D12 승계).
**D14.** ③ 미해결 ledger는 **ledger 전체**(단일 원본 위치 참조 + 루프 직접 판정 표시) + 미확인 FIXED 큐 + 미판정 blocking을 담는다. ③을 "큐 + 미판정"으로 좁히면 §0 복원 필드와 §2i 핸드오프 필드가 **동일 목록**이라는 계약이 문면에서 깨지고, FIXED 큐가 비었는데 루프 직접 판정만 있는 상태에서 재개 세션이 감사 없이 빠른 종료한다(7a D22 승계).
**D15.** 빈 섹션은 생략하지 않고 "해당 없음"을 적는다 — ②는 spec phase·planless 트랙에서 빈다(7a D11 승계).
**D16.** ledger 본문의 단일 원본은 phase 산출물 문서 말미이고, ③은 그 **위치와 루프 직접 판정 목록**을 담는다(복제 금지와 무충돌).

**D21. 4섹션 명칭은 루프 파일에만 강제하고, 기존 문서는 비소급이다.** `## 현재` / `## task 진행` / `## 미해결 ledger` / `## 다음 액션`은 **루프 파일의 공식 명칭**이며, 공유 `remember.md`와 기존 `archive-*.md`의 변형(`## 다음 단계 — …` 등)은 소급 개명하지 않는다(D8·C-6 D8의 비소급 전례와 동형). 실측상 ④는 `## 다음 액션` 3건 + 변형 다수라, 비소급을 적지 않으면 D13이 기존 파일 전부를 비준수로 만든다.

- **④의 내용은 7a 원문대로 "재개 명령 + 다음 단계·트랙 지목"을 유지한다.** D18로 루프 파일이 §4까지 살아 있으므로 ④는 `remember.md` 인계의 **1차 근거**가 된다 — 트랙 지목이 두 파일에 나타나는 것은 복제가 아니라 인수인계 경로다.

### 범위 방어

**D22. 미완 루프 잔존을 별도로 노출하지 않는다.** D7의 fail-closed 시점 외에는 루프 종료 보고·`setup`·`doctor` 어디에도 `loop-*.md` 잔존 개수를 싣지 않는다. 근거 ① 잘못된 재개 경로는 이미 fail-closed로 닫혀 있어 노출은 안전이 아니라 편의다 ② 실측 발생 0건 ③ 종료 보고에 상시 점검 항목을 더하는 것은 G1·G2에 저촉되고, `doctor`까지 넓히면 그 스킬 문면 변경에 별도 writing-skills TDD가 붙어 트랙 범위를 넘는다.

**D17. 다중 머신 git 동기 환경을 전제한 방어는 넣지 않는다.** 이 repo의 `.remember/`는 심링크로 `claude-memories` git repo를 가리키고 3머신이 병렬 push하지만, 그것은 **작성자 개인 인프라**이지 이 플러그인 사용자 일반의 조건이 아니다. 그 전제로 blocking ①을 설계하면 범용 규약에 개인 환경 종속이 들어간다. 확인 근거: `dev-workflow/` 전체에 `ops-hub` 문자열 **0건**(산출물 무종속). 실측 표본이 ops-hub 한 곳이라는 사실은 **근거의 한계**로만 기록한다.

- **예산 = 5 arm × 3그룹 × 10런 = 150런**(D23, 2026-08-10 재판정). 배치 직전 모델 주간 잔여 확인 → 부족하면 **L-1·L-4 우선** 분할.
- **복합 픽스처 원칙 — L-3·L-4·L-5는 각각 매 run이 자기 사례 전부를 답한다.** 재는 축이 arm 안에서 하나이므로 새 arm은 아니지만, **사례별로 10런을 쪼개면 각 2~4회 관측이라 D23이 정한 셀당 10런 하한과 정면으로 모순된다** — 한 사례가 항상 실패해도 다른 사례와 합산돼 GREEN으로 보인다. 복합 픽스처면 10런으로 **각 사례를 10회 관측**하므로 150런 예산 안에서 하한이 지켜진다(예산 재론 아님 — D23 확정분 유지).
- **사례별 판정은 독립적으로 낸다.** 한 run의 응답에서 사례마다 따로 채점하고, arm의 GREEN은 **모든 사례가 각각 통과**할 때만 성립한다. 합산 점수를 쓰지 않는다.
- **L-4의 `cur` 기대를 세 경로에 하나로 일반화하지 않는다.** 현행 §2i는 컨텍스트 경로에 대해 이미 "**핸드오프 전 커밋으로 clean tree를 만든다**"(`SKILL.md:318`)라고 규정한다 — 즉 그 경로의 `cur`은 커밋을 먼저 한다. 세 경로를 "핸드오프 먼저, 커밋 나중"으로 묶으면 **baseline 계약이 실제 0.13.0 동작과 어긋나** 측정이 무효가 된다. 경로별 실패 사유를 위 표대로 따로 둔다.
- **각 arm이 덮는 결정**: L-3(5사례) = D7 3분기 + 2단계 대조(자동 감지의 ledger·**phase** 두 축) · L-4(4사례) = D25·D26을 유지 3경로 전부에서 + **D29**(tracked `.remember/`) · L-5(3사례) = D27 + D28(우회·잠금·**불완전 응답 시 미소비**). 이렇게 배치해야 AC3·AC4·AC5가 문면 확인이 아니라 실측으로 확인된다.
- **사례 수가 늘어도 arm·런 수는 불변이다**(5 arm × 3그룹 × 10런 = 150런, D23 확정분). 복합 픽스처는 한 run에서 자기 arm의 전 사례를 답하므로, 사례 추가는 **런 수가 아니라 각 run의 응답 길이**를 늘린다.
