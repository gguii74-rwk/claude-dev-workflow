## 1. 문제

1.2.0 `orchestrate` 스킬은 2026-10-17~18 메인 세션 운영 실측 1일분(트랙 10여 건)과 spec→plan→impl 적대검증에서 드러난 결함을 반영해 릴리스됐다. 그 과정에서 범위 밖으로 미룬 빈자리와, 오르카 내장 `orchestration` 스킬이 이미 규약으로 갖고 있는 것 중 우리 운영에도 바로 맞는 작은 항목이 남았다(메모리 `dev-workflow-1-2-0-followups`).

**(a) 오르카 미설치 환경의 동작 미정의.** SKILL.md 시작 자가 점검은 메인의 `DEV_WORKFLOW_MODE`만 본다. 오르카 CLI가 없는 머신(또는 `ORCA_CLI_COMMAND`가 잘못 가리킬 때)에서 「트랙 띄워」라고 하면 ① 기동 5의 `orca terminal create`가 실패하거나, 스크립트가 `ERR orca 실행 실패: spawnSync orca ENOENT`(exit 2)로만 멈춘다 — 멈추는 쪽이라 안전하지만 다음 행동(이 스킬을 쓰지 말고 단일 세션으로 진행) 안내가 없다. 효과 2(review-loop·dev-cycle의 위임 자동 채택)는 `DEV_WORKFLOW_MODE`만 보므로 오르카와 무관하다(변경 없음).

**(b) 기동한 트랙의 실제 모델을 확인하는 절차가 없다.** 트랙 모델은 기동 명령의 `--model`로만 정한다(D14). 그런데 기동 뒤 실제로 그 모델로 떴는지는 절차에 없고, 이 트랙(10-18)에서 메인은 손으로 화면을 읽어 「모델 `claude-fable-5-1`(화면 확인 Fable 5.1)」을 핸드오프 블록에 적었다. 오르카 `orchestration`은 `launch.requested`와 `launch.effective`를 대조하고 「요청 인자만으로 모델을 주장하지 말라」고 못 박는다(coordinator-loop) — 우리는 `terminal create --command`로 띄우므로 그 필드가 없고, 화면이 유일한 근거다.

**(c) 단계 종료 뒤 트랙 터미널의 처분이 절차에 없다.** ④ 단계 종료는 검증·대장·핸드오프·정지까지만이고, DONE 뒤 트랙 터미널을 닫는지 두는지는 메인 재량이다(⑤-1은 HANDOFF 후계 때의 옛 세션 종료만 정한다). 오르카 `orchestration`은 정착한 워커마다 「재사용 · 유지(사유) · 해제」 중 하나를 반드시 결정하고 그 결정이 없으면 코디네이터 턴을 끝내지 않는다(Completion accounting). 우리 운영에서도 이 트랙 직전 메인 교체 때 「옛 메인 `/exit`·close 완료」를 핸드오프에 적어야 했다 — 기록 자리가 없다.

**(d) 트랙 프롬프트에 편집 가능 범위와 완료 증거가 없다.** 템플릿 §4 「진행 범위」는 「할 일과 끝 지점」만 묻는다. 오르카 Task-spec 5요소(Target·Change·Constraints·Ownership·Observable acceptance) 중 Ownership(무엇을 편집해도 되는가)과 Observable acceptance(완료를 증명하는 관찰 가능한 증거)가 없어서, ④ 체크리스트 (d) 「diff가 spec 대상 파일 안」은 spec이 없는 단계(브레인스토밍·harden)에서 기준이 없고, 완료 증거는 트랙 보고의 산문에 맡겨진다.

**(e) SKILL.md 분량 상한에 여유가 없다.** 1.2.0 M3 「≤ 15KB(15,360B)」에 현재 15,358B(여유 2B). impl R4-1 때도 1구절을 넣느라 15,358B까지 눌러 썼다. 위 (a)(b)(c)는 SKILL.md 문면 1줄씩이라 상한을 넘는다.

**범위 밖으로 남는 것(§7)** — 워크트리 기본 절차·병합 순서 · 종료 표지 성공/실패 필드(D27 변경) · 오르카 `orchestration` 구조 채택(`ask`/`worker_done`).

## 3. 설계

### 3a. 오르카 미설치 안내 (a — D3)

- **SKILL.md 「시작 자가 점검」**에 1줄 추가(기존 `DEV_WORKFLOW_MODE` 점검 앞): 셸로 오르카 CLI 유무를 본다 — `command -v "${ORCA_CLI_COMMAND:-orca}"`(스크립트 해소 규칙 M4의 앞 두 단 — `ORCA_CLI_COMMAND` → `orca`. 개발 빌드 `orca-dev`는 `ORCA_CLI_COMMAND=orca-dev`로 지정해 쓴다 — 셸 줄을 M4 3단 전부로 늘리지 않는다, harden 재확인 후보). 비면 「오르카 미설치 — `orchestrate`는 오르카 터미널이 전제라 이 머신에서 쓸 수 없다. 이 세션에서 그 단계를 직접(단일 세션) 진행하라」를 1줄 안내하고 **멈춘다**(AskUserQuestion 없음 — 선택지가 없다).
- **스크립트 `orca()`**: `r.error.code === 'ENOENT'`면 `Fail('오르카 CLI 없음(<해소된 이름>) — orchestrate는 오르카 없이 쓸 수 없다: 트랙을 띄우지 말고 단일 세션으로 진행하라')`. 그 밖의 실행 실패는 현행 `orca 실행 실패: <message>` 유지. 모든 서브커맨드(`watch`·`alive`·`key`)가 같은 경로를 지나므로 자가 점검을 건너뛴 메인에게도 같은 안내가 간다(exit 2 — 종료로 오판되지 않는다, 1.2.0 plan R5-1 규칙 유지).
- 테스트: `ORCA_CLI_COMMAND=<존재하지 않는 이름>`으로 `alive`(및 `watch`) 1회 → 첫 줄 `ERR 오르카 CLI 없음(…)` · exit 2.
- 1.2.0 AC1 「본문에 오르카 옵션 문자열 0건」 금지 목록은 그대로 통과한다(`command -v`·환경변수 이름은 오르카 옵션이 아니다). `${…:-…}` 형은 Claude Code 인자 치환 대상이 아니다(1.1.1 spec §1 실측).

### 3b. 기동 뒤 실제 모델 확인 (b — D4)

- **SKILL.md ① 기동 5**: 「idle 대기 → `alive` →」 뒤에 「**화면의 모델 표기를 읽어 `--model`과 대조**(다르면 포인터를 보내지 않고 사용자에게 보고·멈춤 — `/model` 전송 금지는 D14 그대로) →」 1구절. 화면 읽기는 orca-cli의 터미널 읽기(스크립트 아님 — 사람이 읽는 1회성 확인).
- **① 6 트랙별 블록**: 「모델 id」 → 「모델 id(화면 확인 〈표기〉)」. 후계·복구(⑤-1·⑤-5)도 같은 기동 명령으로 뜨므로 같은 확인을 한다(⑤ 문면 추가 없이 ① 5 준용 — 분량).
- 근거: 이 트랙 핸드오프 블록의 「모델 `claude-fable-5-1`(화면 확인 Fable 5.1)」 = 이미 하고 있는 일의 절차화. 오르카 `launch.requested/effective` 대조 원칙의 터미널판.

### 3c. 단계 종료 때 트랙 터미널 처분 (c — D4)

- **SKILL.md ④ 단계 종료**: 핸드오프 문단 앞에 1줄 — 「**트랙 터미널 처분**: 대장 처리·검증이 끝나면 **닫음**(기본 — ⑤-1 (a)(b) 순서: codex 잡 0 확인 → `/exit` → 셸 복귀 확인 → close) 또는 **유지(사유)**(번복 수정 대기 · 사용자 지시 등). 결정을 트랙별 블록 「처분」에 적는다.」 번복(D42)으로 단계가 미완료면 유지가 기본이다(트랙이 고쳐야 한다).
- **① 6 트랙별 블록**: 「처분」 항목 추가(값 = `닫음 (<날짜>)` | `유지 — <사유>` | `미정`(DONE 전)).
- 근거: 오르카 Completion accounting의 「정착한 워커마다 재사용/유지/해제 중 하나」 — 재사용은 우리 규약(단계 경계 = 새 트랙, ④)과 어긋나므로 닫음/유지 2택.
