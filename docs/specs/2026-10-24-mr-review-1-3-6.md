## 1. 배경 · 목표

1.3.5 설치본(어댑터 v1.1 — 공통 필수 렌즈 + 순서 분산 · 코드 주 검토자 = Codex)으로 **같은 head 의 큰 구현 MR 1건**(정식 트랙 · 24파일)을 2026-10-24 오전에 네 번째로 돌렸다(1.3.1 → 1.3.2 → 1.3.3 → 1.3.5, 같은 head). 네 실행을 나란히 놓으면:

- **핵심 결함**(기준선 결정 「조회는 남은 허용 상태와 상관없이 매번 비밀번호 요구」 vs 코드 = 남은 확인 상태만으로 개인정보 조회 API 가 응답)을 **Codex 2/4 · Claude 2/4 · 둘 중 하나라도 3/4** 만 잡았다. 1.3.5 실행은 Codex 깊이 표지가 정상(변경 24 중 12 언급 · 명령 38회 · `weak:false`)인데도 놓쳤다 → 깊이(1.3.5 ①)가 아니라 **「기준선 결정 ↔ 코드」 대조를 강제하는 출력이 없는 것**이 원인 가설.
- 같은 결함의 **`fixableInDesign`** 이 1.3.3(두 모델 모두 `no` → RETURN_TO_DESIGN)과 1.3.5(Claude 단독 `yes` → CHANGES_REQUESTED)에서 갈려 **검토자 1명의 한 단어가 판정 단계를 정했다**.
- 같은 사안을 두 모델이 다른 파일·제목·유형(DEFECT ↔ MISSING_EVIDENCE · MISSING_EVIDENCE ↔ FOLLOW_UP)으로 내 **지문(파일 + 정규화 제목)이 안 맞아 메인이 손으로 합쳤고**, 의도 대조표 34행 병합·검증 표 행 수 세기도 즉석 스크립트였다 — 팀원 공유를 앞두고 실행자마다 결과가 달라질 위험.
- **운영 함정**: 1.3.5 를 설치한 뒤 떠 있던 세션(/clear 포함)이 스킬 로더로 1.3.2 「Base directory」를 띄웠다(mr-review·orchestrate 둘 다). 모르고 돌리면 고쳐진 결함이 그대로인 옛 버전으로 리뷰한다.

메인이 정리한 개선점 7건 중 ⑤(다른 저장소 사본 파일을 어댑터가 모름)는 프로젝트 어댑터 v1.3 으로 처리돼 범위 밖이고, 사용자가 이번 범위를 **①·②·⑦ + ③**(Q1 — D113)으로 정했다. ④(위키 발췌 관련성)·⑥(리포트 중복 문장)은 비목표(후속 후보). 우선순위 = ① > ② > ⑦ > ③(③ 은 ① 의 「사안 키」와 같이 설계해 비용이 작다).

예시는 전부 가상 값이다(프로젝트 `alpha` · MR `!66` · head `e5e5e5e` · 기준선 1차 spec `docs/specs/2026-10-06-account-verify-design.md`(결정 D1·D3) · 2차 spec `docs/specs/2026-10-12-info-download-design.md`(결정 D4) · 코드 `src/main/java/com/example/alpha/account/AccountController.java:357`). 이 저장소는 공개 repo 다(D10) — 리뷰 대상 프로젝트·저장소 이름·호스트·사람 이름·계정은 spec·코드·테스트 어디에도 적지 않는다(SC-7 T6). 실행 수치(4회 · 2/4 · 24파일 · 12 언급 · 38회 · 34행)는 그대로 쓴다(프로젝트 식별이 아니다).

**목표**

- G1(①). 검토자 출력에 **기준선 결정 대조표**(`decisions`)가 생겨, 기준선 문서의 결정 항목마다 지켜짐(KEPT)/어김(VIOLATED)/모름(UNKNOWN) + 코드 위치를 **빈칸 없이** 내게 한다 — 의도 대조표(`intent`, 검증 표 행 기준)와 같은 방식. 결정 목록은 **스크립트가 기준선 원문에서 뽑아 번호를 매긴다**(두 검토자가 같은 번호 목록을 본다 → 번호로 병합). 판정 계산 불변(대조표는 판정 입력이 아니다 — 어김은 검토자가 finding 으로도 낸다, 어김인데 finding 이 없으면 메인이 코드로 확인해 결과를 정정하거나 출처 `main` 발견을 추가하고, 남은 어김은 `verdict` 가 입력 검사로 막는다 — D124).
- G2(②). **단독 출처**(한 모델만 잡은) 차단 DEFECT·DESIGN_DRIFT 의 `fixableInDesign` 은 「검토자 1명의 주장」으로 다뤄 **메인이 코드·기준선으로 판단**하고, 못 하면 지금의 상충 처리와 같이 「판정 미확정」 3갈래로 리뷰어에게 간다. 스크립트도 스킬도 엄한 쪽을 자동 선택하지 않는다(D9 불변).
- G3(③). 검토자 출력에 **사안 키**(`decisionIds` · `intentRows`)를 넣고, 새 서브커맨드 **`merge`** 가 두 결과를 결정적으로 합쳐 `findings.json` 초안을 쓴다. 사람 판단이 필요한 칸만 `needsMain` 으로 남겨 메인이 채우고, `verdict` 는 미처리 항목이 남아 있으면 `ERR`(fail-closed). 제목 유사도 병합은 하지 않는다(1.3.5 비목표 ⑦ 유지 — 키로 해소).
- G4(⑦). 스킬 §0 전제 확인에서 **띄운 스킬 폴더(`${CLAUDE_SKILL_DIR}` 치환값 — D144) ↔ 설치 기록(`installed_plugins.json`) 불일치**를 검사해 다르면 **멈추고** `/reload-plugins` → 세션 재시작을 안내한다(D145). mr-review 만(다른 스킬 공통화는 후속 트랙).

`review-claude.json`·`review-codex.json`(**`--valid` 에 적힌 검토자의 파일만, 그중 `validateReview({ head, reviewer })` 를 다시 돌려 통과한 것만** — 실패·파일 없음은 `validReviewers` 에서 빼고 둘째 줄 `invalid:`). **`--valid`(필수 — R4-1, `findings.json` 을 쓴다**(R4-2 — 삭제 실패면 `ERR` 로 멈추고 `findings.json` 은 그대로 둔다: 쓰기와 삭제 사이에 중단돼도 새 발견 + 옛 판정 조합이 남지 않는다) — 재병합 뒤 `verdict` 가 `ERR` 로 끝나거나 건너뛰어도 `render` 가 옛 판정(예: APPROVE)을 새 발견과 함께 렌더하지 못한다(현행 `render` 는 `verdict.json` 없음 = 리뷰 실패 렌더, `report.mjs:363`). 같은 이유로 **`cmdVerdict` 가 `ERR` 로 끝나면**(검증 실패 · `needsMain` 미처리 · 결정 어김 대응 없음 · `--resolve` 오류 모두) 그 W 의 `verdict.json` 을 지운다(fail-closed — 다음 `render` 는 `verdict` 를 다시 돌리기 전까지 리뷰 실패). **출력 입구 한 곳(R3-2 — 추천 자동 채택(위임))**: `merge` 가 stdout 에 쓰는 모든 줄(첫 줄·둘째 줄 이하·`ERR` 문구)은 **하나의 출력 함수**를 거친다 — 줄마다 원문 가림(어댑터 `mask` + `SECRET_MASK`) → 줄바꿈 평탄화(D84 집합 → 공백) → 다시 가림(`report.mjs` `mline` 과 같은 순서 — 그 함수를 export 해 재사용) → 그 뒤에 줄 단위 절단·선택. 외부 유래 값(검토자 결정 id·파일 경로·제목·`invalid` 이유·`--same` 인자)을 조립 자리마다 따로 가리지 않는다(자리 목록 누락 방지 — D88 원칙의 출력 입구판).
3. **결정적 병합 규칙(입력 파일 순서·실행 환경 무관 — 같은 입력 = 같은 바이트)**:
   - 단위 = 각 검토자의 finding(배열 순). **같은 사안** = (가) 지문 같음(현행: `file` + 제목 소문자·공백·구두점 제거) ∨ (나) `decisionIds` 교집합 비어 있지 않음(`check.json.baselineDecisions` 에 없는 id 를 걸러 낸 **뒤**의 값으로 — 3.①-6, R5-2) ∨ (다) `intentRows` 교집합 비어 있지 않음(`--rows` 가 있으면 1~n 밖 번호를 걸러 낸 뒤) **그리고** `file` 같음(둘 다 `null` 아님 — 행만 같은 다른 파일 발견은 합치지 않는다, 검증 표 행 하나에 여러 발견이 걸릴 수 있다) ∨ (라) `--same claude:<i>=codex:<j>`(1부터 센 배열 번호). 같은 검토자 안의 두 발견은 합치지 않는다(모델 내 중복은 검토자 몫). 짝은 **1:1**(D136 — 전이 폐포 없음: 세 발견이 한 사안이어도 둘만 합치고 남는 것은 단독 + 후보). **짝 짓기는 강한 규칙부터 패스를 나눈다(D137)**: 패스 0 (라) `--same` → 패스 1 (가) 지문 → 패스 2 (나) `decisionIds` → 패스 3 (다) `intentRows`+같은 `file`; 각 패스 안에서 claude 배열 순으로 각 발견에 아직 짝이 없는 codex 발견 중 그 규칙에 맞는 첫 것(codex 배열 순)을 짝 짓고, 이미 짝 지은 발견(양쪽)은 다음 패스에서 다시 쓰지 않는다 — 배열 순서만으로 약한 일치가 강한 일치를 가로채지 않는다. 남는 발견은 단독(`source: claude|codex`).
   - 합친 값: `type` = 센 쪽(DEFECT > DESIGN_DRIFT > MISSING_EVIDENCE > FOLLOW_UP) · `confidence` = 높은 쪽 · `title`·`file`·`line_start`·`line_end`·`evidence`·`scenario`·`recommendation`·`lens` = **센 `type` 쪽**(같으면 claude) · 다른 쪽 원본은 `alt: { "<모델>": { type, title, file, line_start, evidence } }` 로 보존(부록 D 의 「(codex: MISSING_EVIDENCE 로 분류 — …)」 표지를 **렌더가 여기서 만든다** — 메인 메모 불필요) · `decisionIds`·`intentRows` = 합집합(정렬) · `fingerprint` = 대표 쪽 · `source: both` · `joinedBy: "same|fingerprint|decisionIds|intentRows"`(짝 지은 패스 이름 — 감사용).
   - `fixableInDesign`: **주장으로 세는 쪽 = 그 발견을 DEFECT·DESIGN_DRIFT(설계 유형)로 낸 검토자뿐**(D141 — MISSING_EVIDENCE·FOLLOW_UP 으로 낸 쪽의 yes/no 는 그 유형에서 뜻이 없어 비교에 쓰지 않는다). 합친 유형이 DEFECT·DESIGN_DRIFT 일 때: 설계 유형으로 낸 쪽이 둘이고 같은 값 → 그 값 · 둘이고 다름 → `null` + `fixableInDesignClaims` 두 주장 + `brokenPremise` = `no` 쪽(현행 §6-3 — `unresolved` 는 세우지 않는다, R2-2: `null` 자체가 미확정 표지) · **설계 유형으로 낸 쪽이 하나(단독 출처, 또는 `both` 인데 한쪽만 설계 유형) → `null` + 1인 claims**(3.② — 확신 무관 D127 · `unresolved` 없음, R2-2) · 합친 유형이 MISSING_EVIDENCE·FOLLOW_UP → 대표 쪽 검토자 값(claims `null`).
   - `blocking`: DEFECT·MISSING_EVIDENCE → `true` · FOLLOW_UP → `false` · **DESIGN_DRIFT → `null`**(어댑터 렌즈 「차단 승격」 조건은 산문이라 메인이 정한다 — `needsMain` 항목 「DESIGN_DRIFT 차단 승격 판단」, `validateFindings` 가 `null` 을 거부하므로 채우기 전 `verdict` 는 `ERR`). **유형 상충(D126 — 현행 §6-3 첫 문장 유지)**: `both` 쌍에서 한쪽 원본 유형이 FOLLOW_UP(비차단)이고 다른 쪽이 차단 유형(DEFECT·MISSING_EVIDENCE·DESIGN_DRIFT)이면 초안 값은 위 규칙대로(센 쪽) 두고 `needsMain` 항목 「유형 상충 — 한쪽 비차단: 코드·문서로 확인(확인되면 유지 · 반박되면 `blocking:false` + `dismissReason` · 못 하면 `unresolved:true`)」. 차단 유형끼리(DEFECT ↔ MISSING_EVIDENCE)는 상충이 아니다(자동). 단독 출처 `confidence: low|medium` 차단 후보(DEFECT·MISSING_EVIDENCE·DESIGN_DRIFT)는 현행 §6-3 대로 `needsMain` 항목 「단독 출처 낮은 확신 차단 — 코드로 확인(확인되면 유지 · 반박되면 `blocking:false` + `dismissReason` · 못 하면 `unresolved:true`)」 — 초안 값은 위 규칙대로 두고 **`unresolved` 는 바꾸지 않는다**(② 의 `fixableInDesign` 초안과 별개 — 둘이 겹치면 `needsMain` 2건이고, 표지도 따로다: 낮은 확신 = `unresolved` · 수정 가능 판단 = `fixableInDesign: null`, R2-2).
   - `intent`: `row` 기준(현행 §6-5 코드화 — D41 의 「`row` 병합」 그대로) · 둘 다 있는 번호: `result` 다르면 `UNKNOWN`, `basis` 는 「코드로 확인」이 하나라도 있으면 그것, `location` 은 「코드로 확인」 쪽(같으면 claude) · 한쪽만 → 그 값 · **`criterion` = claude 검토자 값, 그 행이 codex 에만 있거나 claude 값이 비어 있으면 codex 값, 둘 다 비어 있거나 없으면 고정 문구 `(행 n — criterion 없음)` + 둘째 줄 `criterionMissing: <행 번호들>`**(D143 — 고정 문구라 D88 평탄화 대상 아님)(Q9 — D122: D41·D67 「메인이 본문 첫 칸 원문을 읽어 적는다」 변경 — 메인은 손대지 않는다; `|`·줄바꿈은 현행 `cell()` 처리) · `row` 없는 항목 = 배열 순서 번호(현행) + 둘째 줄 `rowsMissing: <모델>` · `--rows <n>` 이 주어지면 1~n 밖·중복 번호를 버리고 둘째 줄 `rowsDropped: <모델>: <번호들>`(없으면 전부 유지 — n 은 메인이 세므로 선택 인자, D44 불변) · 행 순 정렬.
   - `decisions`: 3.①-6.
   - `baselineCandidateRelevant`: 유효 결과 전부 같으면 그 값(`baselineCandidateReason` = 「유효 결과 전부 일치」 또는 「단일 모델 값」) · 상충 → `null` + `needsMain` 항목 「후보 문서 관련성 상충 — 메인이 후보 문서를 읽고 판정(§6-4)」.
   - `id` = 합친 목록 순서대로 `F1`, `F2`, …(순서 = claude 배열 순 → codex 단독 배열 순) · `head_sha` = `snapshot.head_sha` · `validReviewers`·`crossChecked`(둘 다 유효) · `outsideWorktreePaths: []`(메인이 §5 경로 감시 결과를 채운다 — 현행) · `reviewerStats`(codex-stats.json 있을 때) · `coveredBy` 없음(메인 — 1.3.5 ④ 1b 그대로, `needsMain` 에 올리지 않는다: 기계 증거와 같은 사안인지는 제목 판단이라 메인 몫이고 빠져도 판정 불변).
