## 1. 배경 / 문제

dev-cycle은 0.1.0 이후 **읽기 전용 지도**로만 존재했다. ops-hub 전수 점검(브리프 §1·§트랙 C C-6 행)과 2026-08-08 재조사에서, 이 지도가 **실채택되지 않고**(①②) **지도 밖 구간에서 규약 이탈이 반복**(③)되는 것이 실측됐다.

**핵심 관찰 (브리프 서술의 정정):** 브리프는 ③을 "**소형** 트랙 파이프라인 통째 우회"로 적었으나, 실측상 우회는 **규모와 무관**했다 — 우회군에는 1 task 트랙과 **7 task 트랙(사후 수정 plan 유발)이 함께** 있다. 따라서 경량 경로의 목적은 "소형이면 건너뛰어도 된다는 승인"이 아니라 **우회의 하한선(어떤 트랙이든 최소 무엇은 남긴다) + 분기 기준의 명시화**다. 이 정정이 D1(분기 축 = 접촉 표면·가역성, 규모 아님)의 근거다.

## 2. 목표 / 비목표

**목표:** dev-cycle 지도를 **전 구간(착수 → 종료)** 으로 확장하고, **전부 아니면 무(無)** 이분법을 없앤다.

- ① **9단계 신설** — 통합·후속 검증(PR·머지·배포·실측)을 지도에 넣고, 각 repo 규약을 느슨 참조한다(D8~D10).
- ② **착수 브리프 생성 안내** — 트랙 착수 시 다음 세션에 넘길 브리프의 필수 항목을 지도가 안내한다(읽기 전용 출력, D12~D14).
- ③ **경량 경로(fast lane) 공식화** — 분기 축(D1)·입도(D2)·하한(D3)·승격(D4)·판정 주체(D5)를 규약화한다.

**비목표 (YAGNI / 기결정 준수):**

- **dev-cycle을 오케스트레이터로 만들기** — 현행 스킬 문면의 기결정("이건 읽기 전용 지도다", "한 세션에서 전 과정을 자동으로 돌리지 않는다")이자 ops-hub `docs/specs/2026-06-20-adversarial-review-loop-workflow-design.md:45`의 보류 결정("메가스킬은 깨지기 쉽다"). 확장해도 **파일을 고치지 않는 지도**라는 성격은 불변 — 착수 브리프도 출력만 한다(D12).
- **기계 검증 장치(파서·스위트·자동 게이트·훅) 신설** — 브리프 §기결정 대조(G1·G2) 준수. 9단계 완료 판정도 grep·`gh` 조회 수준을 넘지 않고, 불명확하면 사람에게 묻는다(D9).
- **PR·머지·배포 절차 자체의 규약화** — 9단계는 **repo 규약을 가리키는 포인터**다(D8). 절차 내용(머지 컨벤션·배포 명령·체크 항목 열거)은 각 repo AGENTS.md/CLAUDE.md 소유이며 이 스킬이 복제하지 않는다 — 중복 서술 = 드리프트(ops-hub CLAUDE.md:9의 자기 교훈).
- **dev-cycle 외 스킬 문면 개정** — `review-loop`(C-1~C-3)·`ui-mockup`(C-7)·훅(C-8)·`setup`(C-9)은 순번 7 범위. 이번 압박에서 드러난 두 접점도 **미수정으로 확정**했다: setup 마커 문구의 "큰 변경"(D11) · review-loop impl 게이트의 npm 고정(D7 — dev-cycle 안내로 처리).
- **superpowers 스킬 수정** — 외부 플러그인. 9단계는 `finishing-a-development-branch`를 **느슨 참조**만 한다(D10).
- **각 repo CLAUDE.md·AGENTS.md 수정** — 각 repo 소유. C-5 D8 전례대로 종료 보고 안내 1줄까지.
- **기존 트랙 소급 적용** — 지도는 착수 시점 안내다. 진행 중·완료 트랙을 경량/정식으로 재분류하지 않는다.
- **단계 경계 = 새 세션 + `/clear`** 규약 완화 — 정착 자산. 경량 경로는 *단계를 생략*할 수 있을 뿐 남은 단계의 경계 규약을 바꾸지 않는다(D2).
- **경량 경로의 산출물 서식 신설** — spec-lite는 **새 서식이 아니라** 기존 review-loop spec 게이트 6항목 + 재논의 금지 블록이다(D3). 별도 템플릿·전용 디렉터리를 만들지 않는다.

## 3. 설계 확정 (harden-spec 2026-08-08 · D1~D19 / spec 적대검증 루프 2026-08-08 · D20~D23 + D1·D16 보강)

### 경량 경로 (C-6③)

**D1. 분기 축 = 접촉 표면·가역성** — **스키마·마이그레이션·권한·인증·보안 경계·외부 연동·데이터 손상/유실·비가역 작업**에 닿는가로 판정한다. **task 수(규모)는 기준이 아니다.** (목록은 아래 근거가 인용하는 review-loop 기준과 **같은 어휘로 맞춘 것**이다 — 세션·토큰 검증 같은 인증 변경이나 데이터 정합성 변경이 목록 누락으로 경량에 빠지지 않게 한다. *spec 루프 R4 fp-S8*)
- 근거: §1 핵심 관찰 — 사후 수정 plan을 부른 것은 7 task 트랙이고 1 task 트랙은 무사고였다. 규모 기준은 실측에 반증된다. 이 어휘는 review-loop §1의 "보안 크리티컬 자가 판정"(권한·인증·보안 경계·데이터 손상/유실·비가역 마이그레이션)과 같은 신호를 쓰므로 두 스킬이 같은 축을 공유한다.

**D2. 입도 = 하한 고정 + 단계별 선택** — 경량은 정해진 생략 패키지가 아니다. **하한(D3)은 고정**하고 그 위 단계(spec 적대검증·plan·plan 루프)는 각각 생략할 수 있되, **생략할 때마다 spec의 `## 재논의 금지(기결정)`에 D번호로 근거를 남긴다.**
- 근거: 실증된 경량 운용은 두 형태다 — 이 repo의 "plan만 생략"(트랙 A·B·C-5)과 ops-hub 08-01~03의 "전부 생략". 고정 패키지로 묶으면 전자가 규격 밖(정식인데 plan이 없음)이 된다. 생략을 D번호로 남기는 것은 ui-mockup이 이미 쓰는 형태(ops-hub 3건 실측)라 새 장치가 아니다.

**D3. 하한 = spec(게이트 6항목 + D블록) + harden-spec + impl review-loop** — 어떤 경량 트랙도 이 셋은 생략하지 못한다.
- **spec 문서**: review-loop spec 게이트 6항목(목표·범위·비목표·결정사항·acceptance criteria·미해결 질문) + `## 재논의 금지(기결정)` 블록. **새 서식을 발명하지 않고 이미 있는 게이트를 재사용**하므로, 경량→정식 승격 시 그 spec을 그대로 spec 루프에 넣을 수 있다.
- **harden-spec**: D6가 "경량에서도 harden-spec은 하한"으로 확정한 것을 하한 목록에 명시한다. D블록 요구만으로는 갈음되지 않는다 — D블록은 손으로도 쓸 수 있어, harden을 실제로 돌리지 않은 트랙이 형식만 갖추고 통과할 수 있다.
- **impl review-loop**: 우회군 5건 전부 impl ledger 0이었고, 그중 유일하게 외부 리뷰를 받은 트랙이 사후 수정 plan을 낳았다.

**D4. 승격 = 접촉 표면이 드러나면 즉시** — 경량 진행 중 **D1의 접촉 표면(스키마·권한·인증·보안 경계·마이그레이션·외부 연동·데이터 손상/유실·비가역)** 이 새로 드러나면 그 자리에서 정식 경로로 올리고 spec에 사유를 기록한다. D1과 같은 신호를 쓰므로 별도 임계치를 두지 않는다(task 증식·라운드 초과 같은 진행 신호는 트리거가 아니다 — 규모 기준을 뒷문으로 되돌리지 않기 위함).

**D5. 판정 주체 = 지도 1차 판정 + 사용자 확인 1회** — dev-cycle이 접촉 표면 신호로 1차 판정하고 사용자에게 확인 1회를 받는다. review-loop §1의 "보안 크리티컬 자가 판정 — 확인 1회"와 같은 모양이다.
- **확인 실패 경로 = 정식 유지** *(spec 루프 R5 fp-S11)*: **사용자가 명시적으로 승인한 경우에만 경량으로 진입한다.** 거절하거나 답이 불명확하면 **정식 경로를 유지**한다 — 무응답·모호는 경량 승인이 아니다. 확인 절차를 두고도 실패 경로를 규정하지 않으면 문면이 스스로 경량을 확정해 spec 루프·plan을 생략할 수 있고, 그러면 D5의 안전장치가 형식만 남는다.
- 근거: 경량 오판정은 **검증을 건너뛰는 방향**의 오류라 비대칭적으로 위험하다. 확인 1회가 그 방향만 막는다.

**D6. harden-spec 무수정** — 경량 트랙에서도 harden-spec을 그대로 돌린다. lite 모드를 신설하지 않는다.
- 근거: harden-spec의 핵심 원칙은 "질문은 예산이 아니라 커버리지"다. 접촉 표면이 없는 트랙은 갭 대장 자체가 작아 **자연히 짧아진다** — 모드 없이도 경량이 성립한다. dev-cycle은 "경량이어도 harden-spec은 하한(D블록의 출처)"이라고 안내만 한다.

**D7. 비-npm repo의 impl 게이트 = dev-cycle이 갈음 안내** — review-loop impl 게이트는 npm 4종 고정이므로, "비-npm repo는 그 repo의 검증 명령 또는 writing-skills TDD GREEN 기록으로 갈음한다" 한 줄을 둔다. **배치는 8단계 안내에 경로 공통으로** — 경량·정식 **어느 경로에도 적용된다** *(spec 루프 R5 fp-S10 — 경량 절에만 두면 인증·스키마 변경으로 정식 판정된 Python/Go repo가 8단계에서 npm 게이트에 막혀, 이 트랙이 하한으로 못박은 impl 검증을 오히려 우회하게 된다)*. **review-loop 문면은 고치지 않는다**(순번 7 범위 보존).
- 근거: 이 repo 자신이 트랙 B·C-5에서 "writing-skills TDD GREEN 기록으로 갈음"을 이미 썼다(50 runs variance 0).

**D16. ui-mockup(3.5)은 경량에서도 생략 불가** — 화면을 만들거나 기존 화면 구성을 바꾸면 경량이어도 3.5를 돌린다(현행 §판별 3번 유지). 단 **화면 변경이 정식 승격을 부르지는 않는다** — 3.5만 추가된다.
- **생략 불가의 대상 = "경량 판정을 이유로 한 자동 생략"** *(spec 루프 R3 fp-S7 · 사용자 판정 2026-08-08)*. 사용자가 ui-mockup 진입 확인에서 **명시적으로 생략을 택하고 D블록에 기록한 경로는 경량 트랙에서도 그대로 유효**하다 — `ui-mockup/SKILL.md`의 생략 종료 경로와 `dev-cycle` 판별 3의 생략-record 소비는 **무수정**이다(비목표 유지). 근거: §5 UI 우회군 3건은 *생략 기록조차 없이* 우회한 것이라 사용자 명시 생략과 다른 현상이다. **사용자 선택 생략 자체의 타당성 재검토는 순번 7(C-7 ui-mockup)로 이월한다.**
- 근거: UI 우회군 3건(`user-management-ui-redesign`·`workflow-claims-list-consolidation`·`ui-design-system`) 전부 `## UI 설계` 절 0이고 `docs/design/`에도 없다. 그중 `ui-design-system`은 전사 디자인 체계 변경이었다. 반대로 화면 변경 전체를 접촉 표면(D1)에 넣으면 문구·색 수준 변경까지 정식으로 끌어올려 경량이 비게 된다(현행 3.5도 경미 변경은 건너뛰라고 규정).

**D17. impl ledger 위치 = plan이 없으면 spec 문서 말미** — 경량으로 plan을 생략한 트랙의 `## 적대검증 ledger (impl)`은 spec 문서에 신설한다.
- 근거: 이 repo가 트랙 B·C-5에서 이미 그렇게 했고 두 번 다 성공 종결했다. **순번 7(C-3)이 "impl ledger = plan 엔트리포인트 말미"를 규약화할 때 "plan이 없는 경량 트랙은 spec 문서"를 예외로 승계해야 한다** — 이 결정을 그 트랙에 넘긴다.

**D18. 9단계는 경로 무관 공통** — 경량 트랙도 PR·머지·배포·실측을 거친다. 경량은 *설계·검증 단계*를 줄이는 것이지 통합·배포를 면제하지 않는다.
- 근거: 우회군이 사후 수정을 부른 지점이 바로 PR 리뷰 이후 구간이었다.

**D19. 자기적용 = 이 트랙은 plan만 생략하고 spec 루프는 정식으로 돈다** — 이 트랙(C-6)은 D1 기준 접촉 표면 0이라 경량 판정 대상이며, D2의 단계별 선택에 따라 **plan·plan 루프만 생략**한다. spec 적대검증은 생략하지 않는다.
- 근거: 아직 검증되지 않은 규격을 그 규격 자신의 검증에 쓰는 순환을 피한다. 동시에 이것이 **경량 규격의 첫 자기적용 사례**로 기록된다(§8 관찰).

**D20. 생략 기록은 판별이 먼저 읽는다 — 경량 트랙을 생략한 단계로 되돌리지 않는다** *(spec 적대검증 루프 확정 · fp-S1)* — 판별 규칙은 산출물 부재(ledger 없음·plan 없음)를 미완으로 읽기 **전에** spec의 `## 재논의 금지(기결정)` D번호 생략 기록을 먼저 대조한다. 기록이 있으면 그 단계는 *미완*이 아니라 **해당 없음**으로 처리하고 다음 단계로 보낸다. 세부 3항:
- **planless 구현 경로**: plan을 생략한 트랙의 7단계는 plan 파일을 요구하는 `subagent-driven-development`가 아니라 **직접 구현(TDD)** 으로 안내한다.
- **승격 시 철회**: D4로 정식 승격하면 아직 수행하지 않은 단계의 생략 기록은 무효가 된다 — 승격 사유를 spec에 기록할 때 해당 생략 기록도 철회 표기하고, 이후 판별은 그 단계를 정상 요구한다.
- **기록 없는 부재는 생략이 아니다**: D번호 기록이 없는 산출물 부재는 종전대로 미완으로 읽어 해당 단계로 보낸다(경량 판정을 산출물 부재로 사후 추정하지 않는다).
- **하한에는 적용되지 않는다**: 생략 기록이 인정되는 대상은 D2가 열거한 생략 가능 단계(spec 적대검증·plan·plan 루프)뿐이다. D3 하한 3종에 대한 생략 기록은 무효이며, 하한 이행 여부는 D21이 별도로 확인한다.
- 근거: 현행 §판별 4는 ledger 미종결을 4단계로, 5는 plan 부재를 5단계로 되돌리고, 6→7의 SDD는 plan을 요구한다. D2가 허용한 생략을 판별이 소비하지 않으면 경량 트랙이 `/clear` 재개마다 생략한 단계로 회귀하거나 구현 단계에서 막힌다. planless 직접 TDD 경로는 이 repo가 트랙 A·B·C-5에서 세 번 완결한 실증 경로다. **D2 재론이 아니라 D2의 상태 전이 귀결을 명시하는 것이다.**

**D21. 하한 이행 가드 = 판별이 먼저 확인하고, 증명되지 않으면 사용자 확인으로 닫는다(fail-closed)** *(spec 적대검증 루프 확정 · fp-S4·fp-S5)* — D3가 하한을 정해도 하한이 지켜졌는지 볼 신호가 없으면 하한은 문구로만 남는다. **판별 순서 = ① D3 하한 3종 이행 확인 → ② D20 생략 기록 대조 → ③ 잔여 단계 판별.** 확인 신호는 grep 수준을 넘지 않는다(G-b):
- **spec 6항목**: 6항목(목표·범위·비목표·결정사항·acceptance criteria·미해결 질문)이 **내용으로 명시됐는지**를 본다 — **표제 문자열 일치가 아니다.** 표제는 문서마다 다르게 붙는다(이 spec만 해도 범위는 §2·§4에, 결정사항은 §3·재논의 금지 블록에, 미해결 질문은 §잔여 리스크·ledger 미해결 항목에 있다). grep은 후보를 찾는 보조일 뿐이고 판정은 해당 절을 읽어서 한다. 내용이 실제로 없으면 1–2 또는 3단계로 되돌린다. (C-5 impl fp-I2와 같은 계열의 교훈 — 형식 표지가 아니라 내용 기준.)
- **harden-spec**: `## 재논의 금지(기결정)` 블록 존재 **+ 그 블록에 D번호 결정과 근거가 실재**. 블록이 비었거나 실행 여부가 불명확하면 **사용자에게 harden 실행 여부를 확인 1회**(D5·D9와 같은 폴백) — 확인 없이 통과시키지 않는다. D블록은 손으로도 쓸 수 있어 harden 실행을 증명하지 못하므로, 증명 불가 지점은 새 기계 장치가 아니라 사람 확인으로 닫는다.
- **impl review-loop**: 구현이 완료됐는데 `## 적대검증 ledger (impl)`이 없거나 미종결이면 **9단계가 아니라 8단계**로 보낸다. plan을 생략한 트랙은 D17에 따라 **spec 문서 말미**에서 그 ledger를 찾는다(plan 문서 부재를 ledger 부재로 오인하지 않는다).
- **8→9 판별 순서**: 구현 미완 → **7** / 구현 완료 + impl ledger 부재·미종결 → **8** / impl ledger 종결 → **9**.
- 근거: 하한을 승격시켜도 진입 가드가 없으면 미하드닝 spec이 구현으로, 미검증 구현이 9단계로 흘러간다 — 이 트랙이 막으려는 우회(§1 ③)가 규격 안에서 재현된다. D3·D9를 재론하지 않고 그 하한·단계의 이행 신호만 정의한다.

**D23. 새 판별 규칙(D20·D21)은 소급하지 않는다 — 되돌림 확정 전에 사용자 확인 1회** *(spec 적대검증 루프 확정 · fp-S9)* — dev-cycle은 트랙 중간의 "다음 단계 뭐야" 요청에도 호출되므로, **0.11.0 이전에 착수해 새 규격의 D번호 생략 기록도 하한 증명도 없는 진행 중 트랙**이 업데이트 직후 harden·spec 단계로 되돌려질 수 있다. 그래서 D20·D21이 **되돌림을 확정하기 직전에** "이 트랙이 새 규격 이전에 착수한 것인지"를 사용자에게 **확인 1회** 받는다(D5·D9·D21과 같은 폴백 — 새 장치를 만들지 않는다). 기존 트랙으로 확인되면 **종전(0.10.0) 판별 규칙을 적용하고 새 하한 가드·생략 기록 규칙을 소급하지 않는다.**
- 근거: §2 비목표가 "진행 중·완료 트랙을 재분류하지 않는다"를 이미 약속했는데, D20 세부 ③(기록 없는 부재는 미완)과 D21 하한 가드는 그 약속과 무조건 충돌한다. 착수 시점은 조회로 확정되지 않는 외부 사실이라(spec 날짜는 착수 시점과 다를 수 있다) 버전 분기 대신 사람 확인으로 닫는다.

### 9단계 — 통합·후속 검증 (C-6①)

**D8. 범위 = PR·머지·배포·후속 실측 전부, 단 포인터로만** — 9단계는 트랙 종료까지를 지도에 넣되, 절차 내용은 각 repo 규약(CLAUDE.md/AGENTS.md)을 가리킨다. **체크 항목을 열거하지 않는다.** 배포가 없는 repo(이 플러그인 등)에서는 릴리스 + `/plugin update` 안내가 그 자리를 대신한다.
- 근거: ops-hub CLAUDE.md #4("트랙 종료 = push + PR + 머지 + 로컬 브랜치 삭제까지")·#7(ff pull·배포). 절차 복제 금지는 ops-hub 자신의 교훈(CLAUDE.md:9 — 중복 서술이 드리프트를 낳아 2026-08-02에 AGENTS.md로 통합).

**D9. 완료 판정 = PR merged + repo 규약이 요구하는 후속, 불명확하면 사용자 확인** — 배포·실측 여부는 repo 밖 사실이라 조회로 확정되지 않는다. 현행 §판별이 이미 "애매하면 사용자에게 확인"으로 끝나므로 같은 폴백을 쓴다.

**D10. 지목 스킬 = `superpowers:finishing-a-development-branch` + repo 규약 포인터 병기** — 9단계에 대응 스킬이 없다는 초안 전제는 사실이 아니었다(스킬 실재). dev-cycle이 1·7단계에서 이미 superpowers를 느슨 참조하므로 구조가 동형이고, "superpowers 미설치 시 대체 가능" 폴백 문면도 그대로 적용된다.

**D11. setup 미수정** — setup 마커 템플릿의 "새 기능·**큰 변경**을 시작하면"이 경량 트랙을 배제하는 것처럼 읽히지만, 이는 트리거 예시일 뿐이고 진입 후엔 dev-cycle 자신이 경량을 안내하므로 실해가 작다. 비목표(dev-cycle 외 스킬 개정 = 순번 7)를 지킨다. 종료 보고 안내 1줄로 대신한다.

### 착수 브리프 (C-6②)

**D12. 출력 형태 = 화면 출력만** — 항목 틀을 화면에 제시하고 파일은 만들지 않는다. "지도를 이유로 파일 수정 금지"라는 dev-cycle 기결정을 그대로 지킨다. 저장 여부·위치는 사용자 몫이다.

**D13. 필수 항목 = ops-hub 실증 5종** — 설계 결론 · 실측 근거 · 변경 대상 파일 · 검증 방법 · 완료 조건(PR 머지·배포까지). 마지막 항목이 D8(9단계 범위)과 자연히 맞물린다.
- 근거: ops-hub CLAUDE.md #9가 스킬 밖에서 발명해 쓰고 있는 목록 그대로 — C-1(런북 흡수)과 같은 패턴이다.

**D14. 발동 시점 = 트랙 착수 시 1회 + 핸드오프와 역할 경계 명시** — 단계 경계의 인계는 review-loop 핸드오프 소관임을 문면에 밝혀 중복을 끊는다. 둘은 다른 문서다 — **브리프는 착수용(설계 결론), 핸드오프는 재개용(루프 상태)**.

### 공통

**D15. 분량 상한 100줄** — 현재 56줄. 표 확장을 우선하고 신설 절은 2개(경량 경로·착수 브리프)까지. 상한 초과 시 내용을 줄이는 게 아니라 절을 통합해 줄인다. "한 화면에 들어오는 지도"라는 성격이 이 스킬의 자산이다.

**D22. dev-cycle description에 경량 트리거를 추가한다** *(spec 루프 R3 fp-S3 · 사용자 판정 2026-08-08)* — 현행 description은 "새 기능·다단계 변경" 중심이라 경량 경로의 대상인 **소형·단일 단계 변경에서 스킬이 로드되지 않는다**. 소형·단일 단계 변경의 **경로 판정 요청** 발화를 트리거로 1~2개 추가한다. **G-c 준수 — 트리거 예시만 늘리고 워크플로 요약은 넣지 않는다.** §7 AC로 문면을 확정하고, §6 GREEN에 "경량 트리거 발화로 dev-cycle이 선택되는가" 시나리오 1개를 **기존 하네스에 추가**한다(별도 discovery 하네스 신설 없음 — G-b).

## 6. 검증 계획 (D9 전례 승계 — writing-skills TDD)

브리프 §0-2가 요구하는 TDD. 트랙 A·B·C-5와 동형이며 실호출·실배포 대조는 불요(문면이 안내만 하므로).

1. **RED / 베이스라인** — 현행 0.10.0 dev-cycle로 재현한다: (a) 접촉 표면 없는 소형 변경 착수 시 지도가 8단계 전체를 요구해 우회를 유발하는지 (b) impl 루프 종결 후 "다음은?"에 9단계 안내가 없는지 (c) 착수 브리프 안내 부재.
2. **GREEN 마이크로테스트** — 개정판으로 **시나리오별 5+ reps · no-guidance 대조군 포함 · variance 0**. 시나리오:
   - 경량 판정 — 접촉 표면 없음(경량) / 스키마·권한 접촉(정식) 각 경계 케이스, 그리고 **7 task이지만 표면 접촉(정식)** · **1 task이지만 마이그레이션(정식)** 으로 규모 축 오염 여부 확인(D1). **인증·보안 경계 변경(세션·토큰 검증)** 과 **데이터 손상/유실 가능 변경**도 각각 정식으로 분류되는가(fp-S8 목록 보강분).
   - 하한 준수 — 경량 판정 후에도 spec 6항목+D블록·**harden-spec**·impl 루프를 요구하는가(D3·D6). **D블록만 있고 harden 미실시인 픽스처에서 3단계로 보내는가**(형식만 갖춘 통과 차단).
   - 생략 기록 재판별(D20) — spec 루프 생략 트랙 / plan+plan 루프 생략 트랙의 `/clear` 재개 시 **생략한 단계로 되돌리지 않고** 다음 단계로 보내는가, planless 트랙을 SDD가 아니라 **직접 구현(TDD)** 으로 보내는가. 승격(D4) 후 재판별에서 **철회된 생략 기록을 다시 인정하지 않는가**. **하한 3종에 붙은 생략 기록을 인정하지 않는가**(D20 하한 예외).
   - **자기적용 판별(D19·D21)** — **이 spec 문서 자신**을 입력으로 준 픽스처에서, 6항목 표제가 문자 그대로 없어도(범위·결정사항·미해결 질문 표제 부재) **내용 기준으로 완료 판정**하고 1–2·3단계로 되돌리지 않는가.
   - 하한 이행 가드(D21) — **spec 6항목이 내용으로도 1개 누락된** 픽스처에서 되돌리는가 · **D블록은 있으나 D번호 근거가 빈** 픽스처에서 3단계 또는 사용자 확인으로 가는가(무조건 통과 금지) · **구현 완료 + impl ledger 부재·미종결** 픽스처에서 9단계가 아니라 **8단계**로 보내는가(**일반 트랙 / planless 트랙 각각** — planless는 spec 말미 ledger를 찾는가) · impl ledger 종결 픽스처에서만 9단계로 가는가.
   - 승격 — 진행 중 스키마 접촉이 드러난 시나리오에서 즉시 승격 안내(D4).
   - 비소급(D23) — **새 D번호 기록도 하한 증명도 없는 0.11.0 이전 진행 중 트랙** 픽스처에서 되돌림을 확정하지 않고 **사용자 확인 1회**를 거치는가. 확인 결과 기존 트랙이면 종전 판별로 진행하는가.
