## 1. 배경 / 문제

세 마찰의 뿌리가 같다: **적대 리뷰어의 목적함수는 "공격"이라 몇 번을 돌려도 finding 0이 나오지 않는다.** (실측 근거는 전부 이웃 repo `../ops-hub/` 기준, 2026-08-07 점검.)

1. **확인 부채** (78개 파일) — max 5 도달 시 마지막 라운드 FIXED가 재확인 없이 다음 단계로 넘어간다. "max 도달" 계열 55개 파일 — 대부분의 트랙이 예산 5회를 소진하고 끝난다.
2. **churn** — 후반 라운드가 신규 영역·자기유발 결함(수정이 도입한 결함 계열 3회: cR2-B→cR4-A→cR5-A)으로 소모되고 score가 수렴하지 않는다. **7개 트랙 실측 전부 비단조**(예: 3→4→5→7→7→0). 적대 리뷰는 매회 전체 diff를 다시 보므로 절대 0은 도달 불가 — "2회 연속 비감소=정체" 규칙이 상시 성립 직전이다.
3. **오버엔지니어링 압력** — 적대검증자가 위협 모델 밖 기계 장치를 반복 요구한다(이 repo `docs/specs/2026-07-25-ui-mockup-skill-design.md` impl R2 관찰: "G1·G2 블록이 diff에 있어도 억제하지 않는다").

**확인 라운드의 가치 실증** (max 너머 수동 연장 사례):

- `../ops-hub/docs/plans/2026-07-31-content-ops-visibility.md:361` — max 도달 후 사용자가 확인 라운드 R6 선택 → R6가 iR5-F1의 불완전성(iR6-F1)을 실제로 잡음. R7이 파생 결함 1건 추가, R8이 소멸 확인. impl 총 9라운드.
- `../ops-hub/docs/plans/2026-07-18-report-knowledge-search.md:302` — cR6(새 세션 whole-branch)가 확인 부채 해소를 확정했는데, cR7이 다시 "cR6 수정이 도입한 unsatisfiable 게이트"를 발견. 이 트랙은 spec·plan·impl **3연속 확인 부채**.
- `../ops-hub/docs/plans/2026-06-23-teams-and-permission-matrix.md:198` — **보안 크리티컬 트랙**: R6→R8 연장이 critical(F-N)·데드락(F-P)·override in-tx(F-Q)·비활성 팀 경계(F-R)·배포 순서(F-T) **신규 5건**을 잡음. ⚠ "후반 라운드=확인만"이 보안 트랙에서는 위험함을 보여준다 — 탈출구·보안 예외(D5·D7)의 근거.
- 대조: SDD 내장 리뷰를 잘 돌린 트랙은 review-loop impl이 R1 종결(`../ops-hub/docs/plans/2026-08-05-report-weekly-meeting-view.md:120`) — C-1 SDD 연계 흡수(§5-3)의 근거이자 확인 생략 규칙(D8)의 전례.

## 2. 목표 / 비목표

**목표:**

1. review-loop의 리뷰 라운드를 **적대(발굴)/확인(중립) 2모드**로 나눠 — ① 마지막 FIXED의 재확인이 예산 안에서 구조적으로 보장되어 확인 부채가 사라지고, ② "신규 blocking 없음, 수정 확인됨"이 정당한 출력이 되어 종료가 자연스러워지며, ③ 확인 모드의 비례성 시각이 오버엔지니어링 요구를 거른다.
2. **(C-1)** ops-hub 런북의 범용 보완 4항(phase별 리뷰 입도·증분 base 안전조건·SDD 연계·codex 실행 팁)을 SKILL.md로 흡수한다.
3. **(C-2)** severity 재평가 지침(문자적 갭 ≠ 즉시 high)을 §2c 판정 절차에 넣는다.

**비목표 (YAGNI / 기결정 준수):**
- ESCALATE batch 기계장치 변경 — "무해라 유지"가 기결정(review-loop 0.2.0 회고). 건드리지 않는다.
- 기계 검증 장치(파서·스위트·자동 게이트) 신설 — 이 트랙은 **프롬프트/절차 수준 변경**이다(G1·G2 저촉 없음).
- codex companion 스크립트 자체 수정 — 다른 플러그인(openai-codex) 소유. 이 spec은 호출 방식만 정한다.
- 기결정 가드 focus-text 자동 주입 — 실행 순서 2번(트랙 B) 별도. 인터페이스 정합은 확인 완료: 적대 라운드는 어느 결정에서도 `adversarial-review` 경로를 유지하므로 트랙 B의 focus 주입 지점이 보존되고, 확인 라운드(task)는 ledger를 프롬프트에 직접 넣으므로 트랙 B와 자연 정합.
- 핸드오프 4섹션 승격·훅 재넛지·doctor 등 — 실행 순서 7번. 이 릴리스에 넣지 않는다.

## 3. 설계 확정 (골격 D1 + harden-spec 확정 D2~D11)

### 3-1. 2모드 정의 (D1 — 사용자 발의·승인 2026-08-07)

- **적대(발굴) 모드** — 현행 adversarial-review. 초반 라운드. 목적함수 = 공격(누락·결함 발굴).
- **확인(중립) 모드** — 후반 라운드. 목적함수 = **"머지 가능한가 판정"**. 확인 리뷰어에게 **ledger를 입력으로 주고 임무 4종**을 지시한다:
  - ① **미확인 FIXED 큐 전체**의 소멸 확인(sR2-F1 정밀화 — 통상 직전 라운드 FIXED와 일치하나, 부분 확인·복귀·resume 재개 후에는 과거 잔여분 포함. 큐 = §3-8 resume의 미확인 FIXED 목록과 동일 실체)
  - ② 수정이 닿은 영역 주변의 회귀 확인
  - ③ 루프가 직접 내린 판정(ACCEPTED/OUT_OF_SCOPE/**DEFERRED_TO_IMPL** — sR3-F1/**DUPLICATE** — R4-F2)의 비례성 점검(판정 감사). DEFERRED_TO_IMPL은 impl AC·테스트 연결의 존재·타당성 점검 포함. 루프 직접 DUPLICATE의 감사 = 원 fingerprint와의 의미적 동일성·원 disposition 확인만(오매칭 검출) — 원 기결정 자체의 재론은 금지(D9·기결정 가드 유지)
  - ④ 머지 준비도 verdict
  - **"신규 영역 발굴은 임무가 아니다. 단, 발견한 blocking은 보고한다"를 명시**(도장 찍기 / 사냥 재개 사이 균형).
- **탈출구** — 확인 라운드에서 blocking이 나오면 적대 모드 복귀(상한 = D5).

### 3-2. 예산 구조 (D2 — 분리)

- `--max`(기본 5) = **적대(발굴·수정) 라운드 상한**으로 재정의. **확인 라운드는 별도 예산 기본 2회**(인자명 예: `--confirm-rounds` — 구현 시 확정).
- **예산 산법(sR1-F2 명시화)**: 확인 예산(기본 2회)은 **루프 전체 누적 상한**이며 복귀 재진입 시 초기화되지 않는다. 복귀(D5) 시 적대 1라운드 + 확인 재진입 1라운드가 **누적 상한 밖에서 추가 허용**된다(복귀 상한 1회). 총 라운드 상한 = 적대 max(5) + 확인(2) + 복귀 적대(1) + 재진입 확인(1) = **기본값 기준 최대 9회**(ops-hub 실측 최장 트랙 9라운드와 일치).
- 정체가 R4~5에 늦게 와도 확인이 구조적으로 보장된다(확인 부채 78파일의 직접 해소 지점).

### 3-3. 전환 신호 (D3 — 현행 신호 재활용)

- **적대→확인 전환 = 현행 "판정 루프 전환" 신호 재활용**: blocking score 2회 연속 비감소(`s_n ≥ s_{n-1} ≥ s_{n-2}`) OR FIXED 큐 소진 OR **적대 예산(`--max`) 소진(sR1-F2 추가)**.
- **적대 예산 소진 경로(sR1-F2)**: 마지막 적대 라운드에서 새 FIXED가 생기고 score가 감소 중이어도, 상한 도달 시 미확인 FIXED가 있으면 **batch 정리(D6 순서) 후 반드시 확인 모드로 진입**한다 — 상한 도달이 확인을 건너뛰는 종료 경로(현행 확인 부채의 재발)가 되지 않게 한다. `--max`는 초과하지 않는다(추가 적대는 복귀 D5 경로뿐).
- 근거: 재지목(DUPLICATE)은 이미 score 밖이라 신호를 오염시키지 않고, 자기유발 결함은 확인 임무 ①②가 정확히 잡는 대상이라 조기 전환이 오히려 이득. "신규 실결함 유입" 기준은 자기유발 판별의 주관성·매 라운드 분류 비용 때문에 불채택.
- **score 상승 시퀀스(예: 3→4→5)도 전환 신호에 포함되는 것은 의도된 동작이다(D3 재론 금지, sR2-F2 각하 근거)**: 실측 7개 트랙 전부 비단조로 후반 상승은 churn의 전형이며, 실제로 확장 중인 결함 표면은 ① 확인 임무의 "발견한 blocking은 보고" → 적대 복귀(D5), ② 재진입 확인에서 재발 시 ESCALATE + whole-branch 리뷰 권고(D5), ③ 보안 트랙 D7 예외(score 신호 자체를 무시)의 3중 안전망이 받는다. 상승/평탄을 구분하는 신호 재정의는 불채택된 "신규 실결함 유입" 기준의 변형이다.

### 3-4. 확인 리뷰 실행 (D4 — task 커맨드)

- 확인 리뷰는 `codex-companion.mjs task`로 실행한다 — **프롬프트 전체 통제**(기저 적대 템플릿 잔존 위험 없음). `adversarial-review`+focus 방식은 불채택.
- 확인 리뷰 프롬프트에는 ledger 표·**미확인 FIXED 큐 전체**(sR2-F1)·리뷰 기준(base ref)을 첨부하고 임무 4종을 지시한다(문구는 마이크로테스트로 다듬는다). 성공 종료의 불변식: **큐의 전 항목이 소멸 확인 또는 blocking 재분류로 기록되어 큐가 비어야** 확인 경유 성공 종료가 성립한다.
- codex 샌드박스는 read-only — 게이트(테스트)는 현행대로 루프 세션이 실행한다.
- `task` 커맨드 부재(codex 플러그인 구버전) 시 기존 실패 규약을 확장 적용: 멈추고 `/codex:setup`(플러그인 갱신) 안내, 임의 대체 실행 금지.
- **도구 실패 의미론(sR3-F2)**: `task` 실행 실패·타임아웃·부분 응답(스키마 불일치)은 **소멸 확인으로 간주하지 않고 미확인 FIXED 큐를 변경하지 않으며 확인 예산을 소모하지 않는다**. 기존 실패 규약대로 멈추고 원문 보고(임의 대체 실행·재시도 기계장치 금지 — G1·G2 준수, 재실행은 사용자 판단).

### 3-5. 복귀 규칙 (D5 — 복귀 1회)

- 확인 라운드에서 blocking 발견 → 적대 모드 복귀는 **1회만**.
- 복귀 후 재진입한 확인에서 또 blocking이 나오면 → **ESCALATE**(edge 표면이 넓다는 신호 — 현행 규약대로 새 세션 whole-branch 리뷰 권고 동반).

### 3-6. 모드 축 관계 (D6 — 직교 + 순서 규정)

- 자동/정밀 축(`--auto-rounds`, ESCALATE 처리 방식)과 적대/확인 축(리뷰어 목적함수)은 **직교** — auto-rounds의 의미·기본값·batch 규약은 불변.
- 두 축의 트리거 신호가 같으므로 **순서를 규정한다**: 전환 신호 발화 → ① 모아둔 batch ESCALATE 일괄 제시(미판정 정리) → ② 확인 모드 진입. 확인 리뷰어는 판정이 정리된 ledger를 입력으로 받는다(임무 ③ 비례성 감사가 유효해지는 전제).

### 3-7. 보안 크리티컬 트랙 예외 (D7)

- **판별**: 사전 게이트(§1)에서 루프 세션이 변경 접촉면으로 자가 판정 — 기준은 ESCALATE 즉시군과 같은 계열(권한·인증·보안 경계·데이터 손상/유실·비가역 마이그레이션). 해당하면 루프 시작 시 사용자에게 "보안 크리티컬 트랙으로 취급할지" **확인 1회**.
- **예외 동작**: 보안 트랙에서는 전환 신호 중 **score 정체를 무시**하고 **FIXED 큐 소진(발굴이 실제로 마름) 또는 적대 예산 소진(sR1-F2)일 때만** 확인 전환. 적대를 max까지 쓸 수 있되 일찍 마르면 공회전 없이 전환(teams 사례 — 계속 신규가 유입되는 동안은 적대가 자연 연장됨). 현행 "보안 크리티컬 작업은 auto-rounds 낮게" 권고와 병존.

### 3-8. 확인 생략·경계 동작 (D8~D11)

- **D8 확인 생략(sR1-F1·sR3-F1·R4-F2 정밀화)**: 확인 라운드 필수 조건 = **미확인 FIXED 존재 OR 루프가 직접 내린 판정(ACCEPTED/OUT_OF_SCOPE/DEFERRED_TO_IMPL/DUPLICATE) 존재**. 루프 전체에서 둘 다 0건이면(예: R1 신규 blocking 0) 확인할 대상이 없으므로 **확인 라운드 없이 현행 빠른 종료 유지**(SDD 선행 R1 종결 트랙에 라운드를 추가하지 않는다). FIXED 없이 루프 판정만 있으면 확인 라운드는 임무 ③(판정 감사)·④(verdict)만 수행한다 — 잘못된 ACCEPTED/OUT_OF_SCOPE 분류·연결 없는 DEFERRED_TO_IMPL·오매칭 DUPLICATE(실제 신규 결함을 기결정 재론으로 잘못 각하)가 감사 없이 다음 단계로 넘어가는 경로를 막는다. 원 근거("확인할 대상이 없으면 생략")는 불변 — 감사할 루프 판정도 '확인할 대상'에 포함됨을 명시했을 뿐이다.
- **D9 판정 감사 이의 처리**: 임무 ③이 기존 루프 직접 판정(ACCEPTED/OUT_OF_SCOPE/DEFERRED_TO_IMPL/DUPLICATE — R4-F2)의 비례성·연결·오매칭 문제를 지적하면 루프가 스스로 번복하지 않고 해당 항목만 **ESCALATE로 사용자 재판정**. 감사 대상 = **루프가 직접 내린 판정만** — 사용자 기결정(D번호·사용자가 닫은 ESCALATE)은 감사 대상이 아님을 확인 리뷰 프롬프트에 명시(기결정 가드 규약 유지). 루프 직접 DUPLICATE의 감사 범위 = 원 fingerprint 동일성·원 disposition 확인(오매칭 검출)만 — 원 기결정의 타당성 재론은 대상이 아니다.
- **D10 ledger 기록**: spec은 **의무만 규정** — 확인 라운드마다 소멸 확인된 FIXED fingerprint 목록·신규 finding·머지 준비도 verdict를 ledger에 기록한다. 표 형식(행 추가 vs 주석)은 구현·마이크로테스트에서 확정. 현행 ledger 규약(단일 원본·fingerprint 키·severity 제외)은 불변.
- **D11 최종 폴백(sR3-F2 일반화)**: **확인 예산(재진입 포함)이 소진됐는데 미확인 FIXED 큐가 비지 않으면 — 복귀 발동 여부와 무관하게** — ESCALATE로 사용자에게 넘기며 **현행 §2h 3택을 폴백으로 유지** — ① 다음 phase 리뷰 필수 확인 항목으로 이월, ② 새 세션 확인 라운드 1회(whole-branch 권고), ③ 배포 smoke/검증으로 대체. 분리 예산이 1차 방어, 3택은 극단 edge 안전망으로 강등.
- **resume 정합(파생, sR1-F3 확장)**: `--resume` 복원 상태에 **현재 모드(적대/확인)·복귀 사용 여부·미확인 FIXED 목록·적대/확인 라운드 소진 카운트(잔여 예산)·보안 크리티컬 트랙 판정 상태**를 추가한다(§0·§2i 핸드오프 필드의 확장은 이 목록이 전부). 예산 카운트가 없으면 확인 도중 재개 시 예산이 초기화되어 총 상한(D2)을 넘거나 조기 소진되고, 보안 상태가 없으면 재개 후 D7 예외(score 정체 무시)가 유실된다.

## 6. 검증 계획

브리프 §0-2 규약: 스킬 문구 변경은 **writing-skills TDD 필수** — 베이스라인(현행 스킬로 실패 재현) → 개정 → 마이크로테스트(5+ reps, no-guidance 대조군 포함). ui-mockup·review-loop 0.2.0 개정 전례와 동일.

- **베이스라인(RED)**: 현행 스킬로 "score 정체 시 판정 루프 전환" 시나리오를 돌려 확인 부채·churn 재현을 기록.
- **ops-hub 파일럿(선택, 스킬 개정 전 실측)** — ops-hub의 다음 review-loop(impl 권장) 세션에 아래 지시를 얹으면 스킬 수정 없이 효과를 실측할 수 있다:

  > 이번 review-loop에서 blocking score가 2회 연속 비감소하거나 FIXED 큐가 소진되면, 이후 라운드는 **확인 리뷰 모드**로 전환한다. 확인 리뷰 = codex companion `task` 커맨드에 ledger 표와 직전 FIXED fingerprint 목록을 첨부하고 임무 4종(소멸 확인·수정 인접 회귀·ACCEPTED/OOS 비례성·머지 준비도 verdict)을 지시한다. "신규 영역 발굴은 임무가 아니다. 단, 발견한 blocking은 보고한다"를 명시한다. 확인 리뷰에서 blocking이 나오면 적대 모드로 복귀한다. 종료 후 기록: 확인 라운드가 잡은 것 / 도장만 찍었는지 / 종료가 깨끗해졌는지.

- **판정 기준**: 확인 라운드가 (a) 실제 회귀·불완전 수정을 잡는가(content-ops R6 재현), (b) 승인 남발하지 않는가, (c) 종료 시 확인 부채 0인가.
- **C-2 시나리오**: 문자적 논리 갭 성격의 finding을 심어 severity 재평가(실행 영향 기준 하향 + 저비용 수정 반영)가 동작하는지 확인(구체 픽스처는 구현 시 설계).
- **C-1**: 문구 반영 확인 + 입도 규칙(plan 통합 1회·마지막 트랙 기준 ref 통합) 시나리오 질의 검증. 비-main 기준 브랜치 시나리오 포함(sR2-F3).
- **D8 경계(sR1-F1·sR3-F1)**: FIXED 0건 + 루프 직접 판정(ACCEPTED/OUT_OF_SCOPE/DEFERRED_TO_IMPL) 존재 시나리오에서 확인 라운드(임무 ③·④)가 실행되는지, DEFERRED_TO_IMPL의 AC·테스트 연결 누락을 감사가 지적하는지 확인.
- **도구 실패(sR3-F2)**: 확인 `task` 타임아웃·부분 응답 시나리오에서 큐 불변·예산 미차감·중단 보고가 지켜지고, 예산 소진+큐 잔존이 복귀 미발동이어도 ESCALATE+3택으로 가는지 확인.
- **resume 왕복(sR1-F3)**: 적대 중단·확인 중단·복귀 후 중단 각 지점에서 핸드오프→재개 시 모드·예산 잔여·보안 트랙 상태가 보존되는지 확인.
- **미확인 FIXED 큐 누적(sR2-F1)**: 여러 라운드에 걸쳐 잔존한 FIXED·부분 확인·resume 재개 시나리오에서 확인 프롬프트에 큐 전체가 들어가고, 큐가 빌 때만 성공 종료되는지 확인.
- **DUPLICATE 오판 감사(R4-F2)**: 루프 직접 DUPLICATE가 존재하는 시나리오에서 확인 라운드가 원 fingerprint와의 의미적 동일성·원 disposition을 감사하고, 오매칭(실제 신규 결함을 기결정 재론으로 잘못 각하)을 지적해 ESCALATE(D9)로 올리는지 확인. FIXED 0건 + 루프 직접 DUPLICATE만 존재해도 확인 라운드(임무 ③·④)가 생략되지 않는지 포함(D8).
- **큐 용어 분리(R4-F3, DEFERRED_TO_IMPL)**: SKILL.md 개정 시 라운드 내 **수정 큐**(FIXED 후보 작업 큐 — 현행 §2e·§2h 용례)와 **미확인 FIXED 큐**(소멸 확인 대기 누적 — §3-1 임무 ① 대상)를 구별 명명하고, D3·D7 전환 신호의 "FIXED 큐 소진" = 수정 큐 기준(최신 적대 라운드 분류 후 신규 FIXED 후보 0건)임을 본문에 명시 — 두 해석이 갈리는 질의 시나리오로 검증.
- **확인 응답 완전성(R4-F4, DEFERRED_TO_IMPL)**: 확인 리뷰 응답은 첨부한 미확인 FIXED 큐의 **전 fingerprint별 명시 결과(소멸/잔존/blocking 재분류)·판정 감사 결과·신규 finding·verdict**를 갖춰야 완전하며, 하나라도 누락·중복·판독 불가면 D4 부분 응답으로 처리(큐 불변·예산 미차감·중단 보고)됨을 SKILL.md에 명시 — 누락 필드 응답 픽스처로 검증(표기 형식 확정은 D10대로 구현 단계).
- **resume 스냅샷 정합(R5-F1, DEFERRED_TO_IMPL)**: 핸드오프에 branch·중단 시 HEAD SHA·해소된 base SHA를 기록하고, resume 시 현재 상태와 대조해 불일치(중단 중 커밋 추가·브랜치 이동·base 이동)면 모드·예산·큐를 그대로 복원하지 않고 중단 보고(fail-closed — D4 실패 규약과 동일, 재개 방식은 사용자 판단, 통상 적대 1회 재실행 권고)하는지 확인 — 중단 중 커밋 추가 픽스처로 검증. 확인 모드는 신규 발굴을 하지 않으므로 미검토 커밋이 큐 소멸·merge-ready 판정을 받는 경로 차단이 목적.
- **verdict 비통과 경계(R5-F2, DEFERRED_TO_IMPL)**: 미확인 FIXED 큐가 비고 신규 blocking도 없는데 verdict가 비통과인 유효 확인 응답이 침묵 종료·종료 불능에 빠지지 않고 **ESCALATE(verdict 근거 동반, 사용자 판정)**로 정규화되는지, blocking 동반 시 D5 복귀로 가는지, 확인 필수 조건(D8) 성립 상태에서 확인 예산 0 설정이 시작 시 ESCALATE되는지 확인 — 모든 미충족 성공 불변식이 성공/복귀/ESCALATE 중 하나로 반드시 전이됨(종료 불능 상태 금지).

## 재논의 금지(기결정)

2026-08-07 harden-spec 세션에서 확정. 아래는 재론하지 않는다.

- **D1.** 골격 = 적대(발굴)/확인(중립) 2모드 + 확인 임무 4종·ledger 입력 + "신규 영역 발굴은 임무가 아니다. 단 발견한 blocking은 보고한다" + 탈출구(blocking 시 적대 복귀). 2026-08-07 사용자 발의·승인. (임무 ① 대상 = 미확인 FIXED 큐 전체 — sR2-F1 정밀화.)
- **D2.** 예산 분리 — `--max`(기본 5) = 적대 라운드 상한, 확인 라운드 별도 예산 기본 2회(루프 전체 누적, 재진입 시 비초기화 — sR1-F2 산법 명시). 복귀 시 적대 1회+확인 재진입 1회 추가 허용(총 유계 = 기본값 최대 9회).
- **D3.** 전환 신호 = 현행 판정 루프 전환 신호 재활용(score 2회 연속 비감소 OR FIXED 큐 소진 OR 적대 예산 소진 — sR1-F2 추가). 상한 도달 시에도 미확인 FIXED가 있으면 batch 정리 후 확인 진입. "신규 실결함 유입" 기준 불채택(자기유발 판별 주관성·분류 비용).
- **D4.** 확인 리뷰 실행 = companion `task` 커맨드(프롬프트 전체 통제). `adversarial-review`+focus 불채택. 게이트는 루프 세션 실행. `task` 부재 시 `/codex:setup` 안내(기존 실패 규약 확장). 실행 실패·타임아웃·부분 응답 = 큐 불변·예산 미차감·중단 보고(sR3-F2).
- **D5.** 복귀 상한 1회 — 확인 2회차에서도 blocking이면 ESCALATE + whole-branch 리뷰 권고.
- **D6.** 축 직교 — auto-rounds(ESCALATE 처리) 축 불변. 순서: 전환 신호 발화 → batch ESCALATE 일괄 제시 → 확인 모드 진입.
- **D7.** 보안 크리티컬 = 사전 게이트 자가 판정(ESCALATE 즉시군 계열 기준) + 사용자 확인 1회. 예외 동작 = score 정체 신호 무시, FIXED 큐 소진 또는 적대 예산 소진 시에만 확인 전환.
- **D8.** 확인 라운드 필수 조건 = 미확인 FIXED 또는 루프 직접 판정(ACCEPTED/OUT_OF_SCOPE/DEFERRED_TO_IMPL/DUPLICATE) 존재(sR1-F1·sR3-F1·R4-F2 정밀화). 둘 다 0건이면 확인 없이 현행 빠른 종료 유지. 원 취지(클린 트랙에 라운드 미추가) 불변.
- **D9.** 판정 감사(임무 ③) 이의 = 해당 항목만 ESCALATE로 사용자 재판정. 감사 대상 = 루프가 직접 내린 판정만(사용자 기결정·D번호 제외). 루프 자체 번복 금지. 루프 직접 DUPLICATE 포함 — 단 감사는 원 fingerprint 동일성·원 disposition 확인만, 원 기결정 재론 아님(R4-F2, 2026-08-07 사용자 확정).
- **D10.** 확인 라운드 ledger 기록은 의무만 spec 규정(소멸 확인 fingerprint·신규 finding·verdict), 형식은 구현·마이크로테스트에서 확정. 현행 ledger 규약 불변.
- **D11.** 확인 예산 소진(복귀 발동 여부 무관 — sR3-F2 일반화) 후 잔여 확인 부채 = ESCALATE + 현행 §2h 3택 폴백 유지(이월/새 세션 확인/배포 검증 대체).
- **D12.** 릴리스 범위 = 1+3 통합(C-1 런북 흡수 + C-2 severity 재평가 포함). 다음 순번 = 2(트랙 B).

**승계 가드 (이 spec이 전제하는 기존 기결정 — 재론 금지):**
- ESCALATE batch 기계장치 유지(review-loop 0.2.0 회고). 실측 트랙당 0~1건도 "무해라 유지" 판단을 뒤집지 않는다.
- G1·G2(ui-mockup spec 2026-07-25) — 기계 검증 장치·보안 하드닝 머신 과설계 금지. 이 트랙은 프롬프트/절차 수준 변경만.
- description은 트리거만(writing-skills 원칙) — 워크플로 요약 금지.
- no-AI-trace — 커밋·산출물에 AI 서명 금지.
- disposition 어휘 6종·"미판정 blocking 0" 목표·fingerprint 규약 — 정착 자산, 변경 금지.
