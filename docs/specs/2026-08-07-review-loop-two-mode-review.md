## 1. 배경 / 문제

세 마찰의 뿌리가 같다: **적대 리뷰어의 목적함수는 "공격"이라 몇 번을 돌려도 finding 0이 나오지 않는다.** (실측 근거는 전부 이웃 repo `../ops-hub/` 기준, 2026-08-07 점검.)

1. **확인 부채** (78개 파일) — max 5 도달 시 마지막 라운드 FIXED가 재확인 없이 다음 단계로 넘어간다. "max 도달" 계열 55개 파일 — 대부분의 트랙이 예산 5회를 소진하고 끝난다.
2. **churn** — 후반 라운드가 신규 영역·자기유발 결함(수정이 도입한 결함 계열 3회: cR2-B→cR4-A→cR5-A)으로 소모되고 score가 수렴하지 않는다. **7개 트랙 실측 전부 비단조**(예: 3→4→5→7→7→0). 적대 리뷰는 매회 전체 diff를 다시 보므로 절대 0은 도달 불가 — "2회 연속 비감소=정체" 규칙이 상시 성립 직전이다.
3. **오버엔지니어링 압력** — 적대검증자가 위협 모델 밖 기계 장치를 반복 요구한다(이 repo `docs/specs/2026-07-25-ui-mockup-skill-design.md` impl R2 관찰: "G1·G2 블록이 diff에 있어도 억제하지 않는다").

**확인 라운드의 가치 실증** (max 너머 수동 연장 사례):

- `../ops-hub/docs/plans/2026-07-31-content-ops-visibility.md:361` — max 도달 후 사용자가 확인 라운드 R6 선택 → R6가 iR5-F1의 불완전성(iR6-F1)을 실제로 잡음. R7이 파생 결함 1건 추가, R8이 소멸 확인. impl 총 9라운드.
- `../ops-hub/docs/plans/2026-07-18-report-knowledge-search.md:302` — cR6(새 세션 whole-branch)가 확인 부채 해소를 확정했는데, cR7이 다시 "cR6 수정이 도입한 unsatisfiable 게이트"를 발견. 이 트랙은 spec·plan·impl **3연속 확인 부채**.
- `../ops-hub/docs/plans/2026-06-23-teams-and-permission-matrix.md:198` — **보안 크리티컬 트랙**: R6→R8 연장이 critical(F-N)·데드락(F-P)·override in-tx(F-Q)·비활성 팀 경계(F-R)·배포 순서(F-T) **신규 5건**을 잡음. ⚠ "후반 라운드=확인만"이 보안 트랙에서는 위험함을 보여준다 — 탈출구·보안 예외(§3-3)의 근거.
- 대조: SDD 내장 리뷰를 잘 돌린 트랙은 review-loop impl이 R1 종결(`../ops-hub/docs/plans/2026-08-05-report-weekly-meeting-view.md:120`).

## 2. 목표 / 비목표

**목표:** review-loop의 리뷰 라운드를 **적대(발굴)/확인(중립) 2모드**로 나눠 — ① 마지막 FIXED의 재확인이 예산 안에서 구조적으로 보장되어 확인 부채가 사라지고, ② "신규 blocking 없음, 수정 확인됨"이 정당한 출력이 되어 종료가 자연스러워지며, ③ 확인 모드의 비례성 시각이 오버엔지니어링 요구를 거른다.

**비목표 (YAGNI / 기결정 준수):**
- ESCALATE batch 기계장치 변경 — "무해라 유지"가 기결정(review-loop 0.2.0 회고). 건드리지 않는다.
- 기계 검증 장치(파서·스위트·자동 게이트) 신설 — 트랙 A는 **프롬프트/절차 수준 변경**이다(G1·G2 저촉 없음).
- codex companion 스크립트 자체 수정 — 다른 플러그인(openai-codex) 소유. 이 spec은 호출 방식만 정한다.
- 기결정 가드 focus-text 자동 주입 — 실행 순서 2번(트랙 B) 별도. 단 실행 경로(§5)가 겹치므로 harden-spec에서 인터페이스 정합만 확인한다.
- 런북 흡수(C-1)·severity 재평가 지침(C-2) — 실행 순서 3번. 이 릴리스로 흡수할지는 §7 Q7에서 판단.

## 3. 승인된 골격 (사용자 발의·승인 2026-08-07 — 재론 금지 대상)

리뷰 라운드를 2모드로 나눈다:

- **적대(발굴) 모드** — 현행 adversarial-review. 초반 라운드. 목적함수 = 공격(누락·결함 발굴).
- **확인(중립) 모드** — 후반 라운드. 목적함수 = **"머지 가능한가 판정"**. "신규 blocking 없음, 수정 확인됨"이 정당한 출력이므로 종료가 자연스럽고, 확인 부채가 구조적으로 사라지며, 비례성 시각이 오버엔지니어링을 거른다.

사용자 원안("3회 적대 + 2회 확인" 고정 분할)에서 논의를 거쳐 다음 두 보완이 함께 승인됐다:

1. **고정 회차가 아니라 신호 기반 전환** — 트랙 편차가 크다(R1 종결 트랙 vs R8까지 실결함 트랙). 기존 "판정 루프 전환" 신호(score 2회 연속 비감소·FIXED 큐 소진)를 전환 트리거로 재활용하면 평균 트랙은 대략 3+2 근처로 수렴한다.
2. **확인 리뷰의 임무 4종 고정 + ledger 입력** — 빈손 "중립으로 봐줘"는 도장 찍기가 된다. 확인 리뷰어에게 ledger를 입력으로 주고:
   - ① 직전 라운드 FIXED fingerprint들의 소멸 확인
   - ② 수정이 닿은 영역 주변의 회귀 확인
   - ③ ACCEPTED/OUT_OF_SCOPE 판정의 비례성 점검(판정 감사)
   - ④ 머지 준비도 verdict
   - **"신규 영역 발굴은 임무가 아니다. 단, 발견한 blocking은 보고한다"를 명시**(도장 찍기 / 사냥 재개 사이 균형).
3. **탈출구** — 확인 라운드에서 blocking이 나오면 적대 모드 복귀. **보안·권한·데이터 크리티컬 트랙은 전환을 늦춘다**(teams 사례 §1이 근거).

## 4. 현행 스킬 접점 — 개정 지도

현행 `dev-workflow/skills/review-loop/SKILL.md` 기준, 2모드 도입이 닿는 지점과 방향. 세부는 §7 확정 후 구현에서 정한다.

| 현행 섹션 | 변경 방향 | 연관 질문 |
|---|---|---|
| 핵심 원칙 (수정 루프 / 판정 루프) | "수정/판정" 축 위에 "적대/확인" 모드 축을 정의 — 판정 루프 전환 신호가 확인 모드 진입 신호를 겸하는지 정리 | Q2·Q6 |
| blocking score — 판정 루프 전환 신호 | 전환 신호를 그대로 재활용할지, "신규 실결함 유입"(재지목 DUPLICATE·자기유발 제외) 기준으로 재정의할지 | Q2 |
| §인자 (`--max`, `--auto-rounds`) | 확인 라운드 예산을 max 5에 포함할지 분리할지. 자동/정밀 축과 적대/확인 축의 직교·통합 | Q1·Q6 |
| §2b 적대검증 실행 | 확인 모드일 때 실행 방식 분기 — `task` 커맨드(프롬프트 전체 통제) vs `adversarial-review`+focus | Q3 |
| §2c 분류·판정 | 확인 모드 출력(임무 4종 결과)의 ledger 반영 방식 — 소멸 확인·판정 감사 결과 기록 | — |
| §2h 판정 루프 전환·확인 부채 | 확인 부채 처리 3택(이월/확인 라운드/smoke 대체)을 확인 모드가 구조로 흡수 — 항목 재작성. 탈출구(적대 복귀)와 복귀 횟수 제한 추가 | Q4 |
| 보안 크리티컬 예외 | 판별 기준과 예외 동작(전환 지연·적대 연장) 신설 — 현행 `--auto-rounds` "보안 크리티컬 작업은 낮게" 서술과 정합 | Q5 |
| 종료 조건 요약 / §4 종료 요약 | 확인 모드 경유 종료 경로 반영 — "확인 부채 0" 확인을 종료 보고에 포함 | Q1 |

## 5. 구현 힌트 (companion 실측 확인, 2026-08-07 · codex 플러그인 1.0.6)

- `codex-companion.mjs adversarial-review [--wait|--background] [--base <ref>] [focus text]` — focus text가 리뷰 프롬프트의 `USER_FOCUS`로 들어간다(`scripts/codex-companion.mjs` `buildAdversarialReviewPrompt`). 단 기저 템플릿이 적대라 **확인 모드를 focus만으로 온전히 누를 수 있을지는 미검증**.
- `codex-companion.mjs task [--background] [prompt]` — 임의 프롬프트 실행. **확인 리뷰 프롬프트를 전체 통제할 수 있어 이쪽이 깨끗하다**(브리프 권고). codex 샌드박스는 read-only라 게이트(테스트) 실행은 못 시킨다 — 게이트는 현행대로 루프 세션이 돌린다.
- native `/codex:review` 매핑은 custom focus를 지원하지 않는다(companion `validateNativeReviewRequest`가 거부).

## 6. 검증 계획

브리프 §0-2 규약: 스킬 문구 변경은 **writing-skills TDD 필수** — 베이스라인(현행 스킬로 실패 재현) → 개정 → 마이크로테스트(5+ reps, no-guidance 대조군 포함). ui-mockup·review-loop 0.2.0 개정 전례와 동일.

- **베이스라인(RED)**: 현행 스킬로 "score 정체 시 판정 루프 전환" 시나리오를 돌려 확인 부채·churn 재현을 기록.
- **ops-hub 파일럿(선택, 스킬 개정 전 실측)** — ops-hub의 다음 review-loop(impl 권장) 세션에 아래 지시를 얹으면 스킬 수정 없이 효과를 실측할 수 있다:

  > 이번 review-loop에서 blocking score가 2회 연속 비감소하거나 FIXED 큐가 소진되면, 이후 라운드는 **확인 리뷰 모드**로 전환한다. 확인 리뷰 = codex companion `task` 커맨드에 ledger 표와 직전 FIXED fingerprint 목록을 첨부하고 임무 4종(소멸 확인·수정 인접 회귀·ACCEPTED/OOS 비례성·머지 준비도 verdict)을 지시한다. "신규 영역 발굴은 임무가 아니다. 단, 발견한 blocking은 보고한다"를 명시한다. 확인 리뷰에서 blocking이 나오면 적대 모드로 복귀한다. 종료 후 기록: 확인 라운드가 잡은 것 / 도장만 찍었는지 / 종료가 깨끗해졌는지.

- **판정 기준**: 확인 라운드가 (a) 실제 회귀·불완전 수정을 잡는가(content-ops R6 재현), (b) 승인 남발하지 않는가, (c) 종료 시 확인 부채 0인가.

## 7. 미해결 질문 (harden-spec 확정 대상 — 갭 대장 시드)

1. **Q1 예산 구조**: 확인 라운드를 max 5에 포함할지, 수정(적대) 라운드 상한과 분리해 확인 1~2회를 별도 예산으로 둘지. (브리프 분리 권고 — 정체가 R4~5에 와도 확인이 보장되도록)
2. **Q2 전환 신호의 정확한 정의**: 현행 score 정체 그대로 쓸지, 재지목(DUPLICATE)·자기유발 결함을 제외한 "신규 실결함 유입" 기준으로 바꿀지.
3. **Q3 확인 리뷰 실행 방식**: `task` 커맨드(프롬프트 전체 통제) vs `adversarial-review`+focus(기저 적대 프롬프트 잔존 위험). 마이크로테스트로 판가름.
4. **Q4 복귀 규칙**: 확인 라운드 blocking 발견 시 적대 복귀의 횟수 제한(무한 왕복 방지).
5. **Q5 보안 크리티컬 트랙 판별 기준과 예외 동작**(전환 지연·적대 연장).
6. **Q6 `--auto-rounds`와의 관계**: 자동/정밀 모드 축과 적대/확인 모드 축이 직교하는지, 통합할지.
7. **Q7 순번 3 흡수 여부**: C-1(런북 자체 보완 흡수)·C-2(severity 재평가 지침)를 같은 SKILL.md 릴리스로 흡수할지(1+3 통합 spec), 별도 순번으로 남길지. (브리프 §실행 순서 — 흡수해도 "전 항목 진행" 결정과 모순되지 않음)

## 8. 완료 조건 (acceptance criteria)

**트랙 A 고유 (브리프 §완료 조건 순번 1):**
- review-loop SKILL.md에 **적대/확인 2모드 · 전환 신호 · 임무 4종 · 탈출구 · 예산 구조**가 반영된다.
- 베이스라인 대비 마이크로테스트로 확인: (a) 확인 라운드가 도장 찍기가 아님, (b) 확인 부채 0 종료, (c) 보안 트랙 예외 동작.

**순번 공통 (브리프 §완료 조건):**
- writing-skills 마이크로테스트 통과.
- `plugin.json` minor 범프 + README 3종(en/ko/ja) 동기 갱신.
- 종료 보고에 각 머신 `/plugin update` 안내.
- 트랙 종결 핸드오프에 다음 순번(2번 — 트랙 B 기결정 가드 focus 주입. 단 Q7에서 3 흡수 시 다음은 4번) 명시.

## 9. 기결정 대조 (이 repo 기존 결정과의 정합 — 충돌 없음 확인)

- **G1·G2**(ui-mockup spec — 기계 검증 장치 과설계 금지): 트랙 A는 프롬프트/절차 수준 변경이라 저촉 없음.
- **ESCALATE batch 유지**(review-loop 0.2.0 회고 기결정): 건드리지 않는다. 실측(트랙당 0~1건)도 "무해라 유지" 판단을 뒤집지 않는다.
- **description은 트리거만**(writing-skills 원칙): review-loop description 갱신 시 워크플로 요약을 넣지 않는다.
- **no-AI-trace**: 스킬이 만드는 커밋·산출물 규약은 현행 유지(이 repo 문서에서 codex를 다루는 것은 도구 자체가 주제이므로 무관).
