# ui-mockup 스킬 설계 (UI/UX 목업 선택 단계)

- 상태: 설계 승인됨 (brainstorming 산출물, 구현 전)
- 대상: `dev-workflow` 플러그인에 추가할 **신규** 스킬 `ui-mockup` (파이프라인 3.5단계, 옵션)
- 날짜: 2026-07-25

## 1. 배경 / 문제

현행 파이프라인(brainstorming → spec → harden-spec → review-loop → plan → review-loop → 구현 → review-loop)에서 **화면(UI/UX)이 필요한 기능은 사용자 의사와 무관하게 구현이 진행**되고, 기능 완성 후 UI/UX를 다시 개선하는 재작업이 반복된다. 취향·시각 결정이 파이프라인 어디에서도 명시적으로 수집·기록되지 않기 때문이다.

## 2. 목표 / 비목표

**목표:** 화면이 새로 생기거나 구성이 바뀌는 기능에서, plan 이전에 사용자의 시각적 취향을 목업 선택으로 확정하고 **spec에 기결정으로 기록**해 구현 단계의 임의 재해석을 차단한다. 선택 결과를 **프로젝트 스타일 가이드로 수렴**시켜 기능 간 UI 파편화를 막는다.

**비목표 (YAGNI):**
- 스크린샷 자동 비교(playwright 대조) — impl 검증은 수동 대조 수준.
- 인터랙션 프로토타입 — 목업은 정적 HTML.
- 스택별 컴포넌트 코드 생성 — 목업은 HTML/CSS 중립, 구현 계약은 시각·구성이지 코드가 아니다.
- 디자인 토큰 자동 주입 도구.
- UI가 없는 기능에의 강제 — 트리거 미충족 시 완전히 건너뛴다.

## 3. 파이프라인 내 위치

```
… → harden-spec → [ui-mockup (옵션, 3.5)] → review-loop(spec) → plan → …
```

**harden-spec 직후·review-loop(spec) 직전**인 이유:
- harden-spec이 화면 목록·빈 상태·에러 상태·범위를 굳힌 **뒤**라 목업 재작업이 최소화된다(상태 확정 전에 만들면 구조적으로 다시 만든다).
- 선택된 UI 결정이 spec에 반영된 **뒤** codex 적대검증(review-loop spec)을 통과하므로, 목업발(發) spec 변경도 검증망 안에 있다.
- review-loop(spec) 이후에 두면 굳은 spec을 목업 선택이 다시 바꿔 재검증 루프가 꼬인다.

**트리거 (관찰 가능 판정):** "spec이 새 화면을 만들거나 기존 화면 구성을 바꾸는가." 예 → 진입 확인 후 실행, 아니오 → 건너뜀. 판정·안내 지점은 harden-spec 종료 권고와 dev-cycle 판별 로직(§6).

- **하한선:** 레이아웃 구조가 바뀌거나 새 UI 블록(섹션·패널·테이블 등)이 생기는 수준부터 충족. 문구·색·아이콘·단일 컨트롤 추가 같은 경미 변경은 미충족(건너뜀). 경계가 애매하면 진입 확인 질문으로 사용자가 판정한다.
- **파이프라인 전용:** 대상 spec 없이 단독 호출되면("목업 만들어줘" 단발) 실행하지 않고 brainstorming → harden-spec 경로를 안내한다(§3 근거: 상태 확정 전 목업은 구조적 재작업). description 트리거도 파이프라인 문맥으로 좁혀 오호출을 줄인다.
- **의도적 생략:** 트리거 충족인데 사용자가 진입 확인에서 생략을 택하면, spec의 `## 재논의 금지(기결정)`에 "UI 목업 생략(사용자 결정)" 한 줄을 기록한다 — dev-cycle·harden-spec의 3.5 재권고를 차단.

## 4. 동작 설계 (5단계)

### 입력
- 굳은 spec 경로(생략 시 harden-spec과 동일한 자동 탐색 + 확인). spec이 없으면 실행하지 않는다(§3 파이프라인 전용).
- `<feature>` 슬러그: spec 파일명에서 날짜 접두를 제거한 값을 기본 제안하고 진입 확인에서 함께 확정한다(예: `2026-07-25-foo-design.md` → `foo-design`). 확정 슬러그는 spec `## UI 설계`에 기록한다 — **이 섹션이 3.5 완료 레코드**이며 dev-cycle 판별 기준이다(디렉터리 존재가 아님, §6). 슬러그는 `[a-z0-9-]+` **단일 경로 세그먼트만 허용**(경로 구분자·`..`·절대경로 거부) — 산출물 경로는 항상 `docs/design/` 직하위로 고정된다.
- 발산 모드 결정: `docs/design/style-guide.md` 존재 여부 + (첫 실행 시) 기존 UI 존재 여부(§4-2).

### 절차

**1) 로드.** spec에서 대상 화면·핵심 상태(기본/빈/에러) 목록을 추출하고 style-guide.md 존재를 확인한다. `docs/design/<feature>/`가 이미 존재하면 **소유자부터 판정**한다 — 그 경로를 `## UI 설계`에서 참조하는 spec을 저장소에서 검색해:
- **다른 spec 소유** → 슬러그 충돌. 재사용·재생성을 금지하고 **슬러그 변경만** 허용한다(다른 기능의 커밋된 산출물 보호).
- **소유 spec 없음**(이전 실행 중단·잔재) → 완료로 간주하지 않고, 진입 확인에서 **재개(기존 후보 재사용) / 재생성 / 슬러그 변경**을 묻는다.
- 같은 spec 소유의 재생성(명시 재발산 등)은 허용 — 산출물은 커밋돼 있어 git 이력으로 복구 가능하다. 단, 재생성·덮어쓰기 전 대상 경로(디자인 디렉터리·style-guide.md·spec)의 **미커밋 변경**을 `git status`로 확인하고, 있으면 보존 방법(선커밋 / 새 슬러그 / 중단)을 사용자에게 확인한 뒤 진행한다(미커밋 변경은 git 이력으로 복구 불가).

**2) 발산 (가이드 수렴형).**
- **가이드 없음 + 기존 UI 없음(신규 프로젝트):** 서로 다른 스타일 **4종** 목업.
- **가이드 없음 + 기존 UI 있음(repo에 화면·템플릿·CSS 존재):** 사용자가 모드를 선택한다(AskUserQuestion) —
  - **(a) 기존 디자인 유지:** 기존 UI에서 style-guide.md 초안을 역추출해 승인받고 "가이드 있음" 모드(레이아웃 변형)로 진행. 기능 추가형 프로젝트의 기본 경로.
  - **(b) 리뉴얼:** 신규 스타일 4종 발산. 선택본이 새 가이드가 되고 이후 실행은 (a)로 수렴.
- **가이드 있음:** 가이드 준수 **레이아웃 변형 2~3종**만(스타일 재발산은 사용자가 명시 요청할 때만).
- **다중 화면 spec:** 발산은 **대표 화면 1개**(가장 복잡한 화면)로만 한다. 나머지 화면은 선택 확정 후 선택 스타일로 생성해 `docs/design/<feature>/`에 포함한다(4종 × 전 화면 생성 금지 — 탈락안에 드는 비용 낭비).
- 목업은 자체완결·**비실행** HTML/CSS — **허용 목록 원칙**: 정적 마크업 + 인라인 CSS(+정적 인라인 SVG)만 허용하고, 그 외 활성 콘텐츠는 전부 금지한다(`<script>`·인라인 이벤트 핸들러·form 제출·`object`/`embed`·meta refresh·`javascript:` 등 실행성 URL 스킴·원격/데이터 URL — 금지 열거가 아니라 **허용 외 전부 거부**. D2 "정적" 원칙의 구체화). 재개(§4-1)로 기존 후보를 재사용할 때도 동일 제약을 재검증한다. **서브에이전트 병렬 생성**, 생성 에이전트는 `model: fable` 지정(시각 품질 — 본체는 세션 모델). 설치돼 있으면 frontend-design·dataviz 스킬을 생성 에이전트가 참조.
- 각 목업은 기본 화면 + 핵심 상태 1~2개(빈/에러)를 포함한다 — harden-spec이 굳힌 상태가 시각화되는 지점.

**3) 제시·선택.** 탭/분할로 한눈에 비교하는 **비교 페이지 HTML**을 함께 생성해 전달하고(후보는 빈 `sandbox` 속성 iframe으로 격리 임베드 — src는 같은 디렉터리의 로컬 상대 경로만 허용), 선택은 AskUserQuestion으로 받는다. **조합 지정 허용**("2번 레이아웃 + 4번 색") — 조합이면 조합본을 1회 재생성해 비교 페이지로 보여주고 **최종 확인 1회 후 확정**한다(사용자가 고른 것은 조합 규칙이지 생성 결과가 아니므로). 거부 시 재조합이 아니라 수정 요청 루프로 보낸다(재조합 무한 루프 금지·발산 상한 유지, D5의 재생성 1회 준수). **전부 거부 시:** "무엇이 아쉬운지" 방향 피드백을 받아 **재발산 1회**(발산 총 2라운드 상한). 그래도 불만족이면 가장 근접한 안을 고르게 하고 수정 요청 루프로 전환한다.

**4) 확정·기록.**
- 선택본을 `docs/design/<feature>/`에 정리(후보·비교 페이지 포함 커밋 — 이력 보존). 다중 화면이면 나머지 화면을 이 시점에 선택 스타일로 생성하고, **비교 페이지에 추가해 사용자 최종 확인 1회를 받는다**(AskUserQuestion — 수정 요청 가능, 재발산 아님·발산 라운드에 불산입). 최종 확인 전에는 spec 기록·커밋을 하지 않는다(§7 "선택 없이 확정 경로 없음"의 다중 화면 적용).
- **완료 레코드:** 아래 spec `## UI 설계` 기록 + 커밋까지 끝나야 3.5 완료다. design 파일만 있고 spec 기록이 없는 상태는 미완료(§4-1 재개 경로).
- **style-guide.md 수렴 규칙:**
  - **첫 실행(가이드 없음):** 선택 결과(또는 역추출 승인본)에서 `docs/design/style-guide.md`(색·타이포·간격·컴포넌트 규칙)를 생성한다.
  - **이후 실행:** 가이드에 없는 새 컴포넌트 규칙(첫 테이블·차트·모달 등)은 확정 시 가이드에 **증분 추가**한다(living document — 기존 규칙의 변경·삭제는 하지 않음, 추가만).
  - **명시 요청 재발산으로 다른 스타일이 선택되면:** 가이드를 새 선택으로 **교체**한다(프로젝트 스타일 전환 — 이전 가이드는 git 이력으로 보존, 기존 화면과의 불일치는 확정 시점에 잔여 리스크로 기록).
  - **동시 변경 가드:** 가이드 쓰기 직전 style-guide.md를 다시 읽어 로드 시점과 달라졌으면(다른 세션·작업의 변경) 최신 내용 기준으로 증분 추가를 재적용한다(lost update 방지 — 잠금·CAS 없이 재로드로 갈음). 커밋은 이 실행이 만든 파일만 명시 stage(D11).
- spec에 `## UI 설계` 섹션(확정 슬러그 + 선택 목업 경로 + 핵심 결정 요약)을 추가하고, **`## 재논의 금지(기결정)` 블록에 UI 결정을 기록**한다 — review-loop·plan·구현의 재해석을 기결정 가드로 차단(harden-spec 규약과 동일 메커니즘).

**5) 종료.** design 파일 + spec만 명시 stage 커밋(`git add -A` 금지, AI 서명 금지). review-loop(spec)을 권고하고 정지(자동 전환 금지 — 파이프라인 규약 동일).

**목업 중 spec 결함 발견 시 (경중 분기):** 목업 작업이 `## UI 설계` 밖의 spec 변경을 요구하면 —
- **경미**(굳힌 화면 목록 안에서 상태 1~2개 보강 수준): 사용자 확인 후 이 세션에서 spec에 직접 반영하고 계속 진행.
- **구조적**(화면 추가·요구 변경): 중단하고 harden-spec 재실행을 권고한다(3.5가 제2 brainstorming이 되는 것 방지).

## 5. 하지 말 것 (red flags 후보 — 구현 시 확정)

- 트리거 미충족(UI 없음·경미 변경)인데 목업을 만든다 → 건너뛴다.
- 가이드가 있는데 스타일 4종을 재발산한다 → 레이아웃 변형만(재발산은 명시 요청 시).
- 기존 UI가 있는 프로젝트에서 감지 없이 4종 자유 발산한다 → 유지(역추출)/리뉴얼 모드 선택을 먼저 받는다.
- 선택을 안 받고 "가장 나은" 목업을 스스로 확정한다 → 선택은 AskUserQuestion, 판정자는 사용자.
- 전부 거부에 재발산을 반복한다 → 재발산 1회(발산 총 2라운드), 이후 수정 요청 루프.
- spec 없이 단독 목업을 만든다 → 거부하고 brainstorming → harden-spec 경로 안내.
- UI 결정을 spec에 기록하지 않고 목업 파일만 남긴다 → 재논의 금지 블록까지가 산출물.
- 목업에 외부 CDN·리소스를 넣는다 → 자체완결 HTML.
- 목업에 script·이벤트 핸들러·form 제출을 넣거나, 비교 페이지에 후보를 sandbox 없이 임베드한다 → 비실행 HTML + sandbox iframe(§4-2·§4-3).

## 6. 연동 변경 (각 한 곳)

| 대상 | 변경 |
|---|---|
| dev-cycle | 파이프라인 표에 3.5 옵션 행 추가 + 판별 로직에 "spec 굳음(`## 재논의 금지(기결정)` 블록 존재) + spec이 화면을 만들거나 바꿈 + **spec에 `## UI 설계` 섹션 없음(완료 레코드 기준 — `docs/design/<feature>` 디렉터리 존재만으로 완료 판정 금지)** + 재논의 금지 블록에 목업 생략 기록 없음 → 3.5 ui-mockup" 조건 추가. 섹션이 있으면 기록된 목업 경로가 실재하는지 확인하고, 불일치면 완료가 아니라 §4-1 재개 경로로 보낸다. **완료(또는 생략) 기록이 생긴 뒤의 다음 단계는 review-loop(spec)** — 3.5는 spec ledger 종결 전 단계이므로 완료 직후 plan 직행·harden-spec 회귀는 없다 |
| harden-spec | 종료 권고에 조건부 한 줄: "spec이 새 화면/구성 변경을 포함하면 review-loop 전에 ui-mockup 권고" |

## 7. 성공 기준 (acceptance criteria)

- UI 없는 spec·경미 변경(구조 변경 미만)·spec 부재 단독 호출에서는 실행되지 않는다(트리거·하한·파이프라인 전용 판정).
- 신규 프로젝트 첫 실행: 4종 발산 → 선택(조합·전부 거부 시 재발산 1회 포함) → style-guide.md 생성 → spec에 UI 설계 + 재논의 금지 기록 → 커밋 → 정지.
- 기존 UI 프로젝트 첫 실행: 유지(역추출)/리뉴얼 모드 선택이 제시되고, 유지 선택 시 역추출 가이드 승인 → 레이아웃 변형 경로로 진행된다.
- 가이드 존재 시: 레이아웃 변형 2~3종만 생성한다(스타일 재발산은 명시 요청 시만). 새 컴포넌트 규칙은 확정 시 가이드에 증분 추가된다.
- 발산은 어떤 경로로도 총 2라운드를 넘지 않는다(초기 1 + 전부 거부 재발산 1). 다중 화면 최종 확인은 발산 라운드에 불산입.
- 선택 없이 목업이 확정되는 경로가 없다 — **조합본**과 다중 화면의 나머지 화면도 결과 최종 확인 후에만 spec 기록·커밋된다(writing-skills 베이스라인 테스트로 검증).
- 3.5 완료(또는 생략) 기록 후 dev-cycle의 다음 판별은 review-loop(spec)이다 — 완료 직후 plan 직행·harden-spec 회귀 경로가 없다.
- 재생성이 대상 경로의 미커밋 변경을 덮어쓰기 전에 반드시 보존 확인(선커밋/새 슬러그/중단)을 거친다.
- `docs/design/<feature>/`만 있고 spec `## UI 설계` 기록이 없는 상태(중단·잔재)는 완료로 판정되지 않는다 — dev-cycle은 3.5를 다시 권하고, 진입 시 재개/재생성/슬러그 변경 확인을 받는다.
- 경로 구분자·`..`·절대경로가 든 슬러그는 거부된다(베이스라인 테스트 포함).
- 다른 spec의 `## UI 설계`가 소유한 디렉터리와 슬러그가 충돌하면 재사용·재생성이 거부되고 슬러그 변경을 요구한다(충돌 사례 베이스라인 테스트 포함).
- 목업·비교 페이지는 비실행 검증(허용 목록 — 정적 마크업·인라인 CSS·정적 SVG — 외 활성 콘텐츠 전부 거부)을 통과하고, 재개 시 기존 후보에도 같은 검증이 재적용된다.
- review-loop(impl) 종료 요약이 수동 대조를 1회 안내하고, writing-plans-split이 UI 기능의 task 파일에 목업 경로를 구현 계약으로 명기한다.
