## 1. 문제

**(0) 운영 배경 — 메인 세션 오케스트레이터 모드(2026-10-17 사용자 기술).** ops-hub는 메인 세션을 두고 트랙 작업은 별도 워크트리 세션을 메인이 `.dev/brief.md`로 띄워 시작한다. 컨텍스트 넛지에 따른 후계 세션 생성도, spec→plan 같은 단계 전환도 메인이 지시한다. 사용자 질문(AskUserQuestion)은 리스크가 크거나 되돌릴 수 없는 작업만 사용자에게 가고, 나머지는 메인 세션이 추천안을 트랙 세션 터미널로 전달한다. 즉 플러그인이 전제한 「세션 안의 사람」 역할을 메인 세션이 대행한다. 10-10~10-17 실측: 실세션 33 · 트랙 세션 첫 메시지는 전부 메인의 브리프 지시 · 추천안 수용 102/107 · 메인 세션 자신은 후계 자동 인계를 8회 사용 · 트랙 세션이 브리프와 달리 스스로 인계한 사례 3건.

**사용자 지시(2026-10-17, harden 중)**: 오케스트레이션 관련 기능은 개별 스위치를 늘리지 않고 **모드 선택** 하나로 묶는다 — **수동** = 사람이 단계별로 확인하며 진행 / **위임** = 야간작업·휴가 때 에이전트에 맡겨 자동 진행. 사용 경계 = 브레인스토밍·harden-spec·ui-mockup처럼 **사람이 해야 하고 취향이 반영되는 단계**는 사람이 하고, 그 뒤 단계(review-loop(spec)부터)를 수동 또는 위임으로 진행한다. 기능 추가는 최소로.

**(a) 보안 크리티컬 트랙 질문의 반복.** review-loop는 루프 시작 시 변경 접촉면이 ESCALATE 즉시군(권한·인증·보안 경계·데이터 손상/유실·비가역 마이그레이션)에 닿으면 「보안 크리티컬 트랙으로 취급할지」를 사용자에게 1회 묻는다. ops-hub에서 이 질문이 16일간 **24회** 나왔다(10-10~17 7일은 0회 — 표본 작음). 오케스트레이터(main 세션)가 이미 판정해 브리프에 「보안 크리티컬 트랙 승계, 사용자 재질문 불필요」라고 적은 사례도 있다 — 그런데 그 판정을 루프에 넘길 공식 입력이 없어, 루프는 문면을 읽고 알아서 건너뛰거나 다시 묻는다. 답이 확인된 11건 중 2건은 추천(일반)과 다른 선택(보안)이었다 — 질문 자체는 필요하지만, 이미 정해진 값을 다시 물을 필요는 없다.

**(b) 위임 운영과 후계 자동 인계의 충돌.** 1.0.0부터 오르카 터미널(`ORCA_TERMINAL_HANDLE`)의 세션은 컨텍스트 넛지 때 같은 체크아웃에 후계 claude를 직접 띄운다. ops-hub는 main 세션이 트랙 터미널을 띄우고 「후계 세션은 main이 띄운다」를 브리프에 적는 운영이 있다(main이 트랙 터미널 핸들을 추적·감시해야 하므로). 1.0.x 넛지 104회 중 **12회**가 이 충돌이었다 — 모델이 브리프를 우선해 인계하지 않았으므로 결과는 옳았지만, 매번 ≈20KB 인계 절차문을 받고 그것을 거부하는 구조다(컨텍스트 낭비 + 브리프 문면에 의존한 우연한 정답). 10-10~17에는 반대로 트랙 세션이 스스로 인계한 사례가 3건이다. 이 세션만 자동 인계를 끄는 공식 입력이 없다. 2026-09-24 spec D8은 「끄기 스위치 없음」이었다 — 이 spec이 그것을 대체한다(§재논의 금지).

## 3. 설계

### 3m. 세션 모드 — 수동 / 위임 (D3·D8·D9)

- **환경변수 `DEV_WORKFLOW_MODE`** — 값이(앞뒤 공백 제거 후) 정확히 `delegated`면 **위임**, 미설정·빈 값·그 외 값(`DELEGATED`·`manual`·`orchestrated`·`off` 등)은 **수동(기본)**. 훅은 `process.env`로, 스킬은 셸로 읽을 수 있는 공통 입력이다(1.1.0에서 스킬 효과는 없다).
- **뜻**: 위임 = 이 세션의 사용자 역할을 에이전트(오케스트레이터, 통상 메인 세션)가 대행한다 — 질문은 오케스트레이터가 답하고 후계도 오케스트레이터가 띄운다. **메인 세션 자신은 수동**(사람이 답한다)이며 자기 후계는 1.0.0 자동 인계 그대로 — 위험군 질문만 사용자를 기다린다.
- **선택 지점**: 브레인스토밍·harden-spec·ui-mockup(사람·취향 단계)은 모드와 무관하게 사람이 한다. 그 뒤 review-loop(spec)부터 트랙을 수동 또는 위임으로 띄운다. dev-cycle §단계 경계에 이 1줄을 둔다.
- **설정 단위 = 트랙 터미널**(D8): 오케스트레이터가 트랙 터미널을 만들 때 실행 명령 앞에 붙인다 — `orca terminal create … --command 'DEV_WORKFLOW_MODE=delegated claude …'`(1.0.1 실측: `--command`의 환경변수 접두는 claude 프로세스에 적용된다 — `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1 claude` 사례). **후계 터미널을 띄울 때도 같은 접두**를 붙인다(빼먹으면 그 후계만 자동 인계로 돌아간다 — 현행과 같음). Windows 오르카(PowerShell)는 `$env:DEV_WORKFLOW_MODE='delegated'; claude …` 형태(미실측, 범위 밖). settings.json `env`로 프로젝트 전체에 걸면 메인 세션까지 위임이 되어 자기 인계를 못 하므로 기본 안내가 아니다(README는 접두를 기본으로, settings `env`는 「메인 세션도 꺼진다」 주의와 함께만).
- **확장 규칙**(사용자 지시 2026-10-17): 향후 오케스트레이션 관련 추가·개선은 새 스위치가 아니라 **이 모드의 효과 목록에 더한다**. 1.1.0 효과 = §3b 하나.
- **중첩 claude**(README 240행 경고의 해결책, 이전 세션 G7): 오르카 탭 안에서 불가피하게 중첩 `claude`(`claude -p …`·tmux 속 claude)를 띄워야 하면 `DEV_WORKFLOW_MODE=delegated claude -p …`로 띄운다 — 부모 탭 핸들을 물려받아도 후계를 스폰하지 않는다.

### 3a. `--security yes|no` (D1·D2·D10) — 모드와 독립

- §인자에 추가: `--security yes|no` — 보안 크리티컬 트랙 판정을 호출자가 미리 지정한다(「사용자가 이미 내린 판정을 넘길 때 쓴다」). **어느 모드에서든** 인자가 있으면 묻지 않는다(M2). 생략하면 현행대로 루프가 접촉면을 보고 필요 시 1회 묻는다.
- §1 「보안 크리티컬 자가 판정」: 인자가 있으면 **질문하지 않고** 그 값을 판정 상태로 확정한다(`yes`는 접촉면과 무관하게 보안 트랙). 판정 상태 기록에 출처를 붙인다 — `보안 크리티컬: yes (호출자 지정)` / `no (호출자 지정)` / 현행 `yes|no (사용자 확인)`·`해당 없음(접촉면 무관)`.
- **기록 위치(D1, 이전 세션 G8)**: 모든 루프(인자 없을 때도)에서 보안 트랙 판정·출처·감지된 접촉면을 **ledger 절 첫 줄 + §4 종료 요약**에 1줄씩 적는다 — 예: `보안 크리티컬: no (호출자 지정) — 접촉면 권한 감지` / `해당 없음(접촉면 무관)`.
- **`no` 지정 + 접촉면이 즉시군에 닿는 경우(D1)**: 묻지 않고 `no`를 따르되 위 기록에 더해 **루프 시작 요약(채팅)에 같은 1줄**을 찍는다. 사후 감사 + 오케스트레이터가 터미널에서 바로 보고 중단·재시작을 판단할 수 있게 한다. 루프 동작은 바꾸지 않는다.
- **재개와 함께 올 때(D2)** — 명시 `--resume`과 루프 파일 자동 감지 모두: 복원한 판정 상태가 권위다. ① 인자 값이 복원 값과 다르면 리뷰를 돌리지 말고 사용자 확인 1회(fail-closed — §0 통합 규칙 「재개 인자가 저장값과 불일치」와 같은 처리). ② 복원 값이 없으면(1.0.3 이전 루프 파일·필드 없음) 인자를 채택하고 출처 「호출자 지정」. ③ 둘 다 없으면 현행 자가 판정.
- 그 외 값(`true`·`1`·빈 값 등)은 인자 오류로 시작 전에 멈추고 보고한다.
- `--auto-rounds`와 독립(D10). README에 「보안 트랙은 `--auto-rounds 1` 병기 권고」 1줄.

### 3b. 위임 모드의 후계 인계 (D4)

- `resolveOrcaHandle(env)`: `typeof env.DEV_WORKFLOW_MODE === "string" && env.DEV_WORKFLOW_MODE.trim() === "delegated"`면(D3 — 앞뒤 공백·개행 제거 후 정확 일치) `null`을 돌려준다 → `decideNudge`는 **오르카 밖 경로와 바이트 동일한 넛지**((2) = `/clear` 안내)를 낸다. 그 외는 현행(핸들 안전 문자 집합 검사 포함). 변경 지점 1곳, `decideNudge`·인계 문면·(0)·(1) 무변경.
- **review-loop §2i 순서 3 ① 재개 안내(이전 세션 G3)**: 현행 「오르카 터미널이면 후계를 스폰 / 오르카 밖이면 /clear 안내」를 **넛지 (2)의 내용 기준**으로 고친다 — 「(2)가 후계 생성 절차면 … / (2)가 /clear 안내면 …」. 위임 모드 세션은 오르카 안에서도 /clear 안내를 받으므로 환경 기준 문면은 틀린 안내가 된다.
- 귀결: 오르카 밖(핸들 없음)에서 위임 모드는 no-op. 오염된 환경(핸들 안전 집합 이탈)과 위임은 같은 출력이라 로그만으로 구분되지 않는다 — 수용(G3, 값은 셸에서 확인).
