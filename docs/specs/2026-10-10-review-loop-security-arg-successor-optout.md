## 1. 문제

**(0) 운영 배경 — 메인 세션 오케스트레이터 모드(2026-10-17 사용자 기술).** ops-hub는 메인 세션을 두고 트랙 작업은 별도 워크트리 세션을 메인이 `.dev/brief.md`로 띄워 시작한다. 컨텍스트 넛지에 따른 후계 세션 생성도, spec→plan 같은 단계 전환도 메인이 지시한다. 사용자 질문(AskUserQuestion)은 리스크가 크거나 되돌릴 수 없는 작업만 사용자에게 가고, 나머지는 메인 세션이 추천안을 트랙 세션 터미널로 전달한다. 즉 플러그인이 전제한 「세션 안의 사람」 역할을 메인 세션이 대행한다. 10-10~10-17 실측: 실세션 33 · 트랙 세션 첫 메시지는 전부 메인의 브리프 지시 · 추천안 수용 102/107 · 메인 세션 자신은 후계 자동 인계를 8회 사용 · 트랙 세션이 브리프와 달리 스스로 인계한 사례 3건.


**(a) 보안 크리티컬 트랙 질문의 반복.** review-loop는 루프 시작 시 변경 접촉면이 ESCALATE 즉시군(권한·인증·보안 경계·데이터 손상/유실·비가역 마이그레이션)에 닿으면 「보안 크리티컬 트랙으로 취급할지」를 사용자에게 1회 묻는다. ops-hub에서 이 질문이 16일간 **24회** 나왔다. 오케스트레이터(main 세션)가 이미 판정해 브리프에 「보안 크리티컬 트랙 승계, 사용자 재질문 불필요」라고 적은 사례도 있다 — 그런데 그 판정을 루프에 넘길 공식 입력이 없어, 루프는 문면을 읽고 알아서 건너뛰거나 다시 묻는다. 답이 확인된 11건 중 2건은 추천(일반)과 다른 선택(보안)이었다 — 질문 자체는 필요하지만, 이미 정해진 값을 다시 물을 필요는 없다.

**(b) 오케스트레이터 운영과 후계 자동 인계의 충돌.** 1.0.0부터 오르카 터미널(`ORCA_TERMINAL_HANDLE`)의 세션은 컨텍스트 넛지 때 같은 체크아웃에 후계 claude를 직접 띄운다. ops-hub는 main 세션이 트랙 터미널을 띄우고 「후계 세션은 main이 띄운다」를 브리프에 적는 운영이 있다. 1.0.x 넛지 104회 중 **12회**가 이 충돌이었다 — 모델이 브리프를 우선해 인계하지 않았으므로 결과는 옳았지만, 매번 ≈20KB 인계 절차문을 받고 그것을 거부하는 구조다(컨텍스트 낭비 + 브리프 문면에 의존한 우연한 정답). 이 세션만 자동 인계를 끄는 공식 스위치가 없다.

## 2. 목표 / 범위 / 비목표

**목표** — (a) 호출자가 보안 트랙 판정을 미리 넘기면 루프가 다시 묻지 않는다. (b) 호출자가 지정한 세션은 오르카 안에서도 후계 자동 인계 대신 기존 `/clear` 안내 넛지를 받는다.

**범위** — review-loop 인자 1개(`--security`)와 그 판정 상태 기록, 훅 환경변수 1개(D3)와 오르카 경로 선택 분기, README 3종 문서화, 1.0.4 릴리스.

**비목표** —
- **추천안 자동 채택(오케스트레이터 모드) 인자는 이 패치 밖.** harden-spec 「질문 없이 닫히는 판단 갭은 없다」·review-loop batch 규약은 무변경. 규약 성장이므로 무인 결정 번복률 실측(dev-workflow-eval `BRIEF-unattended-harden-2026-09-18.md`, 2026-10-17 착수) 결과를 보고 별도 트랙으로 판정한다(L1).
- 보안 크리티컬 판정 기준(ESCALATE 즉시군)·보안 트랙의 의미(score 정체 신호 무시) 무변경.
- 브리프 문면을 훅이 읽어 자동 판단하지 않는다(훅은 환경만 본다).
- 오르카 인계 절차(2-0)~(2-5)·후계 프롬프트 무변경.
- ops-hub 쪽 터미널 생성 절차 변경은 이 repo 밖(9단계 후속에서 안내만).

## 3. 설계

### 3a. `--security yes|no` (D1·D2)

- §인자에 추가: `--security yes|no` — 보안 크리티컬 트랙 판정을 호출자가 미리 지정한다. 생략하면 현행대로 루프가 접촉면을 보고 필요 시 1회 묻는다.
- §1 「보안 크리티컬 자가 판정」: 인자가 있으면 **질문하지 않고** 그 값을 판정 상태로 확정한다. 판정 상태 기록에 출처를 붙인다 — `보안 크리티컬: yes (호출자 지정)` / `no (호출자 지정)` / 현행 `yes|no (사용자 확인)`·`해당 없음(접촉면 무관)`.
- `no` 지정인데 접촉면이 즉시군에 닿는 경우(D1 초안): 묻지 않고 `no`를 따르되 ledger 머리에 1줄 기록 — `보안 크리티컬: no (호출자 지정) — 접촉면 <계열> 감지`. 사후 감사용이며 루프 동작은 바꾸지 않는다.
- `--resume`과 함께 오면(D2 초안): 복원한 판정 상태가 권위다. 인자 값이 복원 값과 다르면 리뷰를 돌리지 말고 사용자 확인 1회(fail-closed — 루프 중간에 트랙 성격이 바뀌면 score 이력 해석이 달라진다). 같으면 그대로 진행.
- 그 외 값(`true`·`1`·빈 값 등)은 인자 오류로 시작 전에 멈추고 보고한다.

### 3b. 후계 자동 인계 opt-out (D3·D4·D5)

- 환경변수 `CLAUDE_CTX_SUCCESSOR`(D3 초안 — 기존 `CLAUDE_CTX_THRESHOLD`·`CLAUDE_CTX_LIMIT`과 같은 접두): 값이 정확히 `off`면 훅은 `ORCA_TERMINAL_HANDLE`이 있어도 **오르카 밖 경로와 바이트 동일한 넛지**((2) = `/clear` 안내)를 낸다(D4). 그 외 값·미설정은 현행.
- 구현 위치: `resolveOrcaHandle(env)`가 opt-out이면 `null`을 돌려준다 — 경로 선택 한 곳만 바뀌고 `decideNudge`·인계 문면은 무변경(D4).
- 설정 방법(D5·D8): 오케스트레이터가 트랙 터미널을 만들 때 실행 명령 앞에 붙인다 — `orca terminal create … --command "CLAUDE_CTX_SUCCESSOR=off claude …"`(1.0.1 실측: `--command`의 환경변수 접두는 claude 프로세스에 적용된다). settings.json `env`로 프로젝트 전체에 걸면 메인 오케스트레이터 세션까지 꺼져 자기 인계를 못 하므로(D8), README는 터미널 접두를 기본으로 안내하고 settings `env`는 「메인 세션도 끈다」는 주의와 함께만 적는다.

## 4. Acceptance Criteria

- **AC1 (훅 — opt-out)**: `ORCA_TERMINAL_HANDLE=term_x` + `CLAUDE_CTX_SUCCESSOR=off`로 임계 초과 입력을 주면 reason이 `ORCA_TERMINAL_HANDLE` 미설정 때의 reason과 **바이트 동일**하다.
- **AC2 (훅 — 기본 유지)**: `CLAUDE_CTX_SUCCESSOR` 미설정·빈 값·`OFF`·`false`·`0`이면 현행 오르카 경로(reason에 `(2-0)`·핸들 포함).
- **AC3 (훅 회귀)**: 기존 훅 테스트 11케이스(`.remember/hook-test-1.0.0/`) GREEN 유지.
- **AC4 (review-loop 문면)**: §인자에 `--security yes|no` 행, §1 보안 자가 판정에 「인자 있으면 질문 없이 확정 · 출처 기록」, `no`+즉시군 1줄 기록, `--resume` 불일치 시 확인, 잘못된 값 시작 전 중단 — 각 grep 1건 이상. §0·§2i 복원 필드의 「보안 크리티컬 트랙 판정 상태」가 출처를 포함한다고 명시.
- **AC5 (문서)**: README 3종에 `--security`와 `CLAUDE_CTX_SUCCESSOR=off` 설명(설정 위치·용도) 각 1곳 — opt-out은 트랙 터미널 생성 명령 접두를 기본으로, settings.json `env`는 메인 세션까지 꺼진다는 주의 문구 동반(D8).
- **AC6 (릴리스 뒤 실측)**: spark2 1.0.4 설치본에서 (i) `CLAUDE_CTX_SUCCESSOR=off`·낮은 임계로 띄운 오르카 세션의 넛지가 `/clear` 안내형 (ii) `--security yes`로 시작한 review-loop가 보안 질문 없이 시작해 판정 상태에 「호출자 지정」을 기록 — 각 1회.
