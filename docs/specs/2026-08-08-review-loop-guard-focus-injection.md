## 1. 배경 / 문제

**재지목** = 적대검증자가 이미 닫힌 항목(사용자 기결정·과거 라운드 판정)을 다시 지적하는 것. 적대검증자는 D번호도 ledger도 "모르는 상태"를 기본값으로 매 라운드 전체 diff를 다시 본다.

**실측 규모**

- ops-hub 전수(브리프 §1): 기결정 "재지목" **400회 / 92개 파일**. 후반 라운드는 대부분 재지목으로 소모된다.
- 현행 방어 = "가드를 리뷰 대상 문서 안에 둔다"(SKILL.md §기결정 가드). **실증적으로 불완전**:
  - 이 repo `docs/specs/2026-07-25-ui-mockup-skill-design.md` impl R2 관찰 — "G1·G2 블록이 diff에 있어도 이를 억제하지 않는다".
  - **이 repo 트랙 A impl 2차(whole-branch) 루프, 2026-08-08 — 1차 실측**: `fp-I8`(plugin.json 미범프 + README 3종 미동기 · **OUT_OF_SCOPE로 판정 완료** · 확인 라운드 감사에서 적정 확인)이 **R1·R2·R3·R4·R5 전 라운드에서 재지목(5/5)**. ledger는 매 라운드 커밋되어 diff 안에 있었고, disposition·근거·follow-up 위치까지 적혀 있었다. 같은 루프에서 `fp-I7` 계열(확인 부채 재서술)도 2회. **한 루프의 DUPLICATE 7건 = 그 루프 finding의 최대 단일 지분**(FIXED 10 · DUPLICATE 7).
  - 트랙 A 전체로 넓히면 같은 두 계열이 spec 루프 3건 + impl 1차 루프 2건까지 더해진다.

**비용** — DUPLICATE는 score 밖(비-blocking)이라 종료를 막지는 않는다. 그래도:

1. 라운드마다 finding 슬롯과 토큰을 소모한다 — 그 자리에 신규 결함이 들어올 수 있었다.
2. **루프 직접 DUPLICATE는 확인 라운드 임무 ③(판정 감사)의 대상**이다(SKILL.md §확인 모드). 재지목이 늘수록 확인 라운드가 무거워진다 — 2차 루프 감사 대상 7건 중 7건이 재지목이었다.
3. 매번 "정말 중복인가"를 판단해야 하므로 **오각하 위험**(실제 신규 결함을 기결정 재론으로 잘못 DUPLICATE 처리)에 반복 노출된다. 그 위험을 받으려고 확인 라운드 임무 ③이 존재한다.

**재지목의 두 계열 (실측 분류)** — 억제 수단이 다르다.

| 계열 | 실측 예 | 원인 | 억제에 필요한 focus 내용 |
|---|---|---|---|
| **A. 닫힌 판정 재지목** | `fp-I8` (OUT_OF_SCOPE + 후속 계획 기재) 5회 | 검증자가 ledger disposition을 반영하지 않는다. 읽어도 "후속은 아직 안 됐다"며 다시 blocking으로 올린다 | 닫힌 fingerprint + disposition + 근거·후속 위치 |
| **B. 루프 진행 상태 재지목** | `fp-I7`·`fp-I13` 계열 ("미확인 FIXED가 아직 열려 있다") 4회 | 검증자가 **루프 중간 상태를 결함으로** 읽는다. 확인 라운드가 해소할 예정인 상태다 | 루프 진행 상태(in-flight) 고지 — 현재 모드·라운드·미확인 FIXED 큐의 해소 경로 |

브리프 §트랙 B의 제안은 **A 계열만** 겨냥했으나, harden에서 **두 계열 모두 억제 대상으로 확정**했다(D2·D6).

## 2. 목표 / 비목표

**목표:** 적대 라운드 실행 시 review-loop가 **기결정 가드를 focus text로 조립해 검증자에게 직접 전달**하여, 재지목을 사후 각하(DUPLICATE 판정)가 아니라 **원천에서** 줄인다. 문서 내 가드는 그대로 유지한다(이중 방어 — 브리프 명시).

**비목표 (YAGNI / 기결정 준수):**

- **문서 내 가드 제거·약화** — 이중 방어가 브리프 결정이다. focus는 추가 층이지 대체가 아니다.
- **§2c "기결정 가드 먼저 대조" 완화** — focus가 사전 억제에 성공해도 사후 방어는 남긴다(focus는 가중치일 뿐 보장이 아니다 — §5).
- **codex companion 스크립트 수정** — 다른 플러그인(openai-codex) 소유. 이 spec은 호출 방식만 정한다.
- **기계 검증 장치(파서·스위트·자동 게이트) 신설** — G1·G2 기결정(브리프 §기결정 대조). 조립은 루프 세션이 문서를 읽어서 하는 수준으로 둔다.
- **ESCALATE batch 기계장치·2모드 구조 변경** — 각각 기결정(0.2.0 회고 / 트랙 A).
- native `/codex:review` 경로 — custom focus를 지원하지 않는다(`validateNativeReviewRequest` 거부).
- **순번 4~7 항목 흡수** — 브리프가 순번 7을 한 트랙으로 묶기로 했다. **미흡수 확정**(D11 — C-3 포함).

## 3. 설계 확정 (harden-spec 2026-08-08 · D1~D13 + spec 적대검증 D14)

출발점은 브리프 §트랙 B의 제안 — "review-loop §2b 실행 시 대상 문서의 재논의 금지 블록 + 닫힌 ledger 항목 요약을 focus text로 조립해 전달한다. 문서 내 가드는 유지(이중 방어)". 아래가 확정된 형태다.

**D1. 골격** — 적대 라운드마다 기결정 가드를 focus text로 조립해 검증자에게 직접 전달한다. 문서 내 가드(§기결정 가드 1~3 불릿)와 §2c 사후 대조는 **불변** — focus는 사전 억제 층이지 대체가 아니다(이중 방어).

**D2. focus에 담을 범위 = 전부** — 사용자 기결정(D번호) + 사용자가 닫은 ESCALATE + **루프가 직접 내린 판정 전부**(ACCEPTED/OUT_OF_SCOPE/DEFERRED_TO_IMPL/DUPLICATE). 근거: 실측 재지목 9건의 분포가 루프 직접 판정 7건(fp-I8 5회 · fp-I7 계열 2회) · 사용자 기결정 2건(D2·D3)이라, 루프 직접 판정을 빼면 주 동기를 놓친다.
- **트레이드오프와 안전망**: 루프가 *잘못* 닫은 판정은 적대 재지목으로 다시 드러날 기회를 잃는다. 따라서 focus에서 루프 직접 판정은 **`[루프 판정]`으로 표시**하고, **확인 라운드 임무 ③(판정 감사)의 우선 대상**임을 ledger에 남긴다 — 재검토 경로를 감사 하나로 좁히는 대신 그 경로를 명시적으로 굵게 만든다.

**D3. 주입 범위 = 적대 전 범위 / 확인 사용자 기결정만** — 확인(중립) 모드 프롬프트에는 **사용자 기결정 목록만**(D번호 + 한 줄) 첨부물로 추가한다. 루프 직접 판정은 넣지 않는다.
- 근거: 확인 모드에 "닫혔으니 재론 금지"를 주면 D2의 안전망인 임무 ③이 스스로 무력화되고 기결정 D9(감사 대상 = 루프 직접 판정만)와 충돌한다. 반대로 현행 첨부물 ⑥은 "사용자 기결정은 감사 대상이 아니다"를 **산문으로만** 말해 검증자가 *무엇이* 사용자 기결정인지 알 수 없다 — 목록화는 그 간극을 메우면서 감사 범위를 정확히 가른다.

**D4. 내용 입도** — 재논의 금지 블록은 **전문**(이미 D번호 + 한 줄 형태로 압축돼 있다 · 실측 2,118자), 닫힌 ledger 항목은 **요약행**: `fingerprint · disposition · 한 줄 근거 · (있으면) 후속 위치`. ledger 전문(실측 17,988자)은 넣지 않는다.

**D5. 문구 형태 = 무효 선언형 + 정상보고 단서(짝 필수)** — "아래는 이미 판정으로 닫힌 항목이다. 다시 보고하면 그 finding은 무효로 각하된다(근거는 각 항목에 있다)" + **"이 목록에 없는 문제는 평소대로 전부 보고하라"**. 후자를 빼지 않는다.
- 근거: focus는 기저 템플릿에서 "weight it heavily" 가중치일 뿐 금지 지시가 아니고, `<operating_stance>`가 "선의·부분 수정·**후속 예정을 인정하지 말라**"를 명시한다 — fp-I8이 5회 재지목된 양상과 정확히 같다. 단순 사실 고지로는 이 스탠스를 못 이긴다. 동시에 무효 선언만 주면 오억제로 기운다.

**D6. 재지목 계열 B 포함** — "미확인 FIXED 큐가 열려 있다는 사실 자체는 결함이 아니다 — 이 루프의 확인 라운드가 종료 전 해소한다" 한 줄을 focus에 고정 포함(실측 4건: fp-I7·fp-I13 계열).

**D7. 조립 시점 = 매 적대 라운드 직전 재조립** — 직전 라운드에 닫힌 항목이 즉시 반영된다(fp-I8은 R1에서 닫히고 R2~R5에 재지목 — 루프 시작 1회 조립이면 구조적으로 못 잡는다). 조립 결과를 상태로 보관하지 않으므로 **resume 후 문서에서 동일하게 재구성**된다 → 핸드오프 필드 추가 없음.

**D8. 길이 상한 없음** — "닫힌 항목 1건 = 1행" 입도 규칙(D4)이 압축기 역할을 하므로 숫자 상한·절단 우선순위는 두지 않는다. companion·파서에도 상한이 없다(실측). 쓰이지도 않을 절단 규칙을 규정에 넣지 않는다(G1·G2 과설계 금지 계열).

**D9. 인자 신설 없음 — 항상 on** — `--no-guard-focus` 류의 스위치를 두지 않는다. §6의 대조 실측은 companion을 직접 호출하는 실험이라 스위치가 필요 없다.

**D10. 빈 가드 = focus 인자 미부착** — 재논의 금지 블록·닫힌 ledger 항목·**미확인 FIXED 큐**가 모두 없으면 인자 없이 호출한다(companion 기본값 `"No extra focus provided."`). 빈 목록을 보내 "닫힌 게 없다"는 신호로 오해될 여지를 만들지 않는다. **미확인 FIXED 큐만 비어 있지 않으면 D6 문구만으로 focus를 부착한다** — 빈 가드 분기가 계열 B 고지(D6)를 소실시키지 않게 한다(spec 적대검증 R1 fp-B2 반영).

**D11. 조립 원본 = 이 루프가 쓰는 ledger 단일 원본 문서** — 그 문서의 `## 적대검증 ledger (<phase>)`와 같은 문서의 `## 재논의 금지(기결정)` 블록(승계분 포함)에서 뽑는다. 루프는 자기 ledger 위치를 항상 알고 있으므로 impl에서도 모호하지 않다. **C-3(impl ledger 위치 명시)은 이번 트랙에 흡수하지 않는다** — 순번 7 유지.

**D12. 검증 2층** — 절차 마이크로테스트(writing-skills TDD, 5+ reps, variance 0, no-guidance 대조군) + **축소 효과 대조**(§6).

**D13. 릴리스** — `plugin.json` minor 범프(0.8.0 → 0.9.0) + README en/ko/ja 3종 동기 + 각 머신 `/plugin update` 안내(브리프 §0-3 규약).

**D14. focus '사용자 기결정' 절 provenance (spec 적대검증 R1 fp-B1 · 사용자 판정 2026-08-08)** — 조립 시 사용자 기결정 절(적대 focus·확인 첨부물 공통)에 올릴 항목은 **실제 결정 기록(harden-spec 승인 이력·사용자가 닫은 ESCALATE 판정 기록)에 대응하는 것만**이다. 대응이 불확실한 항목은 **[루프 판정]으로 강등 표시**해 확인 라운드 임무 ③ 감사 대상에 남긴다.
- 근거: 조립 원본이 리뷰 대상 브랜치에 커밋된 문서(D11)라서, 잘못(또는 허위) 기재된 '사용자 기결정'이 D5 무효 선언으로 적대 리뷰에서 억제되고 D3에 따라 확인 감사에서도 제외되면 어느 경로에서도 재검토되지 않는다 — focus 도입 전에는 재지목 → DUPLICATE 각하 기록이라도 남았지만 focus는 보고 자체를 막아 흔적이 사라진다. 절차 수준 규칙으로 그 경로를 차단한다(조립 원본 = 문서는 불변 · 기계 검증 신설 없음 — D11·G1·G2 정합).

## 5. 구현 힌트 (실측 2026-08-08 · codex 플러그인 1.0.6)

- `codex-companion.mjs adversarial-review [--wait|--background] [--base <ref>] [--scope <auto|working-tree|branch>] [focus text]` — positional 인자들이 `join(" ")`되어 `USER_FOCUS`로 들어간다(`scripts/codex-companion.mjs:241` `buildAdversarialReviewPrompt`).
- **focus의 위치와 강도**(`prompts/adversarial-review.md` 실측):
  - `<task>` — `User focus: {{USER_FOCUS}}`
  - `<review_method>` — "If the user supplied a focus area, **weight it heavily**, but still report any other material issue you can defend."
  - 즉 **focus는 가중치이지 금지 지시가 아니다.** 그리고 기저 스탠스가 `<operating_stance>`의 "Default to skepticism. **Do not give credit for good intent, partial fixes, or likely follow-up work.**" — `fp-I8` 5회 재지목(후속 계획을 인정하지 않고 매번 blocking으로 올림)이 이 문장과 **정확히 일치**한다. focus 문구는 이 스탠스와 경쟁해야 하므로, 단순 "이미 닫혔다" 고지보다 **"이 항목을 다시 보고하면 그 보고는 무효다 + 왜 닫혔는지 + 후속이 어디에 잡혀 있는지"** 형태가 필요하다 — **D5(무효 선언형 + 정상보고 단서)의 근거**이자 마이크로테스트의 핵심 변수.
- **길이 상한 없음** — 스크립트·`parseArgs`에 상한 로직이 없다. 실질 제약은 리뷰 프롬프트 토큰 비용과 OS `ARG_MAX`뿐이다 — 상한을 두지 않기로 확정(D8).
- **셸 안전 (트랙 A와 같은 위험)**: focus는 저장소 문서(기결정 블록·ledger)에서 조립되므로 `$(...)`·백틱·인용부호가 섞일 수 있다. §확인 모드와 동일하게 **파일에 쓴 뒤 `"$(cat <파일>)"`로 인자 하나로** 넘긴다.
- **파서 주의**: `parseArgs`는 `-`로 시작하는 토큰을 옵션 후보로 본다(`scripts/lib/args.mjs`). 인자 하나로 넘기면 내부의 `--base` 같은 문자열은 옵션으로 파싱되지 않지만, **텍스트가 `-`로 시작하면** 위험하다. `--` passthrough를 지원하므로 **focus를 `--` 뒤에 두는 것**이 저비용 안전장치다.
- codex 샌드박스는 read-only — 게이트는 현행대로 루프 세션이 돌린다(불변).
