## 3. 설계 (문면 방향 — 최종 문구는 구현에서)

### F1. codex 라운드 실행 신뢰성

현행 실패 모드 4종:
- (a) 포그라운드 Bash 도구 timeout(기본 2분·최대 10분)이 라운드 소요(10~16분)보다 짧다 → `--wait` 직접 실행이 죽는다. 08-03~04 "`--wait` 직접 실행으로 리뷰 2회 소실".
- (b) companion `--background`는 프로세스를 분리하지 않는다(Windows, 08-29).
- (c) /clear는 분리한 프로세스도 회수한다(09-04).
- (d) 원인 불명의 조기 사망(74초·82초)과 하네스 저메모리 kill(09-07·09-14).

방향:
1. **분리 실행 + 출력 파일 + 종료 마커.** companion 호출을 출력 파일로 리다이렉트하고 끝에 `COMPANION_EXIT:<code>` 줄을 붙이는 한 줄 래퍼로 감싸, 셸에서 분리 실행한다. POSIX는 `setsid nohup … &`, Windows Git Bash는 PowerShell `Start-Process`. 대기는 마커 감시(Monitor 또는 until-loop)로 한다. ops-hub가 08-04 이후 전 트랙에 정착시킨 방식이다(C1, "R1 12분·R2 15분·R3 16분·C1 10분에 안정 회수").
2. **완료·유효 판정.** 마커가 있으면 완료다. 적대 응답은 `# Codex Adversarial Review` 헤더 + 스키마 JSON(+F3 조건), 확인 응답은 기존 응답 완전성 계약을 따른다. 마커 없이 프로세스가 사라졌으면 실행 실패다 — 기존 규칙대로 예산 미소모·원문 보고, 재실행은 사용자 판단.
3. **라운드 진행 중 금지 2종.** /clear(F6과 공유), 그리고 추적 파일 편집. 리뷰어가 디스크를 직접 읽기 때문이다(B12, 09-03~05 3회).
4. **회수 경로를 사용자 판단용으로 제시.** 적대(ephemeral 스레드)는 재실행뿐이다. 확인(`task`, 영속 스레드)은 출력의 `Thread ready (<id>)`로 스레드를 재개할 수 있다(09-04 1회 검증, 약 1분). companion `--resume-last`는 포그라운드 `task`에서 실패했다(state 미기록).
5. **`--help`·무인자 호출 금지 1줄.** 도움말이 아니라 실제 리뷰 job이 뜬다(B3, 09-02·09-10).
6. **확인 모드는 `task --prompt-file <파일>`로.** companion 1.0.6이 지원한다. 셸 보간 금지 규칙을 구조로 대체하고, argv로 전문이 프로세스 목록에 노출되던 문제(B17)도 함께 해소된다. 적대 `adversarial-review`는 argv만 받으므로 현행 유지.

실행을 산문으로 적을지, 스크립트로 동봉할지는 Q1.

### F2. companion 경로 해소 통일

RL의 캐시 glob + `sort -V | tail -1`을 doctor 기준(레지스트리 활성 엔트리의 `installPath`)으로 통일한다. doctor가 이 방식을 금지한 이유 2종이 RL에도 그대로 해당한다: 고아 캐시 버전 때문에 활성 설치본이 없어도 거짓 정상이 되고, zsh `nomatch`에서는 무매치 시 에러가 난다. 해소 시점은 Q2. 실사고가 0건이므로 우선순위는 harden이 판정한다.

### F3. 무효 리뷰 판별

1. **적대 응답 유효성에 실행 흔적 조건을 추가한다.** 스키마가 맞아도 명령 실행 로그가 없거나 샌드박스 오류(예: `bwrap:`)가 있으면 실행 실패로 처리한다. ops-hub의 판정 기준 원문: "90초 만에 approve로 끝나도 명령 실행 로그·헤더가 있으면 유효"(C10).
2. **focus에 고정 첫 줄을 둔다** — "읽기 전용 정적 검토: 테스트·빌드 실행을 시도하지 말 것(게이트는 루프가 실행)". 09-05 원문: "focus 첫 줄에 읽기 전용 … 지시를 넣으면 재발하지 않았다".
   - **파급**: 현행 "빈 가드 = focus 인자 미부착"(RL §2b) 분기가 사라진다(focus가 항상 존재). 빈 목록 오해를 막으려던 원래 취지와의 정합은 Q3.

### F4. task-brief 어댑터를 실행 계약 블록 안으로

WPS §Execution handoff(:89)의 어댑터 요지 2문장을 verbatim 계약 블록(:40)에 넣는다: ① 분할 plan에는 "Task N" 절이 없으니 task 파일 전문을 brief로 넘긴다 ② SDD workspace는 엔트리포인트 기준으로 둔다. 버전 표기 "SDD 6.2.0"도 갱신한다(설치본 superpowers 6.3.0에 `task-brief`·`sdd-workspace` 실재 — AUDIT).
- **파급**: 진행 중 plan의 계약 블록이 구판이 된다. 기존 plan 형식 관문 ①(RL:241 "어긋난 블록은 저비용 수정(블록 교체) … 교체 후 진행")이 루프 진입 시 흡수하므로 추가 규정은 필요 없다.

### F5. 해시 인용 규칙의 부수 비용 — **SLIM D15 재개방 사안**

- **문제**: spec·plan phase는 수정 대상과 ledger가 같은 문서라, 한 커밋에 자기 해시를 넣을 수 없다. 그래서 "수정+ledger 커밋 → 해시 채우기 커밋"이 반복된다(56~60건).
- **해시 수명**: 인용한 해시는 이력 재작성(filter-branch)이나 저장소 이전(GitLab 단일 초기 커밋, 09-15) 때 무효화된다.
- **유지할 요건**: 확인 모드는 수정 커밋 SHA가 필요하다(RL:158·:355). 어느 안이든 이 요건은 지킨다.
- **근거 반증**: 이 규칙은 감량 트랙 기결정 SLIM D15(재비대 방지 A1)다. 근거였던 "비용 ≈0"(0.15.0 단일 트랙 전건 인용)은 ops-hub 규모에서 반증됐다. 이 사실은 어느 안을 고르든 기록한다.

선택지(Q4):
- (i) **순서 규정** — 수정 커밋을 먼저 하고, ledger 행은 다음 커밋에서 해시를 인용한다. 되돌아가 채우는 커밋은 없어지지만 커밋 수가 줄지는 않을 수 있다.
- (ii) **라운드 표식으로 갈음** — spec·plan phase는 커밋 메시지의 라운드 표식(`R3` 등)으로 대신하고, `git log --grep`으로 기계 검증한다.
- (iii) **현행 유지** — 비용을 수용하고, 이력 재작성 시 SHA 매핑을 기록하는 1줄만 추가한다.

### F6. 넛지 후 폭주 차단

넛지의 의미를 "**현재 단위만 마무리하고 다음 단위를 시작하지 않는다**"로 명시한다.
1. **훅 문구**(모든 세션 공통 — 실행 세션이 서브에이전트를 띄우고 기다리는 경우도 같은 문제, B4):
   - ① 넛지 이후 새 작업 단위(새 리뷰 라운드·새 태스크 디스패치·새 수정) 착수 금지.
   - ② 진행 중인 백그라운드 작업이 있으면 사용자에게 "완료 전 /clear 금지"를 명시한다. 완료 알림을 받으면 결과를 기록만 하고 멈춘 뒤, 그때 /clear를 안내한다.
   - ③ 핸드오프 파일 = repo·트랙 규약의 핸드오프 파일(기본 `.remember/remember.md`, review-loop는 자기 루프 파일). 트랙별 파일 운용(C9)을 수용한다.
2. **RL §2i에 진행 중 라운드 분기를 추가한다**: 응답 수신까지 대기 → §2j 카운터 반영(순서 0) → 결과를 루프 파일 `## 미해결 ledger`에 **미판정**으로 기록 → 순서 1~4. 판정·수정·다음 라운드는 재개 세션 몫이다. 루프 파일 스키마는 이미 미판정 blocking을 받으므로 새 필드는 필요 없다.
3. 재넛지 간격(15%p)·임계 기본값은 바꾸지 않는다.
- 예상 효과: 넛지 후 증가폭 = 결과 기록분(수%p, 추정).
- 기계적 강제(넛지 플래그가 있으면 PreToolUse 훅으로 companion 기동을 차단)는 도입하지 않는다. 문구 수리가 실패하는 실사례가 나온 뒤 재론한다(L1, Q5).
