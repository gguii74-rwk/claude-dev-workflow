## 3. 설계 (문면 방향 — 최종 문구는 구현에서)

### F1. codex 라운드 실행 신뢰성

현행 실패 모드(회수 가능 여부 병기 — XVAL2 S4 표, companion 1.0.6 코드 대조 2026-09-21):
- (a) 포그라운드 Bash 도구 timeout(기본 2분·최대 10분)이 라운드 소요(10~16분)보다 짧다 → `--wait` 직접 실행이 죽는다(08-03~04 리뷰 2회 소실). `run_in_background`도 10분 cap이 같다(08-29). **회수 불가 → 재실행.**
- (b) **`adversarial-review`의 `--background`·`--wait`는 1.0.6에서 파싱만 되고 무시된다**(`codex-companion.mjs:714-715` 옵션 파싱 → `:735` 무조건 `runForegroundCommand`) — 전 플랫폼에서 분리 없음(7a:455 macOS · 08-29 Windows). `task --background`만 detached 워커(`:671-680`)를 띄우지만 Bash 툴 timeout·/clear 회수는 못 막는다. **회수: 적대 불가 / `task`는 스레드 재개·`result`.**
- (c) **/clear가 라운드를 죽이는 기제(확정, §1 사슬 2)**: codex 플러그인 `SessionEnd` 훅이 `CODEX_COMPANION_SESSION_ID` 일치 잡의 프로세스 트리를 kill. 셸 세션 분리로는 못 막는다(09-04). env를 비워 결속을 끊는 우회는 **채택하지 않는다**(D5) — 지렛대는 "완료 전 /clear 금지"(F6 ②). **회수: 적대 불가 / `task`는 스레드 재개.**
- (d) 원인 불명의 조기 사망(74초·82초) — **재실행**. **대기 프로세스만 죽는 경우**(하네스 저메모리 kill 09-07·09-14, 10분 cap) — 라운드는 생존, **대기 재개**.

방향(확정):
1. **분리 실행 + 출력 파일 + 종료 마커 + pid 파일**(D4·D6·D11). 라운드 명령(companion 호출 + `-- "$(cat <focus 파일>)"`)을 래퍼 셸 파일에 쓰고 끝에 `echo COMPANION_EXIT:$?`를 붙인다. 분리는 **node 1줄, 전 플랫폼 공통**(node는 훅·companion이 이미 요구): `spawn("bash", [<래퍼>], {detached: true, stdio: ["ignore", <out fd>, <out fd>]}).unref()` 형태로 띄우고 `child.pid`를 pid 파일에 쓴다. **macOS에는 `setsid`가 없다**(이 머신 실측) — setsid 의존 문구를 쓰지 않는다. Windows(Git Bash)에서 Bash 툴 timeout kill을 견디는지는 미검증 → 9단계 실사용 확인(D37); 실패하면 PowerShell `Start-Process` 폴백 1줄(08-29 검증) 병기 패치. **스크립트는 동봉하지 않는다**(D4). ops-hub가 08-04 이후 전 트랙에 정착시킨 방식(C1, "R1 12분·R2 15분·R3 16분·C1 10분에 안정 회수")의 형태 수렴판이다.
   - **파일 위치 = `.remember/`**(D6): `loop-<ledger basename>-<phase>-R<N>.sh` · `.out` · `.pid`(확인 라운드는 `-C<N>`, 프롬프트 파일 `-C<N>.prompt`, focus 파일 `-R<N>.focus`). §0·§2i·§3의 clean 판정·커밋에서 이미 제외된 루프 상태 디렉터리라 추적 파일 편집 금지·리뷰어 디스크 읽기(B12)와 충돌하지 않는다. `.remember/`를 추적하는 repo는 기존 규약대로 사용자 몫.
2. **대기 = 백그라운드 기본**(D1). `run_in_background` until-loop(마커 grep, 10분 cap 안에서 반복) 또는 Monitor로 대기해 **라운드마다 턴이 끝나게 한다** — Stop 훅의 넛지 체크포인트가 라운드 경계마다 생기고, 넛지 시 F6-2 분기가 "현재 라운드까지만"을 성립시킨다. 포그라운드 until-loop는 턴을 유지해 루프 중 넛지를 구조적으로 없애므로 기본으로 두지 않는다(루프 종료·ESCALATE까지 무경고 — §2i ①의 '느껴지거나'는 모델이 사용량을 못 재므로 대체가 안 된다). **대기 프로세스가 죽어도(10분 cap·저메모리 kill) 라운드 실패가 아니다**(D10) — pid 파일로 생존을 확인하고(**`pgrep -f` 자기 매칭 금지**, 09-07 1시간 손실 — D11) 마커를 재확인한 뒤 대기를 재개한다.

### F5. 해시 인용 규칙 — SLIM D15 재개방 → (i) 순서 규정 (D2)

- **문제**: spec·plan phase는 수정 대상과 ledger가 같은 문서라, 한 커밋에 자기 해시를 넣을 수 없다. 그래서 "수정+ledger 커밋 → 해시 채우기 커밋"이 반복된다. **규모(XVAL2 S5)**: 순수 해시 채움 커밋 ≈55건(08-11~09-14, 1파일 1~10줄, 표본 8/8이 분리가 아니라 순증), 라운드당 ≈0.28. 루프당 ledger 커밋 증가(5.9→10.9~13.1)의 주인은 라운드 수(4.8→8)이지 이 규칙이 아니다 — 비용은 소(小)이나 **D15 근거 "비용 0"은 반증**됐다.
- **유지할 요건**: 확인 모드는 수정 커밋 SHA가 필요하다(RL:158·:355). 지킨다.
- **결정(D2)**: SLIM D15를 재개방해 **(i) 순서 규정**으로 바꾼다 — **수정 커밋을 먼저 하고, ledger의 FIXED 행은 다음 커밋에서 그 해시를 인용한다.** 커밋 수는 같지만 "되돌아가 채우는" 커밋이 사라지고, finding별 SHA·기계 감사·확인 프롬프트 첨부물(수정 커밋·diff 요약)은 무손실이다. impl phase(수정 = 코드 커밋, ledger = 문서 커밋)와 동형. ledger 행은 다음 라운드 §2a 커밋 전에 들어가므로 기결정 가드·focus 조립 원본(커밋된 문서)에는 영향이 없다.
- **이력 재작성 SHA 매핑 1줄(D22)**: filter-branch(09-08)·저장소 이전(GitLab 단일 초기 커밋, 09-15)으로 인용 해시가 무효화되면 ledger에 구→신 SHA 매핑을 남긴다. 어느 안이든 공통이라 선택 근거에서는 제외했다.
- **검증(D23)**: 문면은 grep, 효과는 9단계 릴리스 후 ops-hub에서 **"해시 전용 커밋 수/라운드"(기준선 ≈0.28)** 를 직접 잰다 — 자연 지표가 있어 하네스보다 싸다(L3).
- 불채택: (ii) 라운드 표식(`R3` + `git log --grep`) — finding별 SHA 상실·첨부물 계약 재작성. (iii) 현행 유지 + 매핑 1줄 — 반증된 근거를 유지하는 셈(SLIM A2 취지).

### F6. 넛지 후 폭주 차단

넛지의 의미를 "**현재 작업 단위만 마무리하고 다음 단위를 시작하지 않는다**"로 명시한다. **작업 단위 = 리뷰 라운드 1회 · SDD task 1개 · 수정 1건 · 질문 라운드 1회 — phase·루프 전체가 아니다**(D24, 훅 문구와 RL 양쪽에 같은 예시).
1. **훅 문구**(모든 세션 공통 — 실행 세션이 서브에이전트를 띄우고 기다리는 경우도 같은 문제, B4). 최초 넛지·재넛지 양쪽에 동일하게 붙인다(7a D6 "지시 동일 + 사실 추가" 유지 — "즉시 종료"보다 약하므로 D6 취지 안):

   - ② **조건문 형태**(훅은 진행 중 작업을 알 수 없는 정적 문구다): "진행 중인 백그라운드 작업이 있으면 완료 전 /clear 금지. 완료 알림을 받으면 결과를 기록만 하고 멈춘 뒤, 그때 /clear를 안내하라." **넛지 지시는 그 턴에서 끝나지 않는다** — 완료 알림으로 깨어난 뒤에도 유효하다(D1의 백그라운드 대기는 턴을 끝내므로 이 문장이 필요).
   - ③ 핸드오프 파일 = repo·트랙 규약이 정한 핸드오프 파일(기본 `.remember/remember.md`), **review-loop 실행 중이면 그 스킬의 루프 파일**(C-4 D11 단서 유지). 트랙별 파일 운용(C9)을 수용한다.
2. **RL §2i에 진행 중 라운드 분기를 추가한다**: 응답 수신까지 대기(백그라운드 대기 그대로 — 알림으로 깨어난다) → §2j 카운터 반영(순서 0) → 결과를 루프 파일 `## 미해결 ledger`에 **미판정**으로 기록 → 순서 1~4. 판정·수정·다음 라운드(auto-rounds 경계의 batch flush 포함)는 재개 세션 몫이다. 루프 파일 스키마는 이미 미판정 blocking을 받으므로 **새 필드는 없다**(D26) — 규약 위반(/clear 강행)·대기 사망 뒤 완료된 고아 라운드는 재실행한다(응답 미수신 = 예산 미소모). 출력 파일은 규칙 경로(F1-1)라 재개 세션이 원하면 볼 수 있다. F7의 RL:337 정정과 같은 문단이다(같은 웨이브).
3. 재넛지 간격(15%p, 7a D4)·임계 기본값은 바꾸지 않는다(D25). 기계적 강제(넛지 플래그가 있으면 PreToolUse 훅으로 companion 기동을 차단)는 도입하지 않는다 — 문구 수리가 실패하는 실사례가 나온 뒤 재론한다(L1).
- 예상 효과: 넛지 후 증가폭 = 결과 기록분(수%p, 추정). 실측은 FOLLOWUP §3(넛지 후 최대 사용률·루프당 재개 횟수)에서.
- **F1과의 결합(D1)**: 백그라운드 대기가 라운드마다 턴 경계를 만들어 넛지 체크포인트를 보장한다. 포그라운드 대기를 골랐다면 루프 중 넛지 자체가 사라져 이 항목은 비루프 세션에서만 의미가 있었다.
